# デプロイ（Cloud Run + Neon）

> #82 で実施した手動デプロイの記録。**すべて実地検証済みの手順**（書いてから検証ではなく、実行しながら記録した）。
> CD による自動化は #84 で実装済み（末尾の CD 節）。このドキュメントは「手で再現できる一次手順」として維持する。

## 構成

```
GitHub main ──(CD・#84)──> Artifact Registry (asia-northeast1)
                                │  イメージ: api（distroless・server + migrate の2バイナリ）
                                ▼
              Cloud Run Job「migrate」──> Neon (PostgreSQL 16・ap-southeast-1)
                                │              ▲
              Cloud Run「tsunagu-api」─────────┘
                                │  Secret Manager: DATABASE_URL / JWT_SECRET
                                ▼
                        公開 URL（/health ほか）
```

## 判断の記録

| 論点                                 | 判断                                                               | 理由                                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| リージョン                           | API=東京（asia-northeast1）・DB=Singapore（Neon に東京が無かった） | 東京⇔Singapore は約70ms。学習用途で許容。実サービスなら API を asia-southeast1 に寄せる選択もある                               |
| Neon の接続                          | **direct（pooler 不使用）**                                        | Neon の pooler は PgBouncer transaction モードで pgx の prepared statement キャッシュと相性問題。接続数が問題になってから再検討 |
| Postgres バージョン                  | **16**（ローカル・CI と同一）                                      | 環境差バグの排除（バージョン一元化の原則）                                                                                      |
| min-instances                        | **0**                                                              | リクエストが無ければ課金ゼロ。コールドスタート数秒を許容                                                                        |
| 脆弱性スキャン（Container Scanning） | **オフ**（#83・ADR-0011 で確定）                                   | push 毎 $0.26 ×2イメージになるため。代替は無料の govulncheck + GitHub Dependabot                                                |
| 予算アラート                         | 500円（50/90/100% 通知）                                           | 誤課金の早期検知（通知のみ・自動停止はしない）                                                                                  |
| GCP プロジェクト                     | このデプロイ専用に新規作成                                         | **撤退可能性**: `gcloud projects delete` 1回で課金の可能性ごと完全撤去できる                                                    |

## 手順（再現用 CLI）

前提: gcloud CLI・Docker・`.env.prod`（`NEON_DATABASE_URL='...'`・gitignore 済み・**チャットやコミットに貼らない**）

```bash
# 0. 認証とプロジェクト
gcloud auth login
gcloud projects create tsunagu-works-829174 --name="tsunagu-works"
gcloud config set project tsunagu-works-829174
# （コンソールで課金アカウントをリンク + 予算アラート作成）

# 1. API 有効化
gcloud services enable run.googleapis.com artifactregistry.googleapis.com secretmanager.googleapis.com

# 2. Artifact Registry とイメージ push
gcloud artifacts repositories create tsunagu --repository-format=docker --location=asia-northeast1
gcloud auth configure-docker asia-northeast1-docker.pkg.dev
# ⚠️ Apple Silicon では --platform 必須（無いと arm64 になり Cloud Run で "Application exec likely failed"）
docker build --pull --platform linux/amd64 -f api-server/Dockerfile -t tsunagu-api .
docker tag tsunagu-api asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/api:manual-1
docker push asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/api:manual-1

# 3. シークレット（末尾改行を入れない: printf '%s' / tr -d '\n' が重要）
source .env.prod && printf '%s' "$NEON_DATABASE_URL" | gcloud secrets create DATABASE_URL --data-file=-
openssl rand -base64 32 | tr -d '\n' | gcloud secrets create JWT_SECRET --data-file=-
# Cloud Run の実行サービスアカウントに読み取り権限（誰に=SA・何を=secretAccessor）
PROJECT_NUMBER=$(gcloud projects describe tsunagu-works-829174 --format='value(projectNumber)')
gcloud projects add-iam-policy-binding tsunagu-works-829174 \
  --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"

# 4. マイグレーション（Cloud Run Job・API 起動時に流さない理由は api-server/cmd/migrate/main.go 冒頭）
gcloud run jobs create migrate \
  --image asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/api:manual-1 \
  --region asia-northeast1 --command /migrate \
  --set-secrets DATABASE_URL=DATABASE_URL:latest --max-retries 1
gcloud run jobs execute migrate --region asia-northeast1 --wait   # 初回: applied=7

# 5. サービスデプロイ
gcloud run deploy tsunagu-api \
  --image asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/api:manual-1 \
  --region asia-northeast1 --port 8082 --allow-unauthenticated \
  --set-secrets DATABASE_URL=DATABASE_URL:latest,JWT_SECRET=JWT_SECRET:latest \
  --min-instances 0 --max-instances 2

# 6. 確認
gcloud run services describe tsunagu-api --region asia-northeast1 --format='value(status.url)'
curl -si <URL>/health    # 200 + X-Request-Id + {"status":"ok"}
# 本番一巡: signup → 案件作成 → publish → talent signup → 応募 → offer → accept（全て curl で確認済み）
```

## 踏んだ罠（実録）

| 症状                              | 原因                                                                    | 対処                                                                    |
| --------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Job 実行が HTML の 404            | リージョン名タイポ等で存在しないエンドポイントへ                        | `asia-northeast1`（ハイフン1つ）を正確に                                |
| `Application exec likely failed`  | **Apple Silicon の docker build は既定 arm64**・Cloud Run は amd64 専用 | `--platform linux/amd64` でリビルド（ローカルで動くのに本番で死ぬ典型） |
| タグを付け直しても Job が古いまま | Job/サービスは作成時にイメージ実体（ダイジェスト）を固定する            | `gcloud run jobs update / services update` で再解決させる               |
| ダイジェストが増えていく          | タグは動き、旧ダイジェストは untagged で残る                            | untagged は削除して良い（#84 でクリーンアップポリシー）                 |

## セキュリティ運用

- **秘密の置き場は3層**: ローカル=`.env*`（gitignore・Claude も読まない）／本番=Secret Manager（環境変数直書きなし・最小権限の secretAccessor）／CI=#84 で Workload Identity Federation（キーを持たない）
- GitHub 側: **Secret scanning + Push protection**・**Dependabot alerts / security updates** 有効化済み（#82 時点）
- 脆弱性対応の実例（#82）: kin-openapi の指摘 → `go get` で更新・Go stdlib の指摘 → `docker build --pull` で最新パッチの golang イメージ・**govulncheck で「実際に到達可能か」を判定**してから騒ぐ
- 本番 JWT_SECRET はローカルと別のランダム値（環境ごとに独立）

## web のデプロイ（#83・ADR-0011）

Next.js は `output: 'standalone'` + マルチステージ Dockerfile（node:24-slim・291MB）で
api と同じ Artifact Registry / Cloud Run に載せる（Vercel 不採用の判断は [ADR-0011](adr/0011-web-on-cloud-run.md)）。

```bash
# ビルド（⚠️ Apple Silicon は --platform 必須・QEMU で 5〜15分）
docker build --pull --platform linux/amd64 -f web/Dockerfile -t tsunagu-web .
docker tag tsunagu-web asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/web:manual-1
docker push asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/web:manual-1

# デプロイ（api との違い: --set-env-vars = API_URL は秘密ではない・--port 指定なし = 既定 8080 を PORT で受ける）
gcloud run deploy tsunagu-web \
  --image asia-northeast1-docker.pkg.dev/tsunagu-works-829174/tsunagu/web:manual-1 \
  --region asia-northeast1 --allow-unauthenticated \
  --set-env-vars API_URL=<api の Service URL> \
  --min-instances 0 --max-instances 2
```

- 確認済み: ブラウザで公開 URL からログイン〜応募一覧・Cookie は **HttpOnly + Secure**（session.ts の `secure: production` が本番で発火）
- web 固有の要点: `HOSTNAME=0.0.0.0`（コンテナ外から届くバインド）・standalone の static は別 COPY・
  pnpm workspace の照合に api-server/package.json（マニフェストのみ）が必要・ignore は Dockerfile ごとに分割
  （`web/Dockerfile.dockerignore` / `api-server/Dockerfile.dockerignore`）
- **イメージが約300MB** のため untagged の削除を怠ると無料枠 0.5GB を超える → #84 のクリーンアップポリシーが実質必須

## CD（#84・main マージ＝デプロイ）

it-support-service の型に合わせた2段構成。**手順の一次情報はルートの `cloudbuild.yaml`**・GHA（`.github/workflows/deploy.yml`）は WIF 認証と発注だけの薄い起動役。

```
main マージ（paths 該当時）
  → deploy.yml: WIF でキーレス認証 → gcloud builds submit --substitutions=_SHA=<コミットSHA>
  → cloudbuild.yaml:
      build api → build web → push ×2（タグ=コミットSHA）
      → migrate Job update + execute --wait   ★失敗したらここで停止＝旧イメージのまま
      → services update tsunagu-api → tsunagu-web（イメージだけ差し替え・設定は維持）
```

### 身分（サービスアカウント）の二層

| 身分 | SA | 権限 |
| --- | --- | --- |
| GitHub Actions（発注役） | `github-deployer` | cloudbuild.builds.editor + ソースバケット書き込みのみ。**デプロイ権限なし** |
| Cloud Build（実行役） | compute 既定 SA | run.admin / artifactregistry.writer / logging.logWriter / secretAccessor（#82） |

- **WIF**: プール `github` / プロバイダ `github-provider`（issuer=GitHub OIDC・`attribute-condition` でこのリポジトリのみ許可）。GCP のキーは**どこにも存在しない**
- workflow 側の要件: `permissions: id-token: write`（OIDC トークン発行の許可）

### 仕様同期の守り（4層の完成）

① turbo タスクグラフ（仕様変更→生成→ビルド連鎖）／② CI の生成物差分チェック／③ **GitHub Ruleset `protect-main`**（main 直 push 禁止・PR 必須・`backend` / `frontend` チェック緑必須）／④ CD は main を無条件に信頼——③が入ったことで④の前提が仕組みで保証された。

- ⚠️ **required checks × paths 絞りの罠**: paths 対象外の PR（docs のみ等）ではチェックが起動せず「Expected」のまま永遠にマージ不可になる。対処は GitHub 公式の型＝**同じ workflow 名・ジョブ名の常に成功するツイン**（`backend-ci-skip.yml` / `frontend-ci-skip.yml`・paths-ignore が本体と鏡写し）。**本体の paths を変えたらツインも必ず同期する**

### Artifact Registry クリーンアップポリシー（適用済み）

untagged 即削除・14日超削除・**ただし最新3世代は保護**（Keep が Delete に勝つ）。web 291MB × 世代増殖で無料枠 0.5GB が尽きるのを防ぐ。

```json
[
  { "name": "delete-untagged", "action": { "type": "Delete" }, "condition": { "tagState": "UNTAGGED" } },
  { "name": "delete-older-than-14d", "action": { "type": "Delete" }, "condition": { "olderThan": "1209600s" } },
  { "name": "keep-recent-3", "action": { "type": "Keep" }, "mostRecentVersions": { "keepCount": 3 } }
]
```

### 運用

- **手動再デプロイ**: GitHub の Actions → deploy → Run workflow（workflow_dispatch）。または緊急時はローカルから
  `gcloud builds submit --config cloudbuild.yaml --substitutions=_SHA=$(git rev-parse --short HEAD)`（CD と同一手順が走る）
- **ロールバック**: 旧コミットの SHA タグを `gcloud run services update --image` で指定（イメージは最新3世代残っている）
- ログ: `CLOUD_LOGGING_ONLY` のためターミナルには流れない。進行はコンソールの Cloud Build → 履歴
- 費用: Cloud Build は無料枠（月2,500分）内・GHA は公開リポジトリ無料
