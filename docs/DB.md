## Phase0 #3 Step1: users テーブルと sql-migrate 導入

**何をした**: sql-migrate を導入し、最初のマイグレーション `migrations/ddl/20260803000001-create_users.sql` で users テーブルを定義（email UNIQUE / password_hash / role CHECK / TIMESTAMPTZ）。`dbconfig.yml`・`Makefile`（up/down/status/new）を整備。

**概念**

- **マイグレーション管理**: DDLを日付順のファイルで積み上げ、適用履歴を `gorp_migrations` テーブルに記録。「どこまで適用済みか」をDB自身が知っているので、同じファイルが二重適用されない（＝`IF NOT EXISTS` に頼る必要がなくなる）
- **Up / Down**: Up=適用、Down=巻き戻し。Downを毎回書く規律が「変更を戻せる設計」を強制する。ただし本番でのdownは原則禁止（DROP TABLEでデータが消える。戻したいときは「逆操作のUp」を新規作成する＝ロールフォワード）
- `BIGSERIAL`: 自動採番の64bit整数（`SERIAL`=32bitは上限約21億。ユーザー系テーブルは最初からBIGで困らない）
- `UNIQUE` 制約: DBが重複を物理的に拒否する最後の砦。アプリ側チェックだけでは同時リクエストの競合（TOCTOU）を防げない
- `CHECK (role IN (...))`: 列挙値の制約。PostgreSQL の `ENUM` 型と違い、値の追加が制約の張り替えで済み、マイグレーションが軽い
- `TIMESTAMPTZ`: タイムゾーン付き時刻。`TIMESTAMP`（tzなし）は「どの地域の時刻か」が失われ事故のもと

**✅ベストプラクティス**: スキーマ変更は必ずマイグレーションファイル経由（psqlで直接DDLを流さない）／パスワードは `password_hash` 列名にして「ハッシュしか入らない」ことを名前で強制する／時刻列は `TIMESTAMPTZ NOT NULL DEFAULT now()`

**⚠️アンチパターン**: 適用済みマイグレーションファイルを後から編集する（履歴とDBの実態がズレる。修正は新しいファイルで）／本番での安易な down／`TIMESTAMP`（tzなし）／アプリ側の重複チェックだけに頼って UNIQUE を張らない

**理解度チェック**: gorp_migrations テーブルの役割は？ 本番で down を使わずロールフォワードする理由は？ UNIQUE制約がアプリ側チェックより強い理由を同時リクエストの観点で説明できるか？

## Phase0 #31: シードデータ（upsert・冪等な投入）

### 何をした

`migrations/seed.sql`（開発用ユーザー4人・パスワードは既知の password123）を作成し、`make seed` で投入。`ON CONFLICT (email) DO UPDATE` で何度実行しても既知の状態に収束する。

### 概念

- **シード ≠ マイグレーション**: スキーマ（ddl/）は全環境で適用するが、テストユーザーはローカル専用。sql-migrate の管理外（migrations/seed.sql）に置き、本番に混入しない構造にする
- **ON CONFLICT（upsert）の2方式**:
  - `DO NOTHING`: 既存行を尊重（重複を静かにスキップ）。「初回だけ入れたい」データ向け
  - `DO UPDATE`: 既存行を上書きし**必ず既知の状態に収束**させる。「実行後の状態を保証したい」シード向け（過去の手動テストで同emailが別パスワードで存在してもログイン可能を保証）
- **EXCLUDED 疑似テーブル**: 衝突時に「挿入しようとした行」の値を参照する構文（`SET password_hash = EXCLUDED.password_hash`）
- **`psql -v ON_ERROR_STOP=1`**: エラー時に即終了させる（既定では続行してしまい、失敗に気づけない）
- 事前計算した bcrypt ハッシュのコミットは「既知のdev用パスワード」だから許される（実在の資格情報は絶対に置かない）

### ✅ベストプラクティス

- シードは冪等に（何度叩いても同じ結果）
- テストユーザーの資格情報はREADMEに明記（探させない）

### ⚠️アンチパターン

- シードをマイグレーション（ddl/）に入れて本番にテストユーザーを撒く
- シードのたびに手でユーザー登録（手順が属人化・状態が不定に）

### 理解度チェック

- [ ] DO NOTHING と DO UPDATE の使い分け基準を言える
- [ ] EXCLUDED が何を指すか言える
- [ ] シードを ddl/ に置いてはいけない理由を言える

## Phase1 #60: 大量データ生成（案件5万件）

### 何をした

`migrations/seed_large.sql` で案件5万件＋掲載元企業10社を生成。`make seed-large` で**約2秒**で投入でき、何度実行しても同じデータになる。

### 概念

- **`generate_series` による一括生成**: `INSERT ... SELECT ... FROM generate_series(1, 50000)` で1文にまとめる。1行ずつ INSERT すると往復とパースが5万回発生し数分かかるが、1文なら数秒
- **決定的な擬似ランダム**: `random()` を使うと実行のたびに結果が変わり、性能計測の before/after を比較できない。連番 i から `(i * 17) % 36` のように導出すれば**誰がいつ実行しても同じデータ**になる
- **剰余で分散させるときの落とし穴**: `(i * m) % n` は **m と n が互いに素でないと偏る**。実際 14種のスキルに対し乗数7を使ったところ `(i*7)%14` が 0 か 7 しか取らず、**2種類のスキルに全件が集中**した。さらに「複数の乗数」を使う場合は *mod n での剰余が互いに異なる*必要がある（17 ≡ 3 (mod 14) で衝突し、DISTINCT で個数が減った）
  - 最終形は `(i*3 + j*5) % 14`（i で開始位置をずらし、j で5ずつ進める）。3も5も14と互いに素なので j=0..3 で必ず異なる4つになる
- **delete-then-insert による冪等性**: 生成データは `title LIKE 'デモ案件 #%'` で識別できるので、実行時にまず削除してから作り直す。手動作成データは消えない（upsert とはこの点が異なる）
- **`ANALYZE` の実行**: 大量投入後は統計情報が古いままで、プランナが誤った実行計画を選ぶ。投入直後に `ANALYZE` して実データに基づく計画にする
- **`CROSS JOIN LATERAL`**: 同じ式（下限単価）を上限計算でも使い回すため、一度だけ計算して名前を付ける

### ✅ベストプラクティス

- 計測用データは「現実的なばらつき」を持たせる（1社に集中させると company_id の索引が意味を持たない・statusが一様だと絞り込みの効果が見えない）
- created_at をばらけさせる（新しい順の並び替え・seekページングの計測に必要）
- 生成データと手動データを識別できる接頭辞を付ける

### ⚠️アンチパターン

- ループで1行ずつ INSERT（桁違いに遅い）／random() を使って再現性を失う
- 剰余の乗数を確認せず「なんとなく素数」で分散させたつもりになる（今回の実バグ）
- 投入後に ANALYZE を忘れる

### 理解度チェック

- [ ] generate_series が速い理由を説明できる
- [ ] 計測用データで random() を避ける理由を言える
- [ ] `(i*7)%14` が2値しか取らない理由を説明できる
- [ ] 投入後に ANALYZE が必要な理由を言える

## Phase1 #83: applications テーブル（一意制約と複合索引）

### 何をした

応募（人材→案件）を保持する `applications` を作成。**二重応募を `UNIQUE (project_id, talent_id)` でDB側から拒否**し、状態機械①の土台にした。

### 概念

- **交差テーブル**: `projects` と `talents` の多対多を「応募」という**業務上の意味を持つ実体**として表現する。単なる中間テーブルと違い、status・志望動機・時刻など固有の属性を持つ
- **参照先の選択（users ではなく talents）**: `projects.company_id → companies.id` と対称にした。結果として**「人材プロフィール未登録では応募できない」という仕様が外部キーとして表現される**（アプリのif文より強い保証）
- **TOCTOU（Time Of Check to Time Of Use）**: 「SELECT で重複確認 → INSERT」は、確認と挿入の間に別リクエストが割り込むと両方通ってしまう。手元では絶対に再現せず、本番の同時アクセスで初めて出る類のバグ。**一意性はDB制約でしか担保できない**
- **UNIQUE 制約は索引でもある**: PostgreSQL は UNIQUE を btree 索引で実装する（`\d` の Indexes に現れる）。制約と検索性能を1つで賄える
- **複合索引の左端規則（leftmost prefix）**: `(project_id, talent_id)` の索引は「姓→名で並んだ電話帳」と同じ。`project_id` での絞り込みには効くが、**`talent_id` 単独では効かない**。そのため「自分の応募一覧」用に `talent_id` 単独の索引を別途張った
- **外部キーに索引は自動で付かない**: PostgreSQL は参照**先**（主キー側）にしか索引を持たない。参照元の絞り込み・JOIN用には自分で張る
- **時刻列だけ NULL 許容**: 文字列は空文字、数値は0で「未設定」を表せるが、**時刻には自然なゼロ値が無い**（`0001-01-01` を「まだ」の意味に使うと事故る）。方針の例外にする場合は**理由をコメントに残す**
- **status の CHECK に将来の値も入れる**: 今回書き込むのは `applied` だけだが、取りうる6値を先に定義。状態機械の全体像がスキーマから読め、遷移実装時にマイグレーションを足さずに済む

### ✅ベストプラクティス

- 一意性はアプリではなく**DB制約**で担保する（アプリのチェックはUXのため）
- Down を書いたら**実際に巻き戻して確認**する（戻せる形かの設計レビューになる）
- 方針の例外にはコメントで理由を書く

### ⚠️アンチパターン

- SELECT → INSERT で重複チェック（同時実行で破れる）
- 外部キーを張って索引を張り忘れる
- 複合索引があるから単独索引は不要だと考える（左端規則を忘れる）

### 理解度チェック

- [ ] TOCTOU を具体的な状況で説明できる
- [ ] `(a, b)` の索引が `b` 単独に効かない理由を言える
- [ ] 時刻列だけ NULL を許容した理由を言える

## Phase1 #96: JOIN と集計（LEFT JOIN・count(*) の罠・FILTER 句）

### 何をした

企業向け案件一覧 `GET /me/projects` を実装し、**案件ごとの応募件数をDB側で集計**するようにした。フロントが案件ごとにAPIを叩いていた fan-out（2N+1 リクエスト）が**1リクエスト**になった。

### 概念

#### JOIN は「行を作る」操作

ベン図では「どのデータが含まれるか」しか表せず、**結果が何行になるか**を表せない。実務の落とし穴はほぼ全部そちら側にある。

正しい理解は **「2つの表から、条件に合う行の組み合わせを1行ずつ作る」**。作られた中間結果に対して、そのあと `WHERE` / `GROUP BY` / `count()` が働く。

- **JOIN は行を増やす**: 応募が2件ある案件は、結合結果では2行になる
- **INNER は相手がいない行を消す**: 応募0件の案件が一覧から消える

#### LEFT JOIN は「左を必ず残す」

相手が見つからない場合、**右側の列をすべて NULL で埋めた行**を作る。この行は「存在する」——ここが次の罠に直結する。

#### count(*) が 0 件を 1 と数える

```sql
SELECT p.title, count(*)      -- ❌ 応募0件の案件が「1」になる
FROM projects p
LEFT JOIN applications a ON a.project_id = p.id
GROUP BY p.id
```

- `count(*)` は**行の数**を数える。LEFT JOIN が作った「NULL で埋まった行」も1行なので 1 と答える
- `count(a.id)` は**その列が NULL でない行**だけ数えるので、正しく 0 になる
- **普段この2つは同じ結果になる**（NOT NULL の列なら常に一致）。**LEFT JOIN と組み合わせたときだけ意味が変わる**

#### FILTER 句 — 1スキャンで複数の集計

```sql
count(a.id)                                     AS applications_count,
count(a.id) FILTER (WHERE a.status = 'applied') AS pending_count
```

- 集約関数に条件を付けられる（PostgreSQL 9.4+）
- **同じ結合結果を1回スキャンするだけ**で2つの数字が取れる
- 古い書き方は `sum(CASE WHEN ... THEN 1 ELSE 0 END)`。動作は同じだが FILTER のほうが意図が読める

#### 同じクエリ内で JOIN を使い分ける

```sql
JOIN      companies c    ON c.id = p.company_id      -- 会社は必ず存在する（FKがNOT NULL）
LEFT JOIN applications a ON a.project_id = p.id      -- 応募は0件かもしれない
```

判断基準は **「相手が必ず存在するか」**。外部キーが NOT NULL なら INNER、0件がありうるなら LEFT。

#### 件数を数えるクエリでは結合を外す

**JOIN は行を増やす**ので、表示用の FROM 句を流用すると総件数が水増しされる（応募3件の案件が3行に数えられる）。

- 一覧用（LEFT JOIN あり）と件数用（結合なし）で **FROM を別々に定義する**
- 「何を1件と数えたいのか」を決めてから、必要な結合だけを書く

#### 主キーでの GROUP BY

PostgreSQL は**主キーで GROUP BY すれば同じテーブルの他の列も選べる**（主キーが決まれば行が一意に決まるため）。`p.title` 等を列挙せずに済む。

#### RIGHT JOIN を使わない理由

`FROM a RIGHT JOIN b` と `FROM b LEFT JOIN a` は**完全に同じ結果**。SQLは「主役の表 → 付け足す表」と読むので、**FROM に主役を書き、LEFT で足していく**と決めると3表以上でも追える。

- そもそも**外部キー制約がある限り「親のいない子」は存在しない**ため、RIGHT の出番はほぼ無い

### 実測（EXPLAIN ANALYZE）

最悪ケース（**1社が5000件の案件を持つ**シードデータ）で計測:

```
Limit                    (actual time=3.666..3.669 rows=20)
  -> Sort                Sort Method: top-N heapsort  Memory: 29kB
    -> HashAggregate     (actual time=2.816..3.218 rows=5000)
      -> Bitmap Index Scan on projects_company_id_idx  (rows=5000)
```

- `projects_company_id_idx` が効いている（Seq Scan ではない）
- **LIMIT 20 なのに 5000行すべてを集約している** → `GROUP BY` + `ORDER BY` + `LIMIT` では、上位20件がどれかを知るために全件集約が必要
- それでも **3.7ms**。1社が5000件掲載するのは非現実的なので問題なしと判断
- **`top-N heapsort`**: 全件ソートせず「上位20件だけ保持する」最適化をプランナが選んでいる

### ✅ベストプラクティス

- **集計はDBに任せる**（アプリでループして数えない）
- 件数のクエリでは「**何を1件と数えるのか**」を確認し、不要な結合を外す
- 実行計画は**最悪ケースのデータ**で測る
- 複数の集計は `FILTER` で1回のスキャンにまとめる

### ⚠️アンチパターン

- 集計に INNER JOIN（0件の親が消える）
- LEFT JOIN で `count(*)`（0件が1件になる）
- 一覧と件数で同じ FROM を使い回す
- RIGHT JOIN（表の順番を入れ替えて LEFT に直す）

### 理解度チェック

- [ ] INNER にすると何が起きるか、行レベルで説明できる
- [ ] LEFT JOIN で `count(*)` が 0 を 1 と数える理由を言える
- [ ] `count(*)` と `count(列)` が普段同じ結果になるのはなぜか言える
- [ ] 同じクエリ内で INNER と LEFT を使い分ける基準を言える
- [ ] 件数クエリで結合を外す理由を言える

## Phase2 #103: 契約テーブル（スナップショットとトランザクション）

### 何をした

`contracts` テーブルを作り、**応募が承諾された瞬間にトランザクションで契約を自動生成**するようにした。

### 概念

#### スナップショット — 意図的な非正規化

契約の単価・案件名・稼働時間は、案件を参照せず**値でコピーして保存**する。

「正規化に反するのでは？」への答えは **同じ事実ではないから**:

|                            | 意味                     | 変わるか                |
| -------------------------- | ------------------------ | ----------------------- |
| `projects.hourly_rate_max` | **今の募集条件**         | 企業が編集できる（#97） |
| `contracts.hourly_rate`    | **あのとき合意した条件** | **絶対に変わらない**    |

- 正規化の目的は「同じ事実を1箇所で管理し、更新漏れを防ぐ」こと。**別の事実なら別の列に持つのが正しい**
- 参照のままだと「承諾後に企業が単価を書き換えると、契約の表示まで変わる」
- **確定した合意は値でコピーする**（ECの注文明細に商品名・価格をコピーするのと同じ理屈）

**非正規化の動機は2つあり、区別する**:

- **正しさ**のため: 条件のスナップショット（時間軸の固定）
- **性能**のため: `company_id` / `talent_id` を契約に直接持つ（`contracts → applications → projects → companies` を毎回結合しない）

#### ON DELETE CASCADE を付けない選択

`project_id` には CASCADE を付けない。**契約が残っているのに案件が消える**のを防ぐため（外部キー制約が削除を拒否する）。
当事者（`company_id` / `talent_id`）には付ける。すべての外部キーに機械的に付けない。

#### トランザクション

応募の `accepted` と契約の存在は**同じ出来事の裏表**。片方だけ真になる状態は業務的にありえない。

| 応募         | 契約     |                                                     |
| ------------ | -------- | --------------------------------------------------- |
| accepted     | あり     | ✅                                                  |
| offered      | なし     | ✅                                                  |
| **accepted** | **なし** | ❌ 人材は承諾したのに契約が無い（手で直すしかない） |

```go
tx, err := db.Begin()
if err != nil { return res, err }
// 先に defer しておくことで、途中で return してもロールバックされる。
// Commit 済みなら Rollback は何もしない（返るエラーは無視してよい）
defer func() { _ = tx.Rollback() }()
...
return res, tx.Commit()
```

- **`defer tx.Rollback()` を最初に書く**のが定石。この関数には return が4箇所あり、各所に手で書くと**1箇所忘れた瞬間にトランザクションが開いたまま残る**（接続プールを1本占有し続ける）
- `_ =` で戻り値を捨てるのは、Commit 済みの Rollback が `ErrTxDone` を返すため（正常な流れ）
- **`*sql.Tx` は `*sql.DB` とほぼ同じメソッドを持つ**ので `db.` → `tx.` の書き換えだけで済むが、意味は違う（Commit するまで他の接続から見えない）

#### `INSERT ... SELECT` でスナップショットを取る

```sql
INSERT INTO contracts (application_id, project_id, ..., title, hourly_rate, ...)
SELECT a.id, p.id, ..., p.title, p.hourly_rate_max, ...
FROM applications a JOIN projects p ON p.id = a.project_id
WHERE a.id = $1
```

- 値をアプリに持ってこず**DBの中だけでコピー**する。1回のクエリで完結し、読んでから書くまでの隙間もできない
- 「読む → アプリで組み立てる → 書く」だと2往復し、その間に案件が編集されうる

#### 契約が生まれる条件は遷移表が保証している

```go
if to == applicationStatusAccepted { createContractFromApplication(tx, id) }
```

一見単純な条件だが、**手前で遷移表を通っている**。`accepted` に入れるのは「offered から・人材のみ」の1通りだけなので、**契約が生まれるのはダブルオプトインが成立した瞬間に限られる**。
この条件文は「いつ契約を作るか」を決めていない——**遷移表が決めている**。

#### 防御は重ねる

楽観ロック（`WHERE status = 'offered'`）をすり抜けても、`application_id` の UNIQUE が最後に止める。
UNIQUE違反は 500 ではなく **409 に翻訳**する（原因不明のエラーではなく「競合」としてユーザーに伝わる）。

### ✅ベストプラクティス

- **確定した合意（契約・注文・請求）は値でコピーする**
- 非正規化するときは**理由をコメントに残す**（後任が「バグでは？」と直さないように）
- **1つの事実が複数の表にまたがるならトランザクション**
- `defer` でロールバックを保証する（各 return に書かない）

### ⚠️アンチパターン

- 契約・注文が商品マスタを参照したまま（**マスタを直すと過去の取引が書き換わる**）
- すべての外部キーに機械的に `CASCADE` を付ける
- 各 `return` の前に `tx.Rollback()` を手で書く
- 「アプリが正しく実装されていれば大丈夫」で済ませる

### 理解度チェック

- [ ] 契約に単価をコピーする理由と、「正規化に反するのでは」への反論を言える
- [ ] 非正規化の2つの動機（正しさ / 性能）を区別できる
- [ ] `defer tx.Rollback()` を最初に書く理由を言える
- [ ] `INSERT ... SELECT` が「読んで書く」より優れている点を言える

## Phase2 #105: 週次の稼働報告（週の扱いと二重提出の防止）

### 何をした

`work_reports` テーブルと、提出・再提出・承認/差し戻し・一覧のAPIを実装した。**このサービスの独自機能の柱のひとつ**——「働きぶりが見えない」という企業側の不安と、「作業した証拠を残したい」という人材側の要求を同時に解決する。

### 概念

#### 週は「開始日（DATE）」で持つ。週番号の文字列にしない

`"2026-W32"` のようなISO週番号で持つと**年跨ぎで壊れる**。12/29〜1/4 は同じ週なのに年が変わるため、`2026-W53` なのか `2027-W01` なのかで実装が揺れ、並べ替えも破綻する。

**週の開始日そのもの**を DATE で持てば、比較（`WHERE week_start >= ...`）も並べ替えも素直にできる。

#### 丸めはDB側で

```sql
INSERT INTO work_reports (contract_id, week_start, ...)
VALUES ($1, date_trunc('week', $2::date)::date, ...)
```

- PostgreSQL の `date_trunc('week', ...)` は **ISO週（月曜始まり）**。金曜を渡しても日曜を渡しても同じ月曜になる
- **クライアントの週計算を信用しない**。ブラウザやライブラリによって週の開始曜日が違う可能性がある
- Go 側で丸めることもできるが、DB側なら**どの経路の INSERT でも同じ結果**になり、「保存される値」と「丸める処理」が同じSQLの中で読める

#### 日付の妥当性はアプリ側で先に検証する

`date_trunc('week', 'あいうえお'::date)` はDBでエラーになり **500** が返る。ユーザーには「サーバーエラー」としか見えない。

```go
// 日付として解釈できることをここで確認する。DBに任せると
// パースエラーが500として返ってしまい、入力ミスだと分からない
if _, err := time.Parse("2006-01-02", req.WeekStart); err != nil { ... 400 ... }
```

**DBは正しさを守り、アプリは何が悪いかを伝える**——二重に見えるが目的が違う。

#### DATE は日付文字列で返す

Go は DATE を `time.Time` で受けるため、そのままJSONにすると `"2026-08-03T00:00:00Z"` になる。**時刻もタイムゾーンも意味を持たない**のにクライアントが解釈に迷うので、`weekStart.Format("2006-01-02")` で日付だけの文字列にする。

#### 二重提出の防止は UNIQUE で

`UNIQUE (contract_id, week_start)`。#83 の二重応募と同じ形で、**事前SELECTではなくUNIQUE違反を拾って409**にする（確認と挿入の間に別リクエストが入ると破れるため）。

#### 「未設定」の表現は型で決める

| 列            | 型          | 未設定の表現                      | 理由                                     |
| ------------- | ----------- | --------------------------------- | ---------------------------------------- |
| `review_note` | TEXT        | **空文字**（NOT NULL DEFAULT ''） | 文字列は空値で表現できる                 |
| `reviewed_at` | TIMESTAMPTZ | **NULL**                          | 時刻に「未設定」を表す自然なゼロ値が無い |

#### 昇順索引と降順索引

`UNIQUE (contract_id, week_start)` があるので同じ列の索引が2本になるが、並び順が違う（一覧は新しい週から表示する）。
実際には PostgreSQL は昇順索引を逆から読めるため**必須ではない**が、主要な用途に対して意図を明示する価値を取った。稼働報告は週1回の書き込みなので、書き込みコストより読み取りの意図明示を優先している。

### API設計の判断

#### 再提出は PUT で内容修正と状態変更を同時に行う（#97 と逆の判断）

|                | 案件（#97）            | 稼働報告（#105） |
| -------------- | ---------------------- | ---------------- |
| 下書きの概念   | **ある**               | **無い**         |
| 「保存」の意味 | 公開せず残す           | —                |
| 判断           | 内容と状態を**分ける** | **分けない**     |

**ルールが違うのではなく前提が違う**。稼働報告は「内容を出すこと自体が提出」で、提出しない報告は存在しない。分けると「直す → 出し直す」の2手になり、操作と意味がずれる。

ただし**判定は遷移表に通す**（`rejected → submitted`）。これにより「承認済みを書き換える」「提出済みを何度も出し直す」を同じ仕組みで防げる。

#### 差し戻しには理由を必須にする（#104 の中止とは逆）

|                  | 契約の中止（#104） | 報告の差し戻し（#105）   |
| ---------------- | ------------------ | ------------------------ |
| 相手に求める行動 | **無い**（終わる） | **修正して出し直す**     |
| 理由が無いと     | 気まずいが進める   | **何を直すか分からない** |
| 判断             | 持たせない         | **必須**                 |

**相手に次の行動を求めるなら、理由は必須**。同じ「理由」でも業務上の役割が違う。

#### 列の意味を1つに保つ

承認時は `review_note` を**明示的に空にする**。列名は「確認メモ」だが画面では「差し戻し理由」として表示されるため、承認時のコメントが入ると意味が壊れる。

#### ページネーションを付けない判断

週ごとに1件しか存在せず（UNIQUE制約）、契約期間もせいぜい数十週。**件数の上限がドメインで決まっている**。
画面では週の連続性を見せたいので、ページで切れるとむしろ扱いにくい。**機械的に付けない**。

#### 親の権限チェックを子に流用する

稼働報告の閲覧権限は、**契約の当事者チェック**（#104 の `fetchOwnedContractStatus`）をそのまま使う。
「契約の当事者は、その契約の記録をすべて見られる」という単純なルールで足りる。報告ごとに権限を持たせると複雑になるだけ。

### ✅ベストプラクティス

- **週・月などの期間は「開始日」で持つ**（期間名の文字列にしない）
- **正規化はDB側で**（どの経路でも同じ結果になる）
- 型エラーは**アプリ側で先に検証**して400にする（DBに任せると500になり原因が伝わらない）
- **相手に次の行動を求めるなら理由は必須**
- 列は**1つの意味だけ**を持たせる
- ページネーションは**必要なときだけ**

### ⚠️アンチパターン

- 週を `"2026-W32"` のような文字列で持つ／クライアントが計算した週をそのまま保存する
- 一貫性のためだけに、前提が違うものを同じ形にする
- すべての「理由」欄を一律で任意にする
- 一覧には必ずページネーションを付ける（機械的な適用）

### 理解度チェック

- [ ] 週を開始日で持つ理由（週番号の文字列で何が壊れるか）を言える
- [ ] 丸めをDB側で行う理由を言える
- [ ] #97 では分けたのに稼働報告では分けなかった理由を言える
- [ ] #104 の中止と #105 の差し戻しで理由の扱いが違う理由を言える
- [ ] 一覧にページネーションを付けなかった理由を言える

## Phase2 #106: 契約一覧・詳細 — 同じ問題に同じ解法を使う

### 何をした

`GET /me/contracts`（一覧）を実装し、詳細（`GET /me/contracts/{id}`）にも稼働報告の集計を追加した。**新しい概念はほぼ無く、#96 で確立した形をそのまま再利用**している。

### 同じ形が効いたこと

|                            | #96（案件一覧）                     | #106（契約一覧）            |
| -------------------------- | ----------------------------------- | --------------------------- |
| 集計対象                   | 応募                                | 稼働報告                    |
| **LEFT JOIN が必要な理由** | 応募0件の案件を消さない             | **報告0件の契約を消さない** |
| `count(列)` を使う理由     | LEFT JOIN の NULL 行を1件と数えない | 同じ                        |
| `FILTER` の用途            | 未対応の応募数                      | 未確認の報告数              |
| 総件数で結合を外す理由     | JOINが行を増やして水増しされる      | 同じ                        |

**契約一覧では LEFT JOIN がより深刻**: 成立直後の契約は必ず報告0件なので、INNER にすると**新しい契約ほど見えなくなる**。

**同じ問題には同じ解法を使う**。新しい書き方を試さないほうが、後から読む人にとって圧倒的に楽（「案件一覧が読めれば契約一覧も読める」状態になる）。既出のパターンには**参照先をコメントに書き**、理由を繰り返さない。

### 概念

#### 構造体の埋め込みで型を再利用する

```go
type contractListItem struct {
	contractResponse                    // ← 埋め込み（フィールド名を書かない）
	WorkReportCount    int `json:"work_report_count"`
	PendingReportCount int `json:"pending_report_count"`
}
```

- 埋め込んだ型のフィールドに**直接アクセスできる**（`item.ID`）
- **JSONは平坦に出力される**（`{"contractResponse": {...}}` とネストしない）
- 詳細のフィールドを二重に書かずに済む

#### 一覧と詳細は同じ形で返す

1件取得でも `LEFT JOIN + GROUP BY` が必要になるが、**対象が1契約に限られるので負荷は無視できる**。

判断基準は**どちらのコストが大きいか**:

- 集約のコスト（サーバー側）: 1契約あたり数十行のスキャン
- 分岐のコスト（画面側）: 「詳細では件数が出せない」たびに別APIを呼ぶか諦めるかの判断

明らかに後者が大きいので、**サーバー側が引き受ける**。

#### 所有チェックの条件だけがロールで変わる

契約は当事者が同じものを見るため、視点でレスポンスの形を変えない（#104 の判断）。
**変わるのは「自分の契約とは何か」の定義だけ**で、それは WHERE の1行に現れる。

```
FROM ... JOIN companies co ... JOIN talents t ...   ← 完全に同じ
WHERE co.user_id = $1   （企業）
WHERE t.user_id  = $1   （人材）
```

`companies` / `talents` は**相手の名前を出すために両方結合済み**なので、どちらの条件も追加コストなしで書ける。

#### 再取得の頻度が違うものは分ける

稼働報告の一覧は契約詳細に含めず、別エンドポイント（`GET /contracts/{id}/work-reports`）のまま。
1つにまとめると、**報告を承認するたび契約の情報まで取り直す**ことになる。

#### 古くなったコメントを見直す

#104 で書いた「一覧より先にこの1件取得だけを用意している」というコメントは、一覧ができた時点で**嘘になる**。今回書き換えた。

**コメントは書いた時点の状況を写す**。状況が変われば嘘になり、**嘘のコメントは無いコメントより害がある**（読む人が誤った前提で判断する）。
「実装を変えたらコメントも見直す」は当然だが、**他のIssueが進んだせいで古くなる**ケースは見落としやすいので意識的に確認する。

### 実行計画（EXPLAIN で確認）

```
Limit → Sort (c.created_at DESC, c.id DESC) → HashAggregate
  → Bitmap Index Scan on contracts_company_id_created_at_idx   ← #103 で張った索引
  → Index Scan using work_reports_contract_week_desc_idx        ← #105 で張った索引
```

**#103 と #105 で張った索引が両方使われている**。特に `contracts_company_id_created_at_idx` は「当事者ごとに1本ずつ」張ったもので、企業側のクエリで期待どおり効いている。

### ✅ベストプラクティス

- **同じ問題には同じ解法を使う**（新しい書き方を試さない）
- 既出のパターンには**参照先をコメントに書く**
- **一覧と詳細は同じ形で返す**（画面側に分岐を持たせない）
- **他のIssueが進んで古くなったコメント**を見直す

### ⚠️アンチパターン

- 同じ問題に毎回違う書き方をする（読む側の学習コストが増える）
- サーバー側の都合だけで形を決める（画面側のコストが見えていない）
- **古くなったコメントを放置する**

### 理解度チェック

- [ ] 契約一覧で LEFT JOIN が特に重要な理由を言える（成立直後の契約は？）
- [ ] 構造体の埋め込みで JSON がネストしない理由を言える
- [ ] 1件取得なのに集約する判断の根拠を言える
- [ ] 古くなったコメントを放置する害を言える

## Phase3 #119: レビューの同時公開 — データ設計そのものが機能になる

### 何をした

`reviews` テーブルと、**両者が提出するまで非公開・揃った瞬間に同時公開**する仕組みを実装した。

### なぜ同時公開か

提出したら即公開する方式だと、**後から書く側が相手の評価を見られる**。すると:

- 「★5をもらったからこちらも★5にしよう」（**忖度**）
- 「★2をつけられた、仕返しに★1」（**報復**）

が起きて、評価が実態を表さなくなる。両者が提出するまで互いに見えなければ、正直な評価が集まる（Airbnb 方式）。

### 2つの時刻が機能そのもの

```sql
submitted_at TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 提出した時刻
published_at TIMESTAMPTZ,                          -- 公開された時刻（NULL = 未公開）
```

素直に設計すると `created_at` ひとつになるが、それだと「**提出された ＝ 公開された**」になる。
**分けることで「提出されているが公開されていない」という状態が生まれ、それがこの機能の全部**。

複雑なロジックも公開フラグも要らない。**`published_at IS NULL` かどうか**——これだけ。

**フラグ（`is_published`）ではなく時刻で持つ**利点:

- 公開の**事実と時期**が1列で記録できる
- `published_at IS NOT NULL` が SELECT でそのまま使える

### 同時公開の実装（トランザクション）

```go
tx, _ := db.Begin()
defer func() { _ = tx.Rollback() }()

INSERT INTO reviews ...                              // ① 自分の分を入れる
SELECT count(*) FROM reviews WHERE contract_id = $1  // ② 数える（自分を含む）
if count == 2 {
    UPDATE reviews SET published_at = now()
    WHERE contract_id = $1 AND published_at IS NULL  // ③ 両方を同時に更新
}
tx.Commit()
```

**3つの工夫**:

1. **INSERT してから数える**——先に数えると自分が含まれず条件が `count == 1` になって分かりにくい。「入れてから2件なら揃った」のほうが素直
2. **1つの UPDATE で両方を更新**——`WHERE published_at IS NULL` が両方の行にマッチするため、**片方だけ公開される状態が構造的に作れない**
3. **トランザクション**——判定と更新を分けると、2人がほぼ同時に提出したとき **両方とも「相手はまだ」と判断して、2件あるのに永久に非公開**になる（TOCTOU）

### 「見えない」は SELECT で実現する

```sql
WHERE contract_id = $1
  AND (published_at IS NOT NULL OR reviewer_role = $2)
```

| 条件                       | 意味                                      |
| -------------------------- | ----------------------------------------- |
| `published_at IS NOT NULL` | 公開済み → 誰でも見られる                 |
| `OR reviewer_role = $2`    | **自分が書いたもの** → 公開前でも見られる |

**画面で隠すのではなく、そもそも取得しない。**返してしまうと、表示していなくてもAPIの直接呼び出しで読めてしまい、同時公開の意味が失われる（#117 の原則と同じ）。

**レスポンス型に「公開されているか」のフラグを持たない**——取得された時点で「自分のもの」か「公開済み」だと確定しているため、画面が判断する必要がない。

### 一覧には2つのフラグを返す

配列の中身だけでは、**空配列が「相手が未提出」なのか「自分も未提出」なのか区別できない**。

```go
Published bool  // 双方のレビューが公開されたか
Submitted bool  // 自分がすでに提出したか
```

画面はこの2つで3状態を出し分ける（投稿フォーム / 相手待ち / 双方表示）。

### その他の判断

- **完了した契約にだけ投稿できる**。稼働中や検収待ちで評価を書けると「悪い評価をつけられたくないから検収を通す」という圧力が生まれ、**検収の中立性が失われる**
- **編集・削除は実装しない**。提出後に編集できると、公開後に内容を書き換えられる（相手の評価を見てから自分のを直す）ため
- **公開期限を設けない**。Airbnbは14日で自動公開するが、期限があると「時間が経てば片方だけ公開される」ことになり、**相手が書かないと分かっていれば安心して悪い評価を書ける**——報復防止の意味が薄れる
- **評価は総合1軸のみ**。複数軸は入力の手間が増えて提出率が下がる。**両者提出が公開条件である以上、提出率は機能が成立するかどうかを決める**（制約が設計を決めた例）
- **評価対象を列に持たない**。契約の当事者は2人なので、「書いた側」が分かれば「書かれた側」は自動的に決まる（#116 の `sender_role` と同じ判断）

### SQLの条件をテストで固定する

```go
const requiredCondition = "published_at IS NOT NULL OR reviewer_role = $2"
if !strings.Contains(reviewSelectSQL, requiredCondition) { t.Errorf(...) }
```

SQL文字列の検査という通常はやらない形だが:

- この条件が消えると**機能が根本から壊れる**（相手のレビューが公開前に読める）
- しかも**動作は正常に見える**（エラーにならない）
- DBを使うテストが無い現状では他に検出手段がない

**#117 のリフレクション検査と同じ発想**——完璧ではないが「消したら気づく」仕組みを置く。

### ✅ベストプラクティス

- **状態はフラグではなく時刻で持つ**（事実と時期を同時に記録できる）
- 「同時」は**トランザクションで保証**する
- 見せないものは**取得しない**（画面で隠さない）
- 機能の核心となる条件は、**素朴な方法でもテストで守る**

### ⚠️アンチパターン

- `created_at` ひとつで「提出＝公開」にする
- 判定してから更新する（TOCTOU で「どちらも公開されない」）
- 取得してから画面で隠す（APIを直接叩けば読める）
- 良かれと思って評価軸を増やす（**提出率が下がって機能が成立しない**）

### 理解度チェック

- [ ] `submitted_at` と `published_at` を分けると何が可能になるか言える
- [ ] トランザクション無しだと2人同時提出で何が起きるか言える
- [ ] 1つの UPDATE で両方を更新する理由を言える
- [ ] 評価軸を1つにした理由（何が死活問題か）を言える

## Phase 0 #7: sqlc — SQL を書いて Go を生成する（repository 層を作らない）

### 何をした

`queries/*.sql` に名前付きクエリ（`-- name: CreateProject :one`）を書き、sqlc で pgx/v5 用の型付き Go コード（`generated/db/`）を生成。schema は `migrations/ddl/` を参照させる。

### 概念

- **SQL が一次情報**: ORM のように「Go から SQL を組み立てる」のでなく「書いた SQL から Go を生成する」。実行される SQL が目で見える・EXPLAIN もそのまま使える
- **repository 層を作らない**: 生成された `Queries` が repository 相当。薄皮ラップ（`func (r *Repo) Create(...)` が `q.CreateProject(...)` を呼ぶだけ）は行数だけ増えて何も守らない
- **`:one` / `:many`**: 戻り値の形をアノテーションで指定。RETURNING が全列と一致すればモデル（`db.Project`）が再利用され、ズレると `CreateProjectRow` 型が生えてしまう（列を揃えるシグナルになる）

### ✅ベストプラクティス

- `SELECT *` 禁止・列を明示（列追加で生成型が黙って変わるのを防ぐ）

### ⚠️アンチパターン

- Queries の薄皮ラップ層を「クリーンアーキだから」と機械的に作る

### 理解度チェック

- [ ] sqlc と ORM の「一次情報の向き」の違いを言える
- [ ] repository 層を作らない判断の根拠を言える

## Phase 3 #42: 条件付き UPDATE と sqlc の名前付きパラメータ

### 何をした

状態遷移を `UPDATE ... SET status = @to_status WHERE id = @id AND company_id = @company_id AND status = @from_status` の1文にした。

### 概念

- **競合窓の除去**: 「読んで判定して書く」の間に他リクエストが割り込む窓を、WHERE に前提条件を埋め込むことで消す。DB の行ロックが原子性を保証し、0行更新＝競合または不存在
- **`@名前` 記法**: status が2回登場すると位置パラメータ（$1, $2）では `Status` / `Status_2` という曖昧な生成名になる → 名前付きにして `FromStatus` / `ToStatus` に

### ✅ベストプラクティス

- 同じ列が条件と更新値の両方に出るクエリは必ず名前付きパラメータにする

### ⚠️アンチパターン

- トランザクションで SELECT FOR UPDATE してから判定（1文で書けるものをロックで複雑化）

### 理解度チェック

- [ ] 0行更新が意味する2つの可能性と、その後の分岐を言える

## Phase 3 #43: seek ページネーションの SQL（narg・@>・索引）

### 何をした

公開案件一覧を SQL 1本で動的検索: `(sqlc.narg('x') IS NULL OR 条件)` パターンで cursor / skills / remote_ok / min_hourly_rate を任意条件に。`(status, id DESC)` 複合索引と `required_skills` の GIN 索引を追加。

### 概念

- **`sqlc.narg`**: NULL 許容パラメータ。`IS NULL OR ...` と組むと「未指定なら条件ごと無効」になり、条件の組み合わせごとに SQL を量産しなくて済む
- **`@>`（配列の包含）**: `required_skills @> ARRAY['Go','PostgreSQL']` は「左が右を全部含む」＝スキル AND 検索。GIN 索引が効く
- **seek の SQL**: `WHERE status='published' AND id <= cursor ORDER BY id DESC LIMIT n+1`。`(status, id DESC)` 複合索引で「published を id 降順に」が索引順そのまま＝深いページでも一定コスト
- **プランナは正直**: データが数件だと索引があっても Seq Scan が選ばれる（少量は全走査が速いという正しい判断）。EXPLAIN の答え合わせはある程度の行数で

### ✅ベストプラクティス

- ORDER BY と WHERE を1つの複合索引でカバーできる形にクエリを設計する

### ⚠️アンチパターン

- 検索条件の組み合わせごとに SQL を分岐生成（テスト対象が爆発する）

### 理解度チェック

- [ ] narg の「NULL＝条件無効」の仕組みを SQL の評価順で言える
- [ ] `@>` が AND 検索になる理由と、OR にしたければどうするか（`&&`）を言える
- [ ] `(status, id DESC)` の列順の意味を言える

## P-1 #114: 負荷デモデータ生成（UNNEST バッチ・決定的乱数）

### 何をした

計測用デモデータ生成コマンド（cmd/perfseed）。11.1万行を**1.2秒**で投入・再投入で checksum 完全一致。

### 概念

- **UNNEST バッチ INSERT**: 列ごとの配列を渡し `SELECT ... FROM unnest($1::bigint[], $2::text[], ...)` で1文=1,000行。1行ずつの INSERT はネットワーク往復×行数で、10万行なら数分〜。バッチ化で往復を1/1000にする（COPY プロトコルはさらに速いが、GENERATED ALWAYS の id 明示と併用しづらく、この規模は UNNEST で十分）
- **決定的乱数が計測の前提**: seed 固定の rand → 同じデータ。「昨日と今日で結果が違うのはデータのせいか改善のせいか」を排除する。checksum（md5(string_agg ... ORDER BY id)）で同一性を機械確認
- **分布を現実に寄せる**: スキルに頻度差（TS 3.6万 vs Rust 4千）・NULL 4割・時間は過去1年分散。一様乱数のデータはインデックスの選択率・統計を歪め、本番と違う実行計画になる
- **id 帯域の分離（>= 100万）**: 既存開発データと共存し、削除が「WHERE id >= 100万」だけで安全。シーケンスは前方バンプして以後の採番と衝突させない
- **配列列のバッチ渡し**: text[][] は unnest と相性が悪い → '|' 連結で渡して SQL 側 string_to_array。NULL は -1 センチネル + NULLIF
- **デモデータと fixture の線引き**: 状態は直接 INSERT（遷移表経由にしない）。目的が読み取り計測で遷移の正しさは対象外・30万件を usecase 経由にすると実用にならない。「同じデータ作りでも目的で作法が変わる」

### ⚠️アンチパターン

- ループで1行ずつ INSERT（規模が3桁違う遅さ）／毎回 bcrypt 計算（1万件で数分・固定ハッシュで回避）
- テスト系 DB への誤投入（perfseed は _test/_e2e を拒否するガード付き）

### 理解度チェック

- [ ] UNNEST バッチが速い理由（何を1/1000にしたか）を言える
- [ ] 決定的乱数が無いと計測の何が壊れるか言える
- [ ] 一様分布のデータが計測を歪める理由を言える
