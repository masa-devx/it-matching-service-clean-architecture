## 計測ランブック（P-2・#115）

```
# DB 層: コンテナ内 psql で EXPLAIN (ANALYZE, BUFFERS) を実行
docker exec tsunagu-arch-db psql -U tsunagu -d tsunagu -c "EXPLAIN (ANALYZE, BUFFERS) <SQL>;"
# 規模変更: make seed-perf-clean → go run ./cmd/perfseed -yes -projects 1000000（決定的なので何度でも同じ世界）
# 統計更新: 大量投入直後は ANALYZE projects; を実行してから測る
```

読み方の要点: **Rows Removed by Filter = 読んで捨てた行数（無駄の量）**・Seq Scan = 全行読み・
Buffers read = ディスクから読んだページ数・cost（見積もり）と actual（実測）のズレはプランナの誤算。

## 改善前の計測（DB 層・2026-08-22）

同一クエリを 10万件 / 100万件の両規模で計測（seed 決定的・ANALYZE 済み）:

| クエリ | 10万件 | 100万件 | 実行計画の要点 |
| --- | --- | --- | --- |
| 公開一覧 1ページ目 | 0.06ms | **0.04ms** | (status,id) 複合索引 + LIMIT 早期打ち切り。**規模に依存しない** |
| 深い cursor（seek） | 0.11ms | — | id 座標へ直接ジャンプ。seek の設計どおり |
| skills=Rust（希少単体） | 0.26ms | 0.13ms | ヒット密度が高く早期打ち切りが効く |
| skills=Rust,Terraform（中間帯） | 1.7ms / 5,257行捨て | 2.5ms / 9,854行捨て | プランナが GIN でなく逆順スキャンを選ぶ「狭間」。規模比例で悪化するが軽微 |
| skills 3種（激レア・20件） | 0.63ms | — | **GIN Bitmap Scan に切替**。両極端はプランナが正しく捌く |
| 時給 >= 7800（少数ヒット） | 0.21ms | 0.23ms | ぎりぎりヒットがあるうちは早期打ち切りで救われる |
| **時給 >= 8000（該当0件）** | — | **30.4ms・100万行全読み** | **Parallel Seq Scan。hourly_rate_min に索引が無い**ため全走査でしか「無い」を証明できない。Buffers read 16,187 |
| 自社の案件一覧（1社1,000件） | 1.2ms | 5.2ms | FK 索引で取得後に **Sort**。複合 (company_id, id DESC) なら Sort 不要（軽微） |
| 応募一覧（talent/company 視点） | 0.8ms / ✓ | — | talent_id 索引・UNIQUE(project_id,talent_id) 前置が機能 |

### 結論（P-3 の対象決定）

1. **本命: `hourly_rate_min` の索引欠落**。「該当が少ない/無い」時給検索が全走査（30ms・CPU 3並列・大量ディスク読み）。
   LIMIT の早期打ち切りは「見つかるまで読む」なので、**見つからない時が最悪になる**——ヒットありのベンチだけ見ると隠れる罠。
   打ち手候補: 部分索引 `(hourly_rate_min) WHERE status='published'`（検索対象は公開のみ・NULL 4割を含めない分小さい）
2. 次点: 自社一覧の Sort 除去（複合 (company_id, id DESC)）。5ms 規模で低優先
3. 受忍: skills 中間帯（2.5ms）。GIN と逆順スキャンの狭間だが実害小・対処は複雑
4. **健全性の確認も成果**: 素の一覧・seek・GIN・FK 索引は 100万件でもサブ ms〜数 ms。
   Phase 3〜4 で規約（FK 索引・複合索引・GIN）どおり張った投資が効いている

> 教訓: 計測前の「pkey しか無いのでは」という思い込みは**私（作者側）の索引一覧の取り方ミス**で、実際は張られていた。
> 「計測が思い込みを正す」の実例が計測者自身に起きた。

## 改善前の計測（HTTP 層・2026-08-22・100万件世界）

`make perf-measure`（300リクエスト × 並列10・本物のログイン済みトークン・`make dev-api` のローカル実行）:

| エンドポイント | p50 | p99 | 対 DB 単発比 |
| --- | --- | --- | --- |
| 素の公開一覧（1ページ目） | 1.2ms | 53ms | DB 0.04ms + HTTP/認証等のオーバーヘッド |
| skills 中間帯（Rust,Terraform） | 3.0ms | 45ms | DB 2.5ms とほぼ一致（SQL が支配的） |
| **時給 >= 8000（該当0件・本命）** | **117ms** | **245ms** | **DB 単発 30ms の約4〜8倍。全リクエストが100万行走査×並列で CPU を奪い合い、負荷に比例して悪化** |
| 時給 >= 5000（ヒットあり・対照群） | 2.9ms | 30ms | **同じエンドポイントがパラメータ次第で p50 40倍差** |
| 自分の応募一覧 | 1.5ms | 43ms | 健全 |

### P-2 の最終結論

- **改善対象は `hourly_rate_min` の索引欠落で確定**（P-3 へ）。DB 層 30ms の問題は、負荷下では **p50 117ms のユーザー体感問題**に化ける——「p99 の問題は放っておくと p50 の問題になる」の実測例
- 対照群（ヒットあり 2.9ms）が揃ったことで、P-3 の Before/After は「同一エンドポイント・同一計測・パラメータ違い」の完全な比較になる
- 打ち手（再掲）: 部分索引 `CREATE INDEX ... ON projects (hourly_rate_min) WHERE status = 'published'`

## 改善の記録（P-3・#116・2026-08-26）

P-2 が決めた対象 `hourly_rate_min` に部分索引を追加し、**P-2 と同一の世界（100万件・seed 決定的）・同一のコマンド**で Before/After を取った。
Before は索引の migration を `make migrate-down` で外して再計測（P-2 の数字と一致することを確認済み）。

```sql
-- migrations/ddl/20260825112030-add_projects_hourly_rate_index.sql
CREATE INDEX idx_projects_published_hourly_rate_min
    ON projects (hourly_rate_min)
    WHERE status = 'published' AND hourly_rate_min IS NOT NULL;
```

| クエリ | Before | After | 実行計画の変化 |
| --- | --- | --- | --- |
| **時給 >= 8000（該当0件・本命）** | **32.4ms**・Parallel Seq Scan・Removed 333,349×3・read 11,214 | **0.02ms**・Index Scan・hit 6 | 100万行を3並列で全読みして「無い」を証明 → 索引の範囲の端を1回見て「無い」が分かる。**約1,600倍** |

### 書き込み税（INSERT 1万行を EXPLAIN ANALYZE・ROLLBACK で世界は汚さない・3回の後半2回）

| | Before | After | 差 |
| --- | --- | --- | --- |
| INSERT 10,000 行 | 約 53ms | 約 62ms | **+9ms（約 +17%）** |

索引1本ぶんの税金は 1万行あたり 9ms。この案件テーブルは「読み 100 : 書き 1」以下の比率（掲載は稀・検索は常時）なので、読み側 32ms → 0.02ms に対して十分に安い。
ただし**部分索引にしたことが税を抑えている**点は重要: draft のまま保存される行・時給未設定の行は索引を一切触らない。

### プランキャッシュの検証（実装前に懸念した罠・結果は「出なかった」）

検索 SQL は `($4 IS NULL OR hourly_rate_min >= $4)` の narg 形で、pgx はプリペアドステートメントで実行する（generic plan に切り替わる可能性がある）。
同じ SQL を `PREPARE` して両モードを強制した結果:

| plan_cache_mode | 実行計画 | 実行時間 |
| --- | --- | --- |
| force_custom_plan（パラメータを見る） | Index Scan（新索引） | 0.05ms |
| **force_generic_plan（見ない）** | **Parallel Index Scan Backward（pkey）＋全行 Filter** | **155ms（Seq Scan より遅い）** |

generic plan では `$4 IS NULL OR ...` を畳めず、新索引を使えない。**HTTP 計測 300 リクエストが p50 1.4ms のまま**だったことが、既定の auto モードで PostgreSQL が custom plan を選び続けた証拠（generic の見積もりコスト 7,810 ≫ custom 8.44 なので切り替わらない）。
→ 現状は安全だが「プランナのコスト比較に守られている」状態。統計の変化で見積もりが逆転すれば発火しうるので、再発時の打ち手は `plan_cache_mode = force_custom_plan`（接続設定）または narg をやめた SQL の分岐。今は計測が問題なしと言っているので手を入れない。

### 見送った候補（計測に従う）

- 自社一覧の `(company_id, id DESC)` 複合索引: P-2 で 5.2ms（1社1,000件・Sort 込み）。ユーザー体感に届かない規模で、索引1本の税を払う根拠が無い。**「計測が 5ms と言っているものに索引を足さない」も計測駆動の判断**
- skills 中間帯（2.5ms）: 受忍（P-2 の結論どおり）

### 運用の教訓

- **`make migrate-down` は「適用履歴の末尾1件」を戻す**。Before 計測のために down したところ、二重に実行して1つ前（offer_message）まで巻き戻した。**down の前に `migrate-status` で末尾が何かを見る**・複数人（人と AI 含む）で同じ DB を触るときは、誰が down するか決める
- cold と warm を混ぜない: 同じ Seq Scan でも初回は 133ms（read 11,946）・2回目は 32ms。Buffers の read を見て条件を揃えてから比べる

### 本番適用

マージ後の CD（cloudbuild → migrate Job）で Neon に適用。本番 DB にはデモデータが無いため Before/After の差は本番では出ない。確認するのは「索引が本番に存在すること」（Job ログの applied=1）まで。
