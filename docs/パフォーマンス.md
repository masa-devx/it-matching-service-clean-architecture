```
# DB 層: コンテナ内 psql で EXPLAIN (ANALYZE, BUFFERS) を実行

# 統計更新: 大量投入直後は ANALYZE projects; を実行してから測る
```

読み方の要点: **Rows Removed by Filter = 読んで捨てた行数（無駄の量）**・Seq Scan = 全行読み・
Buffers read = ディスクから読んだページ数・cost（見積もり）と actual（実測）のズレはプランナの誤算。

## 改善前の計測（DB 層・2026-08-22）

同一クエリを 10万件 / 100万件の両規模で計測（seed 決定的・ANALYZE 済み）:

| クエリ | 10万件 | 100万件 | 実行計画の要点 |
| --- | --- | --- | --- |
| 公開一覧 1ページ目 | 0.06ms | **0.04ms** | (status,id) 複合索引 + LIMIT 早期打ち切り。**規模に依存しない** |
| 深い cursor（seek） | 0.11ms | — | id 座標へ直接ジャンプ。seek の設計どおり |
| skills=Rust（希少単体） | 0.26ms | 0.13ms | ヒット密度が高く早期打ち切りが効く |
| skills=Rust,Terraform（中間帯） | 1.7ms / 5,257行捨て | 2.5ms / 9,854行捨て | プランナが GIN でなく逆順スキャンを選ぶ「狭間」。規模比例で悪化するが軽微 |
| skills 3種（激レア・20件） | 0.63ms | — | **GIN Bitmap Scan に切替**。両極端はプランナが正しく捌く |
| 時給 >= 7800（少数ヒット） | 0.21ms | 0.23ms | ぎりぎりヒットがあるうちは早期打ち切りで救われる |
| **時給 >= 8000（該当0件）** | — | **30.4ms・100万行全読み** | **Parallel Seq Scan。hourly_rate_min に索引が無い**ため全走査でしか「無い」を証明できない。Buffers read 16,187 |
| 自社の案件一覧（1社1,000件） | 1.2ms | 5.2ms | FK 索引で取得後に **Sort**。複合 (company_id, id DESC) なら Sort 不要（軽微） |
| 応募一覧（talent/company 視点） | 0.8ms / ✓ | — | talent_id 索引・UNIQUE(project_id,talent_id) 前置が機能 |

### 結論（P-3 の対象決定）

1. **本命: `hourly_rate_min` の索引欠落**。「該当が少ない/無い」時給検索が全走査（30ms・CPU 3並列・大量ディスク読み）。
   LIMIT の早期打ち切りは「見つかるまで読む」なので、**見つからない時が最悪になる**——ヒットありのベンチだけ見ると隠れる罠。
   打ち手候補: 部分索引 `(hourly_rate_min) WHERE status='published'`（検索対象は公開のみ・NULL 4割を含めない分小さい）
2. 次点: 自社一覧の Sort 除去（複合 (company_id, id DESC)）。5ms 規模で低優先
3. 受忍: skills 中間帯（2.5ms）。GIN と逆順スキャンの狭間だが実害小・対処は複雑
4. **健全性の確認も成果**: 素の一覧・seek・GIN・FK 索引は 100万件でもサブ ms〜数 ms。
   Phase 3〜4 で規約（FK 索引・複合索引・GIN）どおり張った投資が効いている

> 教訓: 計測前の「pkey しか無いのでは」という思い込みは**私（作者側）の索引一覧の取り方ミス**で、実際は張られていた。
> 「計測が思い込みを正す」の実例が計測者自身に起きた。
