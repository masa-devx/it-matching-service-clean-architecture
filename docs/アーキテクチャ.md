# Tsunagu Works アーキテクチャ設計書

企業 × IT人材（副業・フリーランスエンジニア）のビジネスマッチングサービス。
本ドキュメントはシステム構成・ディレクトリ設計・各層の責務・データフローを定義する。

---

## 1. システム全体図

```
ブラウザ ── Next.js (App Router / :3000) ── Go API (net/http / :8081) ── PostgreSQL (:5434)
```

| 領域 | 技術 | 役割 |
| --- | --- | --- |
| フロントエンド | Next.js App Router + TypeScript | 画面・ルーティング・サーバーサイドレンダリング |
| バックエンド | Go（net/http） | ビジネスロジック・認証認可・永続化 |
| DB | PostgreSQL 16（Docker） | データ永続化 |
| 認証 | 自前JWT（bcrypt + HS256） | トークンは httpOnly Cookie で保持 |

---

## 2. 設計原則

1. **責務の分離**: ルーティング・UI・ロジック・I/O を混在させない。各ファイル/ディレクトリは単一の役割を持つ
2. **I/Oの集約**: フロントエンドの API 呼び出しは `web/src/lib/` に集約し、コンポーネント・フックには fetch を書かない。バックエンドの共通処理（レスポンス整形・認証）はヘルパー/ミドルウェアに集約する
3. **Server / Client の境界を明確に**: 既定は Server Component とし、`"use client"` は対話が必要な末端コンポーネントに限定する。サーバー専用モジュール（`next/headers` 等）はクライアントから import しない
4. **トークンをクライアント JS に触れさせない**: JWT は httpOnly Cookie に保存し、サーバーサイドで読み取って Go API へ `Authorization: Bearer` として転送する
5. **認可の二重チェック**: ユーザーIDは必ず検証済みトークンから取得し（リクエスト値を信用しない）、リソースの所有チェックは SQL の `WHERE` 句で行う
6. **SQL の安全性**: プレースホルダ必須（文字列連結禁止）・`SELECT *` 禁止（列を明示）
7. **状態遷移の一元管理**: ステータスを持つドメイン（応募・契約・決済）は、許可される遷移をコード上の一箇所（遷移表）に定義する

## 4. api/（Go バックエンド）

```
api/
├─ main.go              # エントリポイント。「設定読込 → DB接続 → ルート登録 → サーバ起動」の組み立てのみ
├─ config.go            # 環境変数の読み取り（必須は fail fast・任意は既定値）
├─ db.go                # DB接続（接続プールの生成・疎通確認）
├─ logger.go            # 構造化ログ（log/slog）・ステータスに応じたレベル分け
├─ response.go          # writeJSON / writeError（レスポンス整形の共通ヘルパー）
├─ middleware.go        # requestID / panic recovery / ログ / CORS / 認証 / ロール認可
├─ jwt.go               # トークンの発行・検証（HS256・署名方式の検証を必須とする）
│
├─ auth.go              # 認証（signup / login / me）
├─ profile.go           # 企業・人材のプロフィール
├─ projects.go          # 案件（掲載・検索・詳細・編集）
├─ company_projects.go  # 企業向けの案件一覧・詳細（下書き含む・応募件数の集計）
├─ applications.go      # 応募（作成・視点別の一覧・状態更新）
├─ contracts.go         # 契約（承諾時の自動生成・一覧・詳細・状態更新）
├─ work_reports.go      # 週次の稼働報告（提出・再提出・承認/差し戻し）
├─ messages.go          # メッセージ（送受信）
├─ masking.go           # 連絡先マスキング（メール・電話・URL）
├─ reviews.go           # レビュー（投稿・取得・同時公開）
│
├─ application_status.go # 状態遷移表（応募）
├─ project_status.go     # 状態遷移表（案件の掲載）
├─ contract_status.go    # 状態遷移表（契約）
├─ work_report_status.go # 状態遷移表（稼働報告）
└─ go.mod
```

**構成のルール**
- `main.go` は組み立てに徹し、ドメインロジックを持たない
- 機能はドメイン語彙のファイル単位で分割する（1ドメイン=1ファイル。太ったら `company_projects.go` のように視点で分ける）
- **状態遷移表は専用ファイルに切り出す**（`*_status.go`）。遷移の定義を1か所に集約し、テストもそこに対応させる
- ハンドラのエラー応答は共通ヘルパー経由とし、内部エラーの詳細をクライアントへ露出しない

### この構成を選んだ理由（Stage 1 で意図的に止めている）

`api/` は **handler / usecase / repository の層分けをしていない**。これは知識が無いのではなく、**意図的な判断**である。

**なぜ層を分けなかったか**

- リファクタの発動条件（CLAUDE.md の R1）は「**ハンドラが太った**」「**状態機械のテストを書きたい**」の2つ
- 状態機械のテストは**純粋関数として書けている**（遷移表を `*_status.go` に切り出したため、DBもHTTPも要らない）。層を分けなくてもテストは書けた
- ハンドラは最大で約100行。所有チェック → 遷移判定 → 更新、という**同じ形が繰り返される**ため、読む負担が小さい
- **機能を出し切ることを優先した**。MVPの完成前に層を増やすと、ドメインが固まる前の抽象化になる

**痛みが出ていない証拠**

| 発動条件 | 現状 |
| --- | --- |
| ハンドラが太った | 最大100行程度。認可の3層（認証→所有→遷移可否）で構造が揃っている |
| 状態機械のテストを書きたい | **書けている**（遷移表が純粋関数のため、5本すべてテスト済み） |
| DBを差し替えたい | 要件が無い（PostgreSQL 固定） |

**では、どこでクリーンアーキテクチャを学ぶか**

**後継リポジトリで、同じドメインを別の設計で実装する**方針を採っている（[#88](https://github.com/masahiro96848/tsunagu-works/issues/88) に記録）。

同じリポジトリでリファクタすると、**Before の姿が git 履歴の中にしか残らない**。別リポジトリなら2つを並べて見せられ、「**この規模ならフラット、この規模ならクリーンアーキ**」という判断そのものを示せる。

そこでは以下に取り組む:
- handler / usecase / repository ＋ コンストラクタDI
- **DBを使うテスト基盤**（go-txdb によるトランザクション分離・factories）
- E2E（Playwright）
- スキーマ駆動開発（TypeSpec → OpenAPI → Go/TS のコード生成）

## 5. web/（Next.js フロントエンド）

```
web/src/
├─ app/                     # ルーティング定義のみ（ビジネスロジックを持たない）
│  ├─ layout.tsx           # ルートレイアウト（html/body・グローバルCSS・Provider）
│  ├─ (auth)/              # 未認証ルートグループ
│  │  ├─ login/page.tsx
│  │  └─ signup/page.tsx
│  └─ (main)/              # 認証済みルートグループ（layout.tsx で認証ガード・共通ナビ）
│     └─ projects/
│        ├─ page.tsx       # 一覧
│        ├─ loading.tsx    # 取得中表示（Suspense fallback）
│        ├─ error.tsx      # エラー境界
│        └─ [id]/page.tsx  # 詳細（動的ルート）
├─ components/              # UI部品（フォーム・カード・ステータストラッカー等）
├─ hooks/                   # カスタムフック（mutation・ローディング/エラー状態の集約。UI非依存）
└─ lib/                     # API アクセス層（fetch の唯一の置き場）
   ├─ types.ts             # 共有型（server / client 双方から参照可能な中立モジュール）
   ├─ auth.ts              # サーバー専用: Cookie からトークン取得・Bearer 付与
   ├─ projects.ts          # 読み取り系（RSC から使用。サーバー間通信で Go API へ）
   └─ projects-client.ts   # 書き込み系（Client Component から使用。サーバー経由で Go API へ）
```

**構成のルール**
- `app/` の page は薄く保ち、表示は `components/`、ロジックは `hooks/`、通信は `lib/` に委譲する
- ルートグループで認証状態を分離する（`(auth)` = 未認証、`(main)` = 認証必須）
- `lib/` はサーバー専用とクライアント用をファイルで分離し、サーバー専用モジュールがクライアントバンドルに混入しないようにする
- ローディング/エラーは App Router の規約ファイル（`loading.tsx` / `error.tsx`）と、書き込み系はフックの error 状態で扱う

## 6. データフロー

```
【読み取り】
ブラウザ → Next.js (Server Component)
         → lib/projects.ts（Cookie からトークン読取 → Bearer 付与）
         → Go API :8081 → PostgreSQL
  ※ サーバー間通信のため CORS 不要・トークンはブラウザ JS に露出しない

【書き込み】
ブラウザ (Client Component) → サーバー経由（lib/projects-client.ts）
         → Go API（Bearer 転送）→ 成功後に該当データを再取得

【認証】
signup / login → Go API が JWT を発行 → Next.js が httpOnly Cookie にセット
未認証アクセス → (main)/layout.tsx の認証ガードで /login へリダイレクト
JWT 検証（Go 側）→ 署名方式（HS256）と有効期限を検証し、ユーザーIDを context 経由でハンドラへ
```
