# 後継リポジトリ 設計プラン（ドラフト）

> このドキュメントは**新リポジトリを作る前の設計検討**。合意できた時点で新リポジトリへ移し、
> 決定事項は ADR（`docs/adr/`）に分割して記録する。
> **「保留」と書かれた項目は着手前に決める。**

---

## 1. 目的

tsunagu-works（MVP完成済み）で**あえてやらなかったこと**に取り組む。

| tsunagu-works                        | 後継リポジトリ                                       |
| ------------------------------------ | ---------------------------------------------------- |
| フラット構成（Stage 1）              | **層を分ける**（handler / usecase / domain）         |
| 手書きの型（フロント・バックで別々） | **スキーマ駆動**（1つの仕様から生成）                |
| 1つの Next.js アプリ内でロール分岐   | **company / talent をアプリごと分ける**（Turborepo） |
| 純粋関数のテストのみ（25%）          | **DBを使うテスト**（go-txdb）＋ E2E                  |
| ローカルのみ                         | **Cloud Run にデプロイ**                             |
| Route Handler（BFF）                 | **Server Actions**                                   |
| RSC のみ                             | **TanStack Query（prefetch / Hydration）**           |
| `database/sql`（手書きSQL）          | **sqlc**（SQLを書いて型を生成）                      |
| ファイル操作なし                     | **KYC＝ファイルアップロード / Cloud Storage**        |

**同じドメインを別の設計で実装し、2つを並べて「どの規模でどちらを選ぶか」を語れる状態にする**のがゴール。

### やらないこと

- 機能の全移植（**設計を示すのが目的**であり、機能量は tsunagu-works が担う）
- エスクロー決済（決済ドメインは別の学習テーマ）

## 2. スコープ

**4ドメイン。ただし着手順が違う**（下記）。

| ドメイン                                 | 含める理由                                                                                   | 着手                |
| ---------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------- |
| **認証 ＋ プロフィール**                 | 無いと何も動かない。JWT・Cookie・ミドルウェア                                                | 前半                |
| **案件**（掲載・一覧・詳細・編集・検索） | 基本的なCRUDで層分けを示す。**seek ページネーション**                                        | 前半                |
| **応募**（応募・状態遷移・視点別一覧）   | **状態機械を層分けした構成でどう扱うか**が最大の見せ場                                       | 前半                |
| **eKYC**（ファイルアップロード）         | **ファイルアップロード・オブジェクトストレージ・機微情報の扱い**（tsunagu-works に無い領域） | **後半**（§8・§12） |

### eKYC はアーキテクチャ確立後に着手する

**理由**：

| | |
| --- | --- |
| ① | **Cloud Storage は本番環境が要る**。デプロイのパイプラインが通ってから着手するほうが、ローカル代替（fake-gcs-server）との差分を確認しやすい |
| ② | eKYC は**アーキテクチャの検証にならない**（層構成・スキーマ駆動・状態機械の見せ場は認証〜応募で出し切れる） |
| ③ | **multipart の生成品質が未知数**（§9）。土台が固まる前に不確実な要素を入れると、原因の切り分けが難しくなる |

**土台（層構成・CI・デプロイ）が動いた状態で、追加ドメインとして載せる**——
これは「**既存のアーキテクチャに新しい種類の機能を足す**」経験そのもので、実務に近い。

**含めないもの**: 契約 / 稼働報告 / メッセージ / レビュー / 案件の掲載状態
→ **同じパターンの繰り返し**で、新しく示せることが少ない。

### 規模の見込み

|                | 見込み                                                                  |
| -------------- | ----------------------------------------------------------------------- |
| テーブル       | 5（users / companies / talents / projects / applications）              |
| エンドポイント | 18〜22（company / talent の2系統に分かれるため tsunagu-works より多め） |
| 画面           | 12前後（2アプリ合計）                                                   |

## 3. 技術選定

### 決定済み

| 領域             | 選択                                                   | 理由                                                                          |
| ---------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------- |
| 言語・基盤       | Go / Next.js App Router / PostgreSQL                   | tsunagu-works と同じ（**設計の違いだけを比較したい**ため変えない）            |
| **モノレポ**     | **Turborepo ＋ pnpm workspace**                        | **Go を含めてタスクグラフに載せる**（仕様変更 → 生成 → ビルドの連鎖を自動化） |
| **アプリ分割**   | **company / talent の2アプリ**（フロント・バック両方） | **ロール分岐がアプリ境界になる**（§7）                                        |
| **DBアクセス**   | **sqlc**                                               | 書いたSQLがそのまま残る。**既存SQLを流用でき、SQL力を保ったまま型安全**になる |
| **API仕様**      | **TypeSpec → OpenAPI**                                 | 共通モデルを `import` で再利用できる（company / talent の2 spec で効く）      |
| **Go生成**       | **oapi-codegen**（StrictHandler）                      | ルーティングを書かない。**仕様と実装のズレがコンパイルエラー**になる          |
| **TS生成**       | **orval**                                              | 型 ＋ Fetch Client ＋ Zod を生成（※Zodの扱いは §9 で要検証）                  |
| **書き込み**     | **Server Actions**                                     | tsunagu-works で Route Handler を書いたので、**比較して語れる**               |
| **サーバー状態** | **TanStack Query**（prefetch / Hydration）             | RSCで温めたキャッシュをクライアントが引き継ぐ                                 |
| **ファイル保管** | **Cloud Storage**（ローカルは **fake-gcs-server**）    | KYC書類。**非公開バケット＋署名付きURL**                                      |
| DBテスト         | **go-txdb ＋ factories**                               | テストごとにトランザクション分離。**モックを作らない**                        |
| E2E              | ~~Playwright~~ → **API 統合テスト**（[ADR-0012](adr/0012-api-integration-tests-over-browser-e2e.md)） | 実MW込みの httptest で通しを固定。ブラウザ E2E は見送り（発動条件は ADR）     |
| デプロイ         | **Cloud Run ＋ Neon**（無料枠）                        | Cloud SQL は個人開発には過剰（月3,000円）                                     |
| マイグレーション | **`cmd/migrate` ＋ Cloud Run Job**                     | API起動時に流すと**複数インスタンスが同時に流す**                             |
| 境界の強制       | **ESLint（依存方向）＋ golangci-lint の depguard**     | 設計を人の注意力ではなく仕組みで守る                                          |
| 観測             | 構造化ログ ＋ **OpenTelemetry**                        | リクエストIDを Next → Go → DB まで貫通させる                                  |
| コンテナ         | **マルチステージビルド**（distroless）                 | イメージサイズがコールドスタートに直結                                        |

### DB は PostgreSQL のままにする（判断の記録 → [ADR-0001](adr/0001-keep-postgresql.md)）

TiDB Serverless（MySQL互換）も検討したが、**tsunagu-works の SQL 資産が使えなくなる**ため見送る。

| PostgreSQL 固有機能             | tsunagu-works での使用箇所 |
| ------------------------------- | -------------------------- |
| `RETURNING`                     | **13箇所**                 |
| `TEXT[]`（配列型）              | 2テーブル                  |
| GIN 索引                        | 2箇所                      |
| `count(...) FILTER (WHERE ...)` | 4箇所                      |
| `@>`（配列の包含）              | 2箇所                      |
| `date_trunc`                    | 2箇所                      |

**全て書き直しになる。**「MySQL も経験する」ことより、**SQLを資産として持ち越す**ほうを取る。

### 保留（着手前に決める）

| 項目                   | 選択肢                                            | 備考                                 |
| ---------------------- | ------------------------------------------------- | ------------------------------------ |
| リポジトリ名           | —                                                 | 未定                                 |
| **フォームZodの扱い**  | 生成物を加工 / 手書き＋型で縛る                   | **§9・Phase 0 で実験してから決める** |
| **ランタイム検証**     | する / しない                                     | **§9 参照。しない方向で検討中**      |

## 4. ディレクトリ構成

> ⚠️ **2026-08-10 [ADR-0006](adr/0006-single-frontend-after-only.md) による変更**: フロントは `apps/company`・`apps/talent` の2アプリではなく **`web/` 1アプリ**（ロール分岐はルートグループ）とし、`apps/` 階層は廃止（`api-server/` `web/` をルート直下に配置）。`packages/ui` は作らない。本節のフロント2アプリ構成・デプロイ図の「Cloud Run×2フロント」は読み替えること。**バックエンドの視点→層分割と認可設計は変更なし**。

### 全体（Turborepo）

```
<repo>/
├─ apps/
│  ├─ api-server/              # Go（Turborepo のタスクとして実行）
│  ├─ company/                 # Next.js — 企業向け
│  └─ talent/                  # Next.js — 人材向け
├─ packages/
│  ├─ spec/                    # ★ TypeSpec（両者の契約）
│  ├─ api-client/              #   orval 生成物（company / talent）
│  ├─ ui/                      #   デザインシステム（2アプリで共有）
│  ├─ eslint-config/
│  ├─ typescript-config/
│  └─ playwright-config/
├─ migrations/ddl/             # sql-migrate の SQL
├─ docs/adr/
├─ turbo.json
├─ pnpm-workspace.yaml
└─ .github/workflows/
```

**`packages/spec` をパッケージにする**のは、**Turborepo のタスク依存に組み込む**ため（§6）。
「どちらのものでもない契約」であることは、`apps/` の外にあることで示される。

### バックエンド

```
apps/api-server/
├─ cmd/
│  ├─ server/main.go           # 起動と DI（依存の組み立てはここだけ）
│  └─ migrate/main.go          # ★ マイグレーション（Cloud Run Job で実行）
├─ internal/
│  ├─ company/                 # ★ 企業向け
│  │  ├─ handler/              #   HTTP境界（生成IFの実装）
│  │  ├─ usecase/              #   業務ロジック・トランザクション境界
│  │  └─ validator/            #   入力検証
│  ├─ talent/                  # ★ 人材向け（同構成）
│  │  ├─ handler/
│  │  ├─ usecase/
│  │  └─ validator/
│  └─ shared/                  # ★ 両者が使うもの
│     ├─ domain/               #   状態遷移表・不変条件（DBにもHTTPにも依存しない）
│     ├─ auth/                 #   JWT・認証/認可ミドルウェア・context
│     ├─ storage/              #   Cloud Storage（KYC）
│     ├─ apierr/               #   エラー型
│     └─ infra/                #   DB接続・ロガー・トレース
├─ generated/                        # ★ 生成物（DO NOT EDIT）
│  ├─ api/company/             #   oapi-codegen
│  ├─ api/talent/
│  └─ db/                      #   sqlc（company / talent 共通）
├─ queries/                    # sqlc に渡す SQL（共通）
├─ test/
│  ├─ factories/               # テストデータ生成
│  └─ helpers/                 # txdb のセットアップ
├─ package.json                # turbo から叩くためのタスク定義
└─ Dockerfile
```

#### なぜ「層 → ドメイン」ではなく「視点 → 層」なのか（→ [ADR-0003](adr/0003-viewpoint-first-directories.md)）

```
❌ 層が先                    ✅ 視点が先（採用）
handler/                     company/
├─ company_project.go        ├─ handler/
└─ talent_project.go         ├─ usecase/
usecase/                     └─ validator/
├─ company_project.go        talent/
└─ talent_project.go         ├─ handler/
                             └─ usecase/
```

**理由は3つ**：

1. **デプロイ単位で割れる形になる**。将来 `cmd/company-server` / `cmd/talent-server` に分けたくなったとき、**ディレクトリを移動せずに済む**
2. **フロントと境界の切り方が揃う**（`apps/company` ↔ `internal/company`）
3. **認可がパスのプレフィックスで一律に決まる**（§7）

> 割り方には「**フェーズ**で割る」（登録 / 業務）という選択肢もあるが、
> 本サービスは**企業と人材で見える世界がそもそも違う**ため、**視点**で割るほうが境界が安定する。

#### 重複しないことの確認

「同じテーブルを両者が触るから重複するのでは」への回答。**スコープ内では自然に分かれる**。

| リソース       | company 側                   | talent 側                  | 重複                      |
| -------------- | ---------------------------- | -------------------------- | ------------------------- |
| サインアップ   | 会社名・所在地・事業内容     | 氏名・スキル・**KYC書類**  | ❌ 入力が違う             |
| プロフィール   | `companies`                  | `talents`                  | ❌ 別テーブル             |
| 案件           | **作る・編集**（下書き含む） | **探す・見る**（公開のみ） | ❌ クエリが違う           |
| 応募           | **受け取る・選考する**       | **出す・取り下げる**       | ❌ 視点が違う             |
| **状態遷移表** | 応募の遷移可否               | 応募の遷移可否             | ✅ **`shared/domain` へ** |

> ⚠️ **契約・メッセージ・レビューまで広げると話が変わる**（「同じ処理を実行者ロールだけ変えて呼ぶ」が増える）。
> そのときは `shared/usecase/` を足す判断になる。**今のスコープでは不要。**

#### 依存の向き

```
handler → usecase → generated/db（sqlc の Queries）→ DB
              ↓
        shared/domain          ← domain は何にも依存しない
```

- `golangci-lint` の `depguard` で「`shared/domain` から `infra` / `gen` を import 禁止」を強制
- **`internal/company` から `internal/talent` を import 禁止**（同上）

#### repository 層は作らない（前案からの変更 → [ADR-0002](adr/0002-no-repository-layer.md)）

**sqlc を使うと repository はほぼ不要**になる。

| ORM の場合                                                                                       | sqlc の場合                                                                          |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| service が `db.Where(...).Find(...)` を書く<br>→ SQLが散らばる → **repository で隔離したくなる** | SQL は `queries/*.sql` に集まる<br>→ **生成された `Queries` が既に repository 相当** |

さらに **go-txdb で実DBをテストする**ため、**モック用のインターフェースも要らない**。

> ⚠️ **アンチパターン**：sqlc を使いながら repository インターフェースを自作し、`Queries` を1対1でラップする。
> **生成物の上に手書きの薄皮をかぶせるだけで、行数だけ増えて安全性は上がらない。**
> インターフェースを切るのは「**実際に差し替える必要が出たとき**」だけ。

### フロントエンド（company / talent で同一構成）

```
apps/{company|talent}/src/
├─ app/                      # ルーティングのみ（薄い）
├─ features/{domain}/
│  ├─ components/
│  │   ├─ server/            # Server Component（テンプレート・prefetch）
│  │   └─ client/            # Container / Presenter
│  ├─ hooks/                 # TanStack Query のフック
│  ├─ queries/               # クエリキー
│  ├─ actions/               # Server Actions（薄いラッパー）
│  ├─ schemas/               # ★ フォームのZod（§9で要検証）
│  └─ types/
├─ external/                 # ★ データ取得の境界
│  ├─ handler/               #   入口（Server Action から呼ぶ）
│  ├─ client/                #   Go API を叩く（server-only・Cookie転送）
│  └─ mapper/                #   DTO ↔ 画面の変換（置き場所は保留）
└─ middleware.ts             # （e2e/ は置かない: ブラウザ E2E 見送り・ADR-0012）
```

生成クライアントは **`packages/api-client/{company|talent}`**（アプリ内には置かない）。

**許可しない依存**（ESLint で強制）

- `features/` → `external/client` の直接 import（必ず `handler` 経由）
- `components/client/` → server 専用モジュール
- `features/{A}` → `features/{B}`（ドメイン間の直接依存）
- **`apps/company` → `apps/talent`**（アプリ間の直接依存。共有は `packages/` 経由のみ）

### サインアップをどちらに置くか

**各アプリが自前で持つ**（`apps/company/signup` / `apps/talent/signup`）。

|     | 理由                                                                      |
| --- | ------------------------------------------------------------------------- |
| ✅  | **入力項目が全く違う**（企業＝会社名・所在地／人材＝スキル・**KYC書類**） |
| ✅  | 登録用の3つ目のアプリを作らずに済む（Cloud Run が増えない）               |

登録専用のアプリを別に立てる構成もあり得るが、それは**両者が同じ登録画面群を共有する**場合の話。
**視点で割った本構成では、登録も視点ごとに分かれるのが自然。**

## 5. 各層の責務

### バックエンド

| 層                 | 責務                                                                     | やらないこと                            |
| ------------------ | ------------------------------------------------------------------------ | --------------------------------------- |
| **handler**        | HTTP境界。生成IFの実装・**生成型への詰め替え**・context から認証IDを取る | 業務ロジック・SQL・**ロール判定**（§7） |
| **usecase**        | 1つの操作を完結させる。**トランザクション境界**・`Queries` の呼び出し    | HTTPの知識                              |
| **shared/domain**  | 業務ルール（状態遷移・不変条件）                                         | DB・HTTP・外部サービス                  |
| **generated/db（sqlc）** | 永続化                                                                   | 業務判断                                |

**トランザクションの位置** = **usecase**。
「応募を承諾したら契約を作る」のような複数テーブルにまたがる操作は usecase が束ねる（`Queries.WithTx(tx)`）。

### フロントエンド

| 層                            | 責務                                  |
| ----------------------------- | ------------------------------------- |
| `app/`                        | ルーティング・メタデータのみ          |
| `features/components/server/` | データの prefetch ＋ Hydration の境界 |
| `features/components/client/` | Container（状態）/ Presenter（描画）  |
| `features/actions/`           | Server Actions の薄いラッパー         |
| `external/handler/`           | 入口。認証・エラー整形                |
| `external/client/`            | Go API への通信（server-only）        |

## 6. スキーマ駆動の運用

### 仕様の分割と共有

```
packages/spec/
├─ shared/models.tsp     # ★ model Project / Application / ApiError …
├─ company/main.tsp      #   import "../shared/models.tsp"  → openapi-company.yaml
└─ talent/main.tsp       #   同上                            → openapi-talent.yaml
```

```
shared/models.tsp（1箇所で定義）
   ├──→ openapi-company.yaml ──→ generated/api/company/ ＋ packages/api-client/company
   └──→ openapi-talent.yaml  ──→ generated/api/talent/  ＋ packages/api-client/talent
```

**同じ `Project` 型が Go とフロント2アプリに一斉に届く。**
これが **TypeSpec を選んだ理由の実演**になる（OpenAPI 直接手書きだと `$ref` の相対パス管理になる）。

### Turborepo のタスクグラフ

```jsonc
{
  "tasks": {
    "@repo/spec#build": {
      "inputs": ["**/*.tsp"],
      "outputs": ["openapi-*.yaml"],
    },
    "api-server#generate": {
      "dependsOn": ["@repo/spec#build"],
      "inputs": [
        "../../packages/spec/openapi-*.yaml",
        "queries/**",
        "sqlc.yaml",
      ],
      "outputs": ["generated/**"],
    },
    "@repo/api-client#build": {
      "dependsOn": ["@repo/spec#build"],
      "outputs": ["dist/**"],
    },
    "api-server#build": {
      "dependsOn": ["api-server#generate"],
      "outputs": ["bin/**"],
    },
    "company#build": {
      "dependsOn": ["@repo/api-client#build", "@repo/ui#build"],
    },
    "talent#build": {
      "dependsOn": ["@repo/api-client#build", "@repo/ui#build"],
    },
    "test": { "dependsOn": ["^build"] },
    "dev": { "cache": false, "persistent": true },
  },
}
```

| コマンド              | 起きること                                                   |
| --------------------- | ------------------------------------------------------------ |
| `turbo build`         | **.tsp → OpenAPI → Go/TS生成 → 全ビルド** が正しい順序で走る |
| `.tsp` を編集         | **依存する全部が再生成**される（手で叩き直さない）           |
| `.tsp` を触っていない | **キャッシュが効いて生成をスキップ**                         |

> **「生成し忘れ」が構造的に起きなくなる。**
> CI で「再生成して差分が出たら落とす」だけでも検出はできるが、**それは気づくのが遅い**。
> タスクグラフに載せれば、ローカルでビルドした時点で正しい生成物になっている。

`apps/api-server/package.json` は**タスクの入口だけ**（Go のコードは一切変わらない）：

```json
{
  "name": "api-server",
  "scripts": {
    "generate": "oapi-codegen -config oapi-company.yaml ... && sqlc generate",
    "build": "go build -o bin/server ./cmd/server && go build -o bin/migrate ./cmd/migrate",
    "test": "go test ./...",
    "lint": "golangci-lint run ./..."
  }
}
```

### 決めること

| 論点                   | 方針                                                             |
| ---------------------- | ---------------------------------------------------------------- |
| 生成物をコミットするか | **する**。差分でAPI変更の影響が見える                            |
| 同期の保証             | **CIで再生成し、差分が出たら落とす**                             |
| 仕様に書くもの         | パス・パラメータ・レスポンス・**認証の要否**・バリデーション制約 |
| 仕様に書かないもの     | **状態遷移のルール**（domain の責務）・表示ラベル                |

**「applied → accepted に直接飛べない」は OpenAPI では表現できない。**
仕様は「入出力の形」だけを定義し、**ルールは domain に置く**。

### エラーレスポンスの統一

```typespec
@error model ApiError {
  error: string;
  requestId?: string;
}

// フィールド別エラー（フォーム表示用）
model ValidationError {
  errors: Record<string[]>;
}
```

**フィールド別エラーを型として定義する**のが tsunagu-works からの改善点
（現状はエラーを文字列1本で返しており、フォームのフィールド単位表示ができていない）。

## 7. 認可の設計（company / talent 分割の最大の利点）

### tsunagu-works の現状

```go
func createProjectHandler(w http.ResponseWriter, r *http.Request) {
    user := userFromContext(r.Context())
    if user.Role != "company" {          // ← 全ハンドラに散らばっている
        writeError(w, 403, "企業のみ")
        return
    }
    ...
}
```

**1箇所でも書き忘れれば、人材が案件を作れてしまう。**

### 新構成

```
POST /company/projects   →  ミドルウェアが role == "company" を強制
GET  /talent/projects    →  ミドルウェアが role == "talent"  を強制
```

```go
func main() {
    db := infra.NewDB(cfg.DatabaseURL)
    queries := gendb.New(db)

    mux := http.NewServeMux()

    companyStrict := companyapi.NewStrictHandler(
        company.NewHandler(company.NewUsecases(db, queries)),
        []companyapi.StrictMiddlewareFunc{auth.Middleware(auth.RoleCompany)},
    )
    companyapi.HandlerWithOptions(companyStrict, companyapi.StdHTTPServerOptions{
        BaseURL: "/company", BaseRouter: mux,
    })

    // talent 側も同じ形
    talentapi.HandlerWithOptions(talentStrict, talentapi.StdHTTPServerOptions{
        BaseURL: "/talent", BaseRouter: mux,
    })

    http.ListenAndServe(":"+cfg.Port, mux)
}
```

**ハンドラからロール判定が消える。**書き忘れが構造的に起きない。

```
web:  apps/company/  apps/talent/     ← アクセス制御の境界
api:  /company/*     /talent/*        ← 同上
```

**フロントとバックで境界の切り方が揃う**のが、この分割の一番きれいなところ。

### 認証要否も仕様から判定する

```go
// 認証が要るかは、生成コードに埋め込まれた OpenAPI spec の security 定義から読む
// → 「どのAPIが認証必須か」の一次情報が仕様ファイルだけになる
```

tsunagu-works では `main.go` で `requireAuth(handler)` と手で包んでおり、**包み忘れれば無防備なエンドポイントができる**。
仕様から導けば、その事故が構造的に起きない。

⚠️ **実装上の注意**：`GetSwagger()` を毎リクエスト舐めると線形探索になる。
**起動時に1回だけ `map[operationID]bool` を作る**こと。

### 認可の3層は維持する

| 層           | 何を守るか           | どこで                                |
| ------------ | -------------------- | ------------------------------------- |
| ① 認証       | ログインしているか   | ミドルウェア                          |
| ② **ロール** | **企業か人材か**     | **ミドルウェア（パスで一律）** ← 新設 |
| ③ 所有       | 自分のリソースか     | **SQLの WHERE に埋め込む**            |
| ④ 遷移可否   | その状態から動けるか | `shared/domain` の遷移表              |

## 8. eKYC / ファイルアップロード（アーキテクチャ確立後に着手）

> **着手時期**: Phase 7（デプロイ・E2E まで通した後）。理由は §2 参照。
> **ここで学ぶこと**: multipart の受け取り・Cloud Storage・署名付きURL・機微情報のライフサイクル。

### スコープ

|                                           | 含める     | 理由                                                     |
| ----------------------------------------- | ---------- | -------------------------------------------------------- |
| アップロード・保存・本人による確認        | ✅         | **ファイル操作・GCS・機微情報**の学習が目的              |
| 審査フロー（未提出→審査中→承認/差し戻し） | ❌         | **また状態機械**で応募と学びが重複                       |
| 企業側の KYC                              | ❌（保留） | 法人番号・登記情報で足り、**ファイルにする必然性が薄い** |

**人材（talent）側のみ。**

### 実装方針（つまずきどころを先に潰す）

素直に書くとこうなりがちだが、**4つとも問題がある**：

```go
// ⚠️ この順序・この作りは避ける
db.Create(&talent)                              // ① DB登録
bucket.Object("talents/" + id + "/" + filename) // ② アップロード（推測可能なパス）
    .NewWriter(ctx).Write(body)                 //    サイズ・MIME 無検証
db.Save(&talent)                                // ③ パス書き戻し
```

| 問題                                                                | 対処                                                                          |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **①〜③がトランザクションでない**（②が失敗するとユーザーだけ残る）   | **先にアップロード → 成功したらDB登録**。または**アップロード状態を列で持つ** |
| **パスが推測可能**（`talents/{id}/{filename}`）                     | **UUID を混ぜる**。バケットは非公開・**署名付きURL**でのみ配信                |
| **MIME を検証していない**                                           | **中身から判定**（`http.DetectContentType`）。拡張子を信用しない              |
| **サイズ制限が無い**（全部メモリに読んでから弾く）                  | **`http.MaxBytesReader`** で読む前に打ち切る                                  |

> **DBとオブジェクトストレージはトランザクションを共有できない。**
> 「片方だけ成功した状態」が必ず起きうる前提で順序を決める——これがファイルを扱う設計の核心。

### 決めること

| 論点               | 方針                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------- |
| ローカル開発       | **fake-gcs-server**（docker compose）                                                  |
| 配信方法           | **署名付きURL**（有効期限つき）。バケットは非公開                                      |
| 保持期間           | GCS の**ライフサイクルルール**で自動削除（本人確認書類は目的達成後に消す）             |
| multipart の受け口 | **OpenAPI で定義し、デコードだけ handler で手書き**（[ADR-0013](adr/0013-multipart-schema-driven-boundary.md)・#106 で検証済み） |

> ✅ **確認済み（#106 スパイク・[ADR-0013](adr/0013-multipart-schema-driven-boundary.md)）**: TS クライアント・Zod・認証導出・レスポンス型まで生成される。
> 弱いのは strict server のリクエストデコードのみ（`*multipart.Reader` が生で渡る）。
> よって**例外は「ボディのデコードを handler で手書き」の1点に限定**した。生ストリームは MaxBytesReader / DetectContentType の要件（下記）とむしろ整合する。

### 設計の要点：ファイルは「本体」と別に扱う

```
POST /talent/kyc/documents   （multipart）
   ① MaxBytesReader でサイズを制限しながら読む
   ② DetectContentType で中身から MIME を判定（拡張子は信用しない）
   ③ GCS へ put（パスに UUID を含める）
   ④ 成功したらDBへパスを記録

GET /talent/kyc/documents/{id}
   → バイト列を返さず、署名付きURL を返す
     （APIサーバーがファイルの中継をしない＝帯域とメモリを使わない）
```

**「APIはファイルを返さない。URLを返す」**のが要点。
tsunagu-works で学んだ「**未公開のものは取得しない**」（レビュー・メッセージ原文）と同じ考え方で、
**APIサーバーの上に機微なバイト列を乗せない**。

## 9. 型の扱い（要検証）

### 課題：フォームと API は本質的に型が違う

tsunagu-works の実測（案件フォーム8項目）:

| 種類             | 項目数 | 例                                                                |
| ---------------- | ------ | ----------------------------------------------------------------- |
| **API と一致**   | **4**  | `title` / `description` / `hours_per_week` / `remote_ok`          |
| 数値変換だけ必要 | 2      | `hourly_rate_min`（HTMLは常に文字列を返す）                       |
| **本質的に違う** | **2**  | `required_skills`（カンマ区切り）/ `status`（値は持つが送らない） |

**「全部を二重に書く」のではなく、「差分だけ手当てする」**なら負担は小さい。

### 検討した案

| 案                                                    | 二重管理             | 型安全 | Go主導                        |
| ----------------------------------------------------- | -------------------- | ------ | ----------------------------- |
| **1. 生成Zodを `.omit().extend()` で加工**            | ほぼ消える           | 高     | ✅                            |
| 2. 手書き ＋ `satisfies z.ZodType<ApiRequest>` で縛る | 残る（が検出される） | 中     | ✅                            |
| 3. **Zod起点**で OpenAPI を生成                       | **完全に消える**     | 高     | ❌ フロントが仕様の起点になる |
| 4. RHF の `setValueAs` で変換                         | 消える               | 中     | ✅                            |
| 5. UIを変えてズレを消す（タグUI等）                   | 部分的               | —      | ✅                            |
| 6. 検証を最小化（HTML標準のみ）                       | 消える               | 低     | ✅                            |

### 暫定方針（Phase 0 で検証してから確定）

**案1 ＋ 案4 の組み合わせ**

```
生成: 型 / Fetch Client / Zod
  ↓
フォーム: 生成Zodを .omit().extend() で加工（案1）
  ↓
変換: 単純な型変換は RHF の setValueAs（案4）
      複雑な変換（カンマ区切り等）は transform
```

**検証が必要なこと**（Phase 0）

- [ ] orval の生成する Zod が `.omit()` / `.extend()` できる形か
- [ ] `nullable` / `optional` の扱いが期待通りか
- [ ] enum が `z.enum([...])` で出るか
- [ ] 日付が `z.string()` か `z.coerce.date()` か
- [x] ~~multipart の生成~~ → **#106 で確認済み**（ADR-0013・§8）

### ランタイム検証をどうするか（決定: しない → [ADR-0004](adr/0004-no-runtime-validation.md)）

| 立場                                                                                                   | 主張                                                                                    |
| ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 検証する                                                                                               | APIが仕様通りとは限らない。壊れたデータで画面が落ちるのを防ぐ                           |
| **検証しない**（[参考記事](https://engineerblog.mynavi.jp/technology/2025-advent-calendar-12/)の立場） | **OpenAPIとバックエンドの齟齬はバックエンドのテストで対処**。フロントの再検証は二度手間 |

**自社APIかつ同一 spec から Go のコードも生成している**ため、後者が合理的と考えている。
ただし**採用するなら ADR に理由を残す**。

### 日付・null の扱い（決めておく）

|                | Go                    | JSON                     | 生成されるTS     | 画面                  |
| -------------- | --------------------- | ------------------------ | ---------------- | --------------------- |
| 日時           | `time.Time`           | `"2026-08-07T10:30:00Z"` | `string`         | `Date` に変換して整形 |
| 日付のみ       | `time.Time`（DATE列） | **`"2026-08-03"`**       | `string`         | 週の範囲表示など      |
| 未設定の時刻   | `*time.Time`          | `null`                   | `string \| null` | 条件分岐              |
| 未設定の文字列 | `string`（空文字）    | `""`                     | `string`         | —                     |

**「未設定」の表現は型で決める**（時刻はnull・文字列は空文字）。tsunagu-works と同じ方針。

## 10. テスト戦略

> ⚠️ **2026-08-17 [ADR-0008](adr/0008-pgx-tx-test-isolation.md) による変更**: 本節の「go-txdb」は **pgx.Tx による分離**（テストごとに BEGIN → 自動 ROLLBACK・同じ考え方の pgx ネイティブ実装）に読み替えること。go-txdb は database/sql 用のため、sqlc の pgx/v5 生成と接続できない。テスト戦略そのもの（実DB・モックしない・同一インスタンスの別DB）は変更なし。

| 層                | 何を                         | どう                                                |
| ----------------- | ---------------------------- | --------------------------------------------------- |
| **shared/domain** | 状態遷移・不変条件           | **純粋関数のテーブル駆動**（DBもHTTPも不要）        |
| **usecase**       | 業務フロー・トランザクション | **go-txdb**（テストごとにロールバック）＋ factories |
| **handler**       | 入出力の変換・**認可**       | httptest（**実ミドルウェア込み**で叩く）            |
| **フロント**      | 部品の振る舞い               | Vitest ＋ Testing Library                           |
| **E2E**           | 通しシナリオ                 | ~~Playwright~~ → **API 統合テスト**（実MW込み httptest・基準世界 fixture・[ADR-0012](adr/0012-api-integration-tests-over-browser-e2e.md)） |

### go-txdb が何をするか

```
sql.Open("txdb", ...)   →  内部で BEGIN
    テストが INSERT/UPDATE し放題
db.Close()              →  内部で ROLLBACK  ★ 自動で元通り
```

| 方式                                      |                                                                         |
| ----------------------------------------- | ----------------------------------------------------------------------- |
| モック（repository をインターフェース化） | 速い／しかし**SQLが正しいかは検証されない**（モックは常に期待通り返す） |
| **txdb（本物のDB）**                      | やや遅い／**SQL・制約・トランザクションが全部検証される**               |

**「モックを減らして実DBで検証する」**のが方針。モックが多いと「テストは通るが動かない」が起きる。

> **目標の目安**：tsunagu-works はテストが実装の 25%（純粋関数のみ）。
> 実DBテストまで書くと**実装と同量かそれ以上**になるのが普通で、そこまで持っていく。

### 決めること

| 論点             | 方針                                                                |
| ---------------- | ------------------------------------------------------------------- |
| テスト用DB       | **同じインスタンスの別データベース**（`_test` サフィックス）        |
| 分離方法         | **go-txdb**                                                         |
| テストデータ     | **factories**（デフォルト値を持ち、必要な項目だけ上書きできる関数） |
| モックの範囲     | **usecase のテストでは何もモックしない**                            |
| **GCS のテスト** | **fake-gcs-server**（モックしない）                                 |

## 11. デプロイ

```
GitHub Actions
  ├→ lint / test / 生成物の差分チェック
  └→ main にマージ
       ├→ Docker マルチステージビルド（distroless）
       ├→ Cloud Run Job: migrate      ★ 先に流す
       ├→ Cloud Run: api-server
       ├→ Cloud Run: company（Next standalone）
       └→ Cloud Run: talent（Next standalone）
```

| 項目                 | 選択                                             |
| -------------------- | ------------------------------------------------ |
| ホスティング         | **Cloud Run**（アイドル時は課金されない）        |
| DB                   | **Neon**（無料枠・PostgreSQL・自動サスペンド）   |
| ファイル             | **Cloud Storage**（非公開バケット・署名付きURL） |
| シークレット         | Secret Manager                                   |
| **マイグレーション** | **`cmd/migrate` を Cloud Run Job で実行**        |

### なぜ Cloud Run Job か

| 方式                 | 問題                                                                       |
| -------------------- | -------------------------------------------------------------------------- |
| API 起動時に自動適用 | ❌ **Cloud Run はスケールする**＝複数インスタンスが同時に流す              |
| **Cloud Run Job**    | ✅ **1回だけ実行される**・CIから起動できる・失敗したらデプロイを止められる |

**同じイメージから2つのバイナリ**（`cmd/server` / `cmd/migrate`）を出し、Job ではエントリポイントだけ変える。
sql-migrate は**ライブラリとして使う**（CLIをイメージに入れない）。

**新旧のコードが同時に動く時間があるため、後方互換な変更に限る**（列の削除は2段階でやる）。

### ビルドの最適化

| 対象    | 手段                                                                                                     |
| ------- | -------------------------------------------------------------------------------------------------------- |
| Next.js | **`output: 'standalone'`** ＋ **`turbo prune --docker`**（依存を絞る）                                   |
| Go      | **マルチステージ**（builder → distroless）。`turbo prune` は効かない                                     |
| CI      | `actions/setup-go` のキャッシュ ＋ **Turborepo のリモートキャッシュ**（Playwright は不採用に・ADR-0012） |

**注意**: 無料枠のDBはコールドスタートが遅い（初回数秒）。面談で見せる前に一度アクセスしておく。

## 14. tsunagu-works から引き継ぐもの

**設計判断の記録はそのまま活きる。**以下は新リポジトリでも同じ方針を採る。

- 所有チェックは **WHERE に埋め込む**（取得してから判定しない）
- 状態遷移は **表で一元管理**し、許可だけを列挙する（ホワイトリスト）
- 「できないようにする」より **「できる形が存在しない」**
- 確定した合意は **値でコピーする**（スナップショット）
- **未公開・原文は「取得しない」**（画面で隠さない）
- 制約には **理由と代替（または見通し）**を添える

## 15. 付録：主要な設計判断の一覧（tsunagu-works との対比）

**面談で「なぜそうしたか」を問われる箇所。**理由まで含めて即答できる状態にする。

| 要素             | tsunagu-works                 | 本リポジトリ                              | 判断の理由                                          |
| ---------------- | ----------------------------- | ----------------------------------------- | --------------------------------------------------- |
| ルーティング     | `mux.HandleFunc` を手書き     | **生成コードが張る**                      | URLの一次情報を仕様に一本化する                     |
| ハンドラの型     | `http.ResponseWriter` 直書き  | **StrictHandler**（型付き req/res）       | **仕様とのズレがコンパイルエラーになる**            |
| 依存の持ち方     | パッケージ変数の `db`         | **main.go で DI**                         | テストで接続を差し替えられる                        |
| デプロイ単位     | 1バイナリ                     | **1バイナリ（ディレクトリは分割）**       | 分割可能な形にして、**今は分けない**判断を示す      |
| 分割の軸         | —                             | **視点**（company / talent）              | 企業と人材で見える世界が違う。認可が境界に一致する  |
| DBアクセス       | `database/sql`（手書き）      | **sqlc**                                  | SQLを資産として残したまま型安全にする               |
| repository 層    | 無し                          | **無し（意図的）**                        | `Queries` が repository 相当。薄皮を重ねない        |
| 認可のロール判定 | 各ハンドラで `if user.Role`   | **パスプレフィックス × ミドルウェア**     | **書き忘れが構造的に起きない**                      |
| バリデーション   | 手書き・エラーは文字列1本     | **宣言的 ＋ フィールド別エラー型**        | フォームのフィールド単位表示が型安全につながる      |
| 一覧の取得       | 全件（ページネーション無し）  | **seek 法**（`id >= token` ＋ `LIMIT n+1`） | OFFSET は深いページで遅く、挿入でズレる           |
| テスト           | 純粋関数のみ（25%）           | **go-txdb ＋ factories**（実DB）          | モックが多いと「テストは通るが動かない」が起きる    |
| フロントの分割   | 1アプリ内でロール分岐         | **2アプリ ＋ Turborepo**                  | ロール分岐がアプリ境界になる                        |
| ファイル         | 扱わない                      | **Cloud Storage ＋ 署名付きURL**          | APIサーバーに機微なバイト列を乗せない               |
| 公開             | ローカルのみ                  | **Cloud Run ＋ Cloud Run Job**            | マイグレーションは1回だけ実行される必要がある       |
