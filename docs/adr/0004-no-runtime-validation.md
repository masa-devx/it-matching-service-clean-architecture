# ADR-0004: フロントエンドでランタイム検証をしない

- ステータス: Accepted
- 日付: 2026-08-08

## 背景

orval は API レスポンスの Zod スキーマも生成できるため、「受信したレスポンスを毎回 Zod で検証（parse）するか」を決める必要があった。

- 検証する派の主張: API が仕様通りに返すとは限らない。壊れたデータで画面が落ちるのを防げる
- 検証しない派の主張: OpenAPI とバックエンドの齟齬は**バックエンドのテストで対処すべき**で、フロントでの再検証は二度手間（[参考記事](https://engineerblog.mynavi.jp/technology/2025-advent-calendar-12/)）

本リポジトリの前提: API は**自社（自分）のもの**であり、**同一の spec から Go 側のコードも生成している**。仕様とのズレは StrictHandler のコンパイルエラーと CI の生成差分チェックで検出される。

## 決定

API レスポンスのランタイム検証（Zod parse）はしない。生成された型を信頼する。

ただし**フォーム入力の検証は別物であり、Zod で行う**——ユーザー入力は「仕様を守る保証が構造的に無い」データなので、検証する理由が残る。

## 代替案と却下理由

| 案 | 却下理由 |
| --- | --- |
| 全レスポンスを Zod で parse する | spec と実装のズレは Go 側（StrictHandler・テスト・CI差分チェック）で既に検出される。同じ保証を2か所で払うのは二度手間で、parse のコストと失敗時のハンドリングコードも増える |
| 境界（external/client）でのみ parse する | 折衷案だが、上記の通り自社APIでは検出の重複に変わりない。外部APIを叩くことになったときに、その境界だけで採る案として保留 |

## 影響

- 生成 Zod の用途は**フォーム検証**（`.omit().extend()` で加工）に限定される
- レスポンス型の信頼性は「同一 spec からの生成 ＋ CI の差分チェック」が担う——**この前提が崩れる変更（手書き型の混入など）をしない**ことが運用条件になる
- **見直しの条件**: サードパーティ API など「自分がテストできない API」を叩くとき。その境界にのみランタイム検証を導入する
