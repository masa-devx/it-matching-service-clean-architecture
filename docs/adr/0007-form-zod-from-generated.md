# ADR-0007: フォーム検証は生成Zodの加工で行う（案1＋案4）

- ステータス: Accepted
- 日付: 2026-08-10

## 背景

フォームと API は本質的に型が違う（HTML入力は常に文字列・カンマ区切り等のUI都合の形がある）。
設計プラン§9 で6案を比較し「案1（生成Zodを `.omit().extend()` で加工）＋案4（単純変換は RHF の `setValueAs`）」を暫定方針としたが、**orval の生成する Zod が加工に耐える形かは Phase 0 で検証してから確定**としていた。

Phase 0（#8）での検証結果:

| チェック項目 | 結果 |
| --- | --- |
| 生成 Zod が `.omit()` / `.extend()` できるか | ✅ 素直な `zod.object()` で生成され、加工可能（テストで固定済み） |
| nullable / optional の扱い | ✅ 入力の `?` は `.optional()`・レスポンスの `\| null` は `.nullable()` と正確に区別 |
| enum の生成形 | ✅ `zod.enum(['draft', ...])` |
| 日付の生成形 | ✅ `zod.iso.datetime()`（文字列のまま形式検証。画面表示の直前で Date 化する方針と整合） |
| 副産物 | `@maxLength` 等の制約が名前付き定数としても輸出され、UI（文字数カウンター等）から再利用できる |

## 決定

1. フォームスキーマは **orval の生成 Zod を `.omit().extend()` で加工**して作る（案1）。API と形が一致するフィールドは生成物を無編集で引き継ぎ、**UIの都合で形が違うフィールドだけ**を `transform` で差し替える
2. 数値入力など**単純な型変換は RHF の `setValueAs`** で吸収する（案4）
3. RHF との接続は **`standardSchemaResolver`** を使う（Zod 4 は Standard Schema 実装のため最も安定）
4. `z.input`（フォームが持つ形）と `z.output`（API に送る形）を型として分離して公開する
5. 方針の成立条件は **テスト（schema.test.ts）で固定**する。生成形の変化で omit/extend が壊れたら、このテストが方針見直しのシグナルになる

## 代替案と却下理由

| 案 | 却下理由 |
| --- | --- |
| 案2: 手書き＋`satisfies z.ZodType<ApiRequest>` で縛る | 二重管理が残る。検証の結果、案1が成立したため不要（案1が崩れたときのフォールバックとして保持） |
| 案3: Zod 起点で OpenAPI を生成 | フロントが仕様の起点になる（ADR-0004 と同じ理由で、契約は中立の場所に置く） |
| 案6: 検証を最小化（HTML標準のみ） | 制約の一次情報（spec）とフォームの検証が切れ、仕様変更がフォームに届かなくなる |

## 影響

- フォーム検証ルールの一次情報が spec（.tsp の `@maxLength` 等）に一本化され、仕様変更が再生成でフォームまで届く
- Zod は **v4 系**を採用（`zod.iso.datetime` 等の新API）。tsunagu-works 時代の Zod 3 の知識とは書き方が一部異なる
- 生成クライアントの置き場は `packages/api-client` に確定（アプリのソースツリーから生成物を隔離・turbo グラフで spec→api-client→web の経路を明示）
- **見直しの条件**: orval のメジャー更新等で生成 Zod の形が変わり schema.test.ts が壊れたとき。案2 へ切り替える
