# ADR-0012: ブラウザ E2E（Playwright）を見送り、API 統合テストに投資する

- ステータス: Accepted（承認済み）
- 日付: 2026-08-20

## 背景

Phase 6 の当初計画は「Playwright によるブラウザ E2E（応募 → 選考 → 承諾の通し）+ handler 統合テスト」だった（設計プラン §13）。着手前に、実務経験のある参考プロダクト（非公開・TypeScript フルスタック・本番運用）のテスト運用を実地調査した結果、以下が分かった:

- テスト投資は **API 統合テスト（150 本超・5万行超）に一点集中**。アプリ全体を本物の配線で起動し、レスポンスと DB の実状態を突合する方式が回帰防止の主力だった
- **ブラウザ E2E（Cypress）は導入されたが廃止**されていた（スクリプトの残骸のみ)。ブラウザ E2E は「書けるか」ではなく「維持できるか」で決まる、という実例
- フロントの正しさは「生成型の一気通貫（スキーマ駆動）＋ビジュアル確認」で担保していた — このリポジトリの「orval 生成型 + Storybook」と同じ分担

このリポジトリでも、認可ミドルウェアを通したリクエストのテスト（最大の守りの穴）は API 統合テストで塞がるうえ、フロントには型 + Storybook（play 関数・a11y）という検証線が既にある（ADR-0009）。

## 決定

**ブラウザ E2E（Playwright）は導入しない**。Phase 6 は以下に投資する:

1. **API 統合テストをこのリポジトリの「E2E」とする**: 本番と同じ配線（生成ルーター + 実ミドルウェア）を httptest で起動し、本物の signin で得た JWT Cookie を使って、認可（401/403）と代表フローをレスポンス + DB 突合で固定する（#93）
2. その土台として、基準世界のデータ運用基盤（seed → dump → 検知3層）を作る（#95）

一度着手した Playwright 基盤（#91 のスモークテストまで）は**マージせず破棄**した。

## 代替案と却下理由

| 案 | 却下理由 |
| --- | --- |
| Playwright を計画どおり導入 | ブラウザ E2E で**しか**検証できないのは「ブラウザ Cookie → Next → Go の転送」「middleware.ts のリダイレクト」等の継ぎ目に限られる。その価値に対し、実行時間・不安定さ・保守の維持コストが釣り合わない（参考プロダクトが廃止に至った構図と同じ）。個人開発では「動かす人間＝作った人間」なので、継ぎ目の退行は手動確認で気づきやすい |
| Cypress など他のブラウザ E2E ツール | ツールの選択の問題ではなく「ブラウザ層の自動テストを維持するか」の問題なので同じ結論 |
| API 統合テストも書かない（現状維持） | 認可ミドルウェアの通しが未検証のまま残る。これは「ロール認可はミドルウェアで一律」という設計の見せ場そのものが守られていない状態で、許容できない |

## 影響

- 楽になること: e2e 専用の CI workflow・ブラウザ起動・Playwright の運用が丸ごと不要。API 統合テストは「DB を使う go test」なので**既存の backend-ci にそのまま乗る**
- 引き受けるコスト: 「ブラウザ Cookie → Next → Go の転送」「ルートグループのリダイレクト」は自動テストで守られない（リリース前の手動確認と型に委ねる）

## 再導入の発動条件（ADR-0009 の流儀）

以下のいずれかが起きたら、このADRを見直してブラウザ E2E を再検討する:

1. **継ぎ目の退行が実際に2回以上発生**した（Cookie 転送・リダイレクト・Server Actions の配線切れなど、API テストで捕まらない種類のバグ）
2. **複数人開発になった**（「動かす人間＝作った人間」の前提が崩れ、手動確認がスケールしなくなる）
3. リリース前の手動確認が**30分を超える**ようになった（自動化の損益分岐）
