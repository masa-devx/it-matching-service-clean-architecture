# ADR-0014: ブラウザ E2E（Playwright）を「継ぎ目」に限って導入する

- ステータス: Accepted（承認済み）
- 日付: 2026-09-30

## 背景

[ADR-0012](0012-api-integration-tests-over-browser-e2e.md) でブラウザ E2E を見送り、API 統合テストをこのリポジトリの「E2E」とした。その際、次の継ぎ目は自動テストで守らず、手動確認と型に委ねるコストとして引き受けた:

- ブラウザ Cookie → Next（RSC / Server Actions）→ Go の転送
- ルートグループの `layout.tsx` によるガード（未ログイン・ロール違いのリダイレクト）
- Server Actions の配線

ADR-0012 の再導入の発動条件（継ぎ目の退行2回以上・複数人開発・手動確認30分超）は、いずれも**満たしていない**。それでも見直すのは、条件の外側で前提が変わったため:

1. **Phase 7（eKYC）で、API 統合テストが構造的に届かない継ぎ目が増える**。ブラウザからのファイル選択 → Server Action → multipart で Go へ、という経路と、**署名付き URL でブラウザが GCS に直接アクセスする経路**（サーバーを通らない）。後者は httptest の外側にあり、API 統合テストをいくら増やしても検証できない
2. eKYC を載せる前に、既存の継ぎ目（認証・ガード）を自動で固定しておきたい。新しい継ぎ目を足したときに「既存の継ぎ目を壊していない」ことを毎回手で確かめる前提は、Phase 7 の作業量に対して割に合わない

## 決定

**ブラウザ E2E（Playwright）を、API 統合テストでは検証できない「継ぎ目」に限って導入する**。API 統合テストが通しの主力であることは変えない（ADR-0012 の投資判断は継続）。

線引き:

- **書くもの**: 継ぎ目（Cookie 転送・ガードのリダイレクト・Server Actions の配線・ブラウザ → GCS）。シナリオは十本未満に保つ
- **書かないもの**: 業務ルール（遷移の可否・403/404 の詳細・seek）は domain / usecase / API 統合テストの担当。入力エラーの表示は Storybook の担当。**層をまたいで同じ検証を繰り返さない**
- **CI の必須チェックにしない**（手動実行 + 定期実行）。ADR-0012 で懸念した不安定さが PR を止めないようにする
- **データは E2E 専用 DB を毎回リセットして使う**。基準世界（#95 の `dump.sql`）を API 統合テストと共用し、書き込むシナリオは実行ごとに一意なデータを自分で作る

## 代替案と却下理由

| 案 | 却下理由 |
| --- | --- |
| ADR-0012 を維持（手動確認を続ける） | 署名付き URL の直アクセスは手動確認以外に検証手段がなくなる。eKYC 以降は継ぎ目が増える一方なので、手動確認の負担が単調に増える |
| 画面ごとに網羅的なブラウザ E2E を書く | 業務ルールの検証が API 統合テストと重複し、保守コストだけが増える。参考プロダクトがブラウザ E2E を廃止した構図（ADR-0012）そのもの |
| 署名付き URL だけを Go のテストで検証（GCS エミュレータに HTTP で直接 GET） | URL が有効であることは確かめられるが、「画面からその URL が開ける」継ぎ目は検証できない。この検証は Phase 7 の API 側のテストで別途検討し、ブラウザ E2E とは役割を分ける |

## 影響

- 楽になること: 認証・ガードの継ぎ目の退行が自動で見つかる。eKYC の継ぎ目も同じ基盤に載せられる
- 引き受けるコスト: ブラウザ・2サーバー起動の実行時間、Playwright のバージョン追従、E2E 専用 DB の運用
- 見直す条件:
  - **不安定なテストが月2回以上**出た → シナリオを削るか、原因の層（API 統合テスト・Storybook）へ検証を移す
  - 実行時間が **5分を超えた** → 並列化（workers）とデータ分離の見直し
  - シナリオが **10本を超えそう** → 業務ルールを書き始めていないか棚卸しする
