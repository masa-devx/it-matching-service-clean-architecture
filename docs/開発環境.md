## Phase0 #25: CI（GitHub Actions: api-ci / web-ci）

### 何をした

`.github/workflows/` に api-ci（golangci-lint→build→test）と web-ci（lint→format:check→build）を作成。パスフィルタで対象領域の変更時のみ実行。Nodeバージョンは `web/.nvmrc`、Goバージョンは `api/go.mod` を単一の真実として参照。

### 概念

- **workflow / job / step / runner**: workflowはyml1枚、jobはrunner（ubuntu-latest等のVM）1台で走る単位、stepはその中の直列コマンド
- **`uses: owner/repo@vN`**: 公開Action（再利用可能な処理）の呼び出し。メジャータグ固定＝パッチは自動追従・メジャー更新は手動判断
- **パスフィルタ**: `paths:` で「apiだけのPRでwebのCIを走らせない」。ワークフロー自身のパスも含める（CI設定変更のPRでCI自体が検証される）
- **バージョンの単一の真実**: CIに直書きせず `go-version-file: go.mod` / `node-version-file: .nvmrc` を読む。ローカル（nvm）とCIが同じファイルを見るので二重管理が消える
- **`npm ci`**: package-lock.json 完全準拠のクリーンインストール。`npm install` と違いlockを書き換えない＝CIの再現性
- **concurrency + cancel-in-progress**: 同一PRへの連続pushで古い実行を自動キャンセル
- **`go test ./...` はテスト0件でも成功**する仕様（#26でテストが入るまでのパススルー）

### ✅ベストプラクティス

- ローカルとCIで同一の設定ファイル・同一のコマンドを使う（golangci-lint は .golangci.yml、format は npm scripts 経由）
- Actionのバージョンは導入時にAPIで最新メジャーを確認して固定（推測で書かない）

### ⚠️アンチパターン

- CIだけにしかない手順（ローカルで再現できない失敗はデバッグ地獄）
- `@main` 等の動くリファレンスでActionを参照
- パスフィルタ無しで全PRに全CI（実行時間とお金の浪費）

### 理解度チェック

- [ ] paths にワークフロー自身を含める理由を言える
- [ ] npm ci と npm install の違いを言える
- [ ] go-version-file / node-version-file 方式の利点を言える

## Phase0 #27: air ホットリロード＋ルートMakefile

### 何をした

air（Go用ホットリロード）を導入し（`.air.toml`・成果物はignore済みの`tmp/`へ）、よく使う操作をルートMakefileに集約（dev-api/dev-web/db-_/migrate-_/test/lint/build）。`make help` でself-documenting。READMEのセットアップをmake経由に更新。

### 概念

- **air**: ファイル監視→`go build`→プロセス差し替えのループを自動化する開発ツール。コンパイル言語のGoでは「停止→ビルド→起動」の手動ループが必須だった部分の代行。Next.jsのFast Refresh（モジュール差し替え・state保持）とは原理が違い、プロセスまるごと再起動
- **開発ツールはgo.modに入れない**: air/golangci-lint/sql-migrateは`go install`でマシンに入れる。アプリの依存（go.mod）と開発マシンのツールは別物
- **Makefileの基礎**: ターゲット＝コマンドの名前付け。`.PHONY`＝「ファイル名ではなくコマンド」の宣言（同名ファイルがあると実行されなくなる事故防止）。**レシピ行は必ずタブ**（スペースだと`missing separator`エラー・最頻出の罠）
- **self-documenting help**: 各ターゲットの`## コメント`をgrep+awkで拾って一覧表示する定番イディオム。`.DEFAULT_GOAL := help`で`make`だけ叩けば一覧が出る
- **`$(MAKE) -C dir`**: サブディレクトリのMakefileへ委譲（migrations/のMakefileを二重管理しない）

### ✅ベストプラクティス

- Makefileのtest/lintはCIと同一コマンドにする（「ローカルで通ればCIも通る」を保証）
- .envも監視対象に（godotenvは起動時読みなので、変更時に自動再起動されると事故が減る）

### ⚠️アンチパターン

- airをgo.modに追加する／ホットリロードの成果物をignoreせず#24のバイナリ事故を再演する
- Makefileのレシピをスペースでインデントする

### 理解度チェック

- [ ] airとFast Refreshの原理の違いを言える
- [ ] .PHONYが防ぐ事故を説明できる
- [ ] make helpの仕組み（##コメントをgrepする）を説明できる

## Phase0 #32: docker compose 拡充（db + api + web）

### 何をした

api/web に開発用 Dockerfile.dev（道具だけ焼き込み・ソースはvolume注入）と .dockerignore を追加。compose に api（air・go-modキャッシュ）/ web（next dev・node_modules遮蔽）サービスを定義。dbにhealthcheck。make docker-up / db-up（dbだけ）で2モード併用。

### 概念

- **コンテナ間DNS**: composeネットワーク内はサービス名がホスト名（api→dbは `db:5432`・web→apiは `http://api:8081`）。`localhost:5434` は「ホストから見た」ポートフォワードの入口。「どこから見たアドレスか」が全て
- **healthcheck + service_healthy**: 「コンテナ起動」≠「サービス準備完了」。pg_isready で後者を待つ（depends_onだけでは起動順しか保証されない）
- **開発用Dockerfileはソースを COPY しない**: 道具（Go+air / node）だけ焼き、コードはマウント注入→ホットリロードが効く。本番用（マルチステージで成果物だけ）とは別物
- **node_modules の遮蔽ボリューム**: macOSホストの node_modules（darwin用バイナリ）をLinuxコンテナに持ち込むと壊れる→専用named volumeで覆い、コンテナ内で npm install
- **実環境変数 > .env ファイル**: compose の environment は .env.local より優先される（NEXT_PUBLIC_API_URL の上書きが効く理由）
- **ポート衝突**: ローカル直起動とDockerモードは同じホストポートを取り合うため同時使用不可。`lsof -nP -iTCP:8081 -sTCP:LISTEN` が調査の第一手

### ✅ベストプラクティス

- .dockerignore で .env をビルドコンテキストから排除（イメージレイヤーに秘密を焼かない）
- 依存キャッシュ（go mod / node_modules）はnamed volumeで永続化し起動を高速化

### ⚠️アンチパターン

- depends_on だけでDB準備完了を仮定する／ホストの node_modules をそのままマウントする
- 開発用イメージにソースをCOPYして「編集のたびにrebuild」する

### 理解度チェック

- [ ] db:5432 と localhost:5434 の違いを説明できる
- [ ] node_modules を専用ボリュームで遮蔽する理由を言える
- [ ] 2モードが同時に使えない理由（ポート）を言える

### 補足: 開発用Dockerと本番用Dockerの違い（実務での使われ方）

**開発でapi/webをDocker化する判断**

- メリット: 環境の再現性（クローン後 make docker-up 一発）・オンボーディング短縮・本番との対称性・OS固有の罠の排除
- デメリット: macOSではVM越しでI/Oが遅い（ビルド1.5〜3倍）・デバッガ接続の一手間・リソース消費
- 実務の現実解: 「DB/ミドルウェアはDocker・アプリはローカル直起動」を日常にし、フルDockerは環境構築直後や本番同等検証で使う（本リポジトリの2モード併用はこの型）

**本番用Dockerfileは別物（将来のデプロイIssueで作る）**

- 開発用: ソースをCOPYせずマウント注入・ツールチェイン込み（〜1GB）・ホットリロード目的
- 本番用: マルチステージビルドで**バイナリだけ**の極小イメージ（distroless等・10〜20MB）。**イメージ＝不変の成果物**（テストを通った同じイメージが全環境へ行き、環境差は環境変数のみ＝#28の設計につながる）
- フロントは事情が異なる: Next.jsはVercelデプロイ（Docker不使用）が最有力。コンテナ化するなら standalone ビルド

**本番の運用フロー（実務の型）**

```
git push → CIテスト → 本番イメージbuild → レジストリpush
  → Cloud Run / App Runner / K8s が新イメージで起動 → 旧コンテナはgraceful shutdown（#29）
```

- composeは「1台の中の編成」しかできないため本番では限定的（小規模VPS等）。スケール・自動復旧はオーケストレーターの仕事
- 本プロジェクトの想定は Cloud Run（マイグレーションは Cloud Run Job で1回だけ実行）

## Phase0 #33: ドキュメント3層化とテンプレ利用手順

### 何をした

READMEを3層に再構成: **ルート=使い方**（セットアップ・スタック選定理由・テンプレ手順）／**api/README・web/README=設計**（構成・規約・選定理由・進化ロードマップ）／**docs=物語と判断ログ**（サービス概要はdocs/サービス概要.mdへ移設）。テンプレ利用手順は scratchpad で実地検証（clone→myappへ一括置換→go mod tidy→build/test/compose config 全通過）。

### 概念

- **ドキュメントの3層分担**: 「どう動かすか（ルート）／どう作られているか（各ディレクトリ）／なぜそうしたか（docs）」を分けると、読者（新規参加者・レビュアー・採用担当）ごとに入口が定まる
- **テンプレ戦略**: サービスリポジトリは継続し、テンプレは別リポジトリへ抽出して GitHub Template repository 化（Use this template で生成）。抽出はスナップショット扱い・R1完了時に第2弾を抽出可能
- **手順は書いたら実地検証**: ドキュメントされた手順は腐りやすい。scratchpadでの通し実行が受け入れ条件

### ✅ベストプラクティス

- 選定理由には「再検討の発動条件」をセットで書く（なぜ使わないかが将来の判断基準になる）
- 一括置換は「識別子→表示名」の順・実行後に残存grepで確認

### ⚠️アンチパターン

- READMEに全部盛り（使い方と設計と物語が混ざり誰も読まない）
- 手順を書いて検証しない（クローンした未来の自分が最初の犠牲者になる）

## Phase 0 #5: Turborepo + pnpm workspace（Go もタスクグラフに載せる）

### 何をした

モノレポの骨格を構築。`packages/spec`（TypeSpec）→ `api-server`（Go）/ `packages/api-client`（TS）→ `web` の依存を turbo.json の `dependsOn: ["^build"]` で表現し、**仕様変更→生成→ビルドが1コマンドで連鎖**するようにした。

### 概念

- **タスクグラフ**: turbo は package.json の依存関係からタスクの実行順を解決する。Go プロジェクトも package.json を持たせればグラフに載る（言語は問わない）
- **キャッシュ**: `inputs` / `outputs` を宣言すると入力が同じタスクはスキップ（FULL TURBO）。「差分が出ない生成」が高速の前提になる
- **strict env**: 宣言していない環境変数はタスクから見えない → 「ローカルでだけ通る」を防ぐ

### ✅ベストプラクティス

- ポートは他プロジェクトと衝突しない値に固定して ADR に記録（5435 / 8082 / 3001）

### ⚠️アンチパターン

- 生成コマンドを README の手順書だけにする（実行し忘れて仕様と実装がズレる）

### 理解度チェック

- [ ] `.tsp` を変更したとき何がどの順で走るか言える
- [ ] キャッシュの inputs / outputs が何を宣言しているか言える

## Phase 0 #10 + Phase 1 #21: モノレポ CI と生成物差分チェック

### 何をした

`monorepo-ci.yml` 1本に集約: PostgreSQL service（5435 マッピング・`tsunagu_test`）→ sql-migrate 適用 → `pnpm turbo lint format:check test build` → **生成物を再生成して `git diff --exit-code`**（仕様と生成物のズレを検出）。

### 概念

- **CI とローカルの同一性**: 同じポート・同じコマンド・バージョンは宣言ファイル参照（.nvmrc / packageManager / go.mod）。「CI でだけ落ちる」の原因を構造的に減らす
- **生成物差分チェック**: 生成物をコミットする方式の弱点は「再生成し忘れ」。CI で再生成して差分が出たら fail ＝ 仕様が常に一次情報であることを機械が保証する
- **実DBテストを CI で**: service コンテナに migrate を流せば pgx.Tx 分離のテストがそのまま走る（モックが無いのに CI が安定する）

### ✅ベストプラクティス

- lint・format・test・build は turbo 経由で1コマンドに（ローカルの検証 = CI の検証）

### ⚠️アンチパターン

- CI 専用のシェルスクリプト群（ローカルで再現できない失敗が生まれる）

### 理解度チェック

- [ ] 生成物差分チェックが何の事故を防ぐか言える
- [ ] CI の DB とローカルの DB を同じ形にする工夫を3つ言える

## #62: CI の並列化と高速化（実測駆動の改善）

### 何をした

実測（1ジョブ直列で約2分54秒・Migrate 46秒・Lint&Build 81秒）を根拠に3段改善: ① sql-migrate を go.mod の tool ディレクティブへ移行（版固定 v1.8.1・go install 廃止）+ setup-go の cache 有効化。② monorepo-ci を **backend-ci / frontend-ci の2ワークフローに分割**（DB・Go は backend のみ・paths もそれぞれに絞る）。③ golangci-lint の版固定（v2.12.2）+ 解析キャッシュ。

### 概念

- **改善は実測から**: 「Migrate 46秒 = 毎回 `go install sql-migrate@latest` のソースビルド」のように、ステップ別時間を取ってから手を打つ（推測で並列化から始めない。今回も最大の犯人はキャッシュ欠落だった）
- **`go -C` と tool の cwd 問題**: `go tool` はモジュール内でしか動かない → `-C ../api-server` で移動 → すると設定ファイル内の相対パス（dbconfig.yml の `dir:`）が cwd 基準で壊れる。「設定内の相対パスは誰の cwd 基準か」はツールごとに違うので実測で確かめる
- **分割の軸は「setup を共有できる単位」**: 言語境界で切ると必要ランタイム・外部依存（DB）がきれいに分かれる。工程（lint/test/build）で切ると全ジョブがフル setup になり並列の利益が相殺される
- **ワークフロー分割 vs 1ファイル複数ジョブ**: ファイル分割は paths を絞れる（無関係な PR では起動すらしない）・引き換えに required checks の「paths 非該当 = pending」の罠がある
- **turbo `--filter`**: `api-server` は依存の ^build（spec 生成）ごと引き込む。filter はパッケージを切るが依存は断ち切らない＝生成チェーンは壊れない
- **actions/cache のキー衝突**: 同キーは先勝ちで上書きされない。複数ジョブはキーにジョブ名を含める
- **化石コメント**: 「go.sum がまだ無いため cache: false」が依存数十個の今も残っていた。「〜になったら変える」系コメントは定期的に疑う
- **公式 action を使わない判断**: golangci-lint-action は lint を action 自身が実行する形＝「CI とローカルは同一コマンド（turbo 経由）」の原則を壊すため、版固定+キャッシュだけ自前で入れた。原則と便利さが衝突したら原則を優先し、理由をコメントに残す

### ✅ベストプラクティス

- CI のツールはすべて版固定（@latest は「ある日突然 CI だけ壊れる」）。versions の一次情報は可能な限り go.mod / package.json に寄せる
- 差分チェックの対象リストは生成物ディレクトリが増えるたびに見直す（talent 側の生成物がノーチェックだった穴を今回発見）

### ⚠️アンチパターン

- 計測せずに並列化から着手する（最大のボトルネックがキャッシュ欠落なら分割しても遅いまま）
- paths フィルタの更新漏れ（migrations/** が入っておらず、マイグレーションだけの PR で CI が走らなかった）

### 理解度チェック

- [ ] 改善前の2大ボトルネックとそれぞれの原因を言える
- [ ] ジョブ分割の軸の選び方（言語 vs 工程）を説明できる
- [ ] golangci-lint-action を採用しなかった理由（どの原則と衝突したか）を言える

## Phase 5 #81: cmd/migrate と本番用 Dockerfile（distroless・23.9MB）

### 何をした

Cloud Run Job 用の `cmd/migrate`（sql-migrate をライブラリとして実行・冪等）と、本番用 Dockerfile（マルチステージ・distroless/static・server + migrate の2バイナリ同居）+ ルート .dockerignore（ホワイトリスト方式）。イメージ 23.9MB・コンテナから migrate / server / health / request_id まで検証済み。

### 概念

- **API 起動時にマイグレーションを流さない**: Cloud Run は複数インスタンスが同時起動しうる → 起動時実行だと同じ DDL が並走（TOCTOU の DDL 版）。デプロイパイプラインの中で Job として1回だけ実行する
- **pgx stdlib アダプタ**: アプリ本体は pgx ネイティブだが sql-migrate は database/sql を要求 → `_ "pgx/v5/stdlib"` のブランクインポートで init() がドライバ登録（Go の定番イディオム）。冪等性は gorp_migrations が担保（Job リトライ安全）
- **マルチステージビルド**: builder（golang:1.26・~1GB）でビルドし、実行イメージは distroless/static（シェルもパッケージマネージャも無い）へバイナリだけ COPY。攻撃面とサイズ（23.9MB）とコールドスタートの最小化
- **CGO_ENABLED=0**: C 依存の無い静的バイナリにする＝ libc の無い distroless/static で動く条件。`-trimpath -ldflags "-s -w"` でさらに削減
- **1イメージ2バイナリ**: サービスは ENTRYPOINT /server・Job は command 上書きで /migrate。「テストを通った同じイメージ」が両用途へ（イメージ＝不変の成果物）
- **go:embed はモジュール境界を越えられない**: migrations/ddl は api-server の外 → イメージに COPY + `MIGRATIONS_DIR` 環境変数（既定はイメージ内パス＝本番がデフォルト・ローカルが上書き）
- **.dockerignore のホワイトリスト方式**: `*` で全部除外 → `!api-server` `!migrations/ddl` だけ通す → その中の .env / tmp を後勝ちで再除外。コンテキスト最小化と「秘密をレイヤーに焼かない」を構造的に

### ✅ベストプラクティス

- 依存取得（go mod download）を COPY より先の独立レイヤーに（go.mod が変わらない限りキャッシュ）
- distroless は nonroot タグで非 root 実行

### ⚠️アンチパターン

- 本番イメージにソース・ツールチェイン・シェルを残す（サイズ・攻撃面・コールドスタートの三重苦）
- migrate をアプリの main に混ぜて起動時に流す

### 理解度チェック

- [ ] 起動時マイグレーションの競合シナリオを言える

## Phase 5 #82: Neon + Cloud Run 手動デプロイ（動く URL の獲得）

### 何をした

Neon（Postgres 16・Singapore・direct 接続）+ GCP（専用プロジェクト・Artifact Registry・Secret Manager・Cloud Run Job / サービス）で API を公開。curl でダブルオプトイン一巡まで本番検証。手順と判断は **docs/デプロイ.md** に一次記録（このエントリは学びの要約）。

### 概念

- **IAM は「誰に・何の権限を」**: シークレットの権限は Secret Manager「に」ではなく Cloud Run の**サービスアカウント（実行主体）に** secretAccessor を付与する。金庫は守る側・開ける許可は実行者に
- **Secret Manager → 環境変数注入**: `--set-secrets` で金庫から注入され、アプリの `os.Getenv` はローカルと1文字も変わらない（12-factor の完成形）
- **Apple Silicon の罠**: ローカル build は既定 **arm64**・Cloud Run は **amd64 専用** → `Application exec likely failed`。`--platform linux/amd64` が必須（CD の ubuntu ランナーでは起きない＝手動ビルドだけの罠）
- **タグとダイジェスト**: タグは動くポインタ・ダイジェストは不変の実体。Job/サービスは作成時にダイジェストを固定するので、同名タグを push し直したら `update` で再解決させる。旧ダイジェストは untagged で残る（削除可）
- **脆弱性のトリアージ**: スキャナの一覧 ≠ 危険の一覧。**govulncheck が「自分のコードから到達可能か」で判定**してくれる。対処は「依存を上げる（go get）」と「最新パッチでリビルド（--pull）」の2本柱で、CD による定期リビルドが恒久策
- **撤退可能性の設計**: デプロイ専用プロジェクトを新規作成 → `projects delete` 1回で完全撤退。費用の防波堤は「min-instances 0 + Neon 自動サスペンド + 予算アラート」の三重
- **シークレットの末尾改行**: `printf '%s'` / `tr -d '\n'` で除去（改行入りの鍵・接続文字列は「たまに動かない」系バグの温床）

### ✅ベストプラクティス

- 手で1回デプロイしてから自動化する（#84）— 各ステップの意味と失敗の切り分け方を知ってから CD に固める
- GitHub の Secret scanning + Push protection・Dependabot を有効化（.env 運用の最後の安全網）

### ⚠️アンチパターン

- サービスアカウントキーを発行して CI に置く（#84 で Workload Identity Federation を使う理由）
- ローカルで動いたイメージを無検証で本番へ（アーキテクチャ・プラットフォーム差は実行して初めて分かる）

### 理解度チェック

- [ ] secretAccessor を「誰に」付けたか・なぜそこかを言える
- [ ] arm64 イメージが Cloud Run で死ぬ理由と、CD では起きない理由を言える
- [ ] govulncheck がスキャナより「騒がない」理由を言える

## Phase 5 #83: web を Cloud Run へ（standalone・モノレポ Docker・ADR-0011）

### 何をした

Vercel 不採用・Cloud Run 統一を ADR-0011 に記録し、Next.js を `output: 'standalone'` + マルチステージ Dockerfile（node:24-slim・291MB）でデプロイ。ブラウザで公開 URL からログイン〜応募一覧まで本番確認・Cookie の HttpOnly + Secure を確認。

### 概念

- **standalone 出力**: ビルド時に import を**トレース**して実行に必要な node_modules サブセット + server.js を自己完結で抽出（開発時 1GB 超 → 数十MB）。static は CDN 配信想定で**意図的に含まれない** → 明示 COPY。モノレポでは `outputFileTracingRoot` で基準を明示
- **モノレポの Docker ビルド3段**: マニフェストだけ COPY → `pnpm install --frozen-lockfile`（**api-server/package.json も必要** = Go でも workspace の一員なので lockfile 照合対象）→ ソース COPY → `turbo build --filter=web`（生成チェーンがイメージ内で走る＝CI・ローカルと同一コマンド）
- **`HOSTNAME=0.0.0.0`**: standalone は既定 localhost バインド。コンテナ外（Cloud Run のプロキシ）からは届かない — 「コンテナで動く条件」の Node 版（Go の CGO_ENABLED=0 に相当する急所）
- **Dockerfile ごとの .dockerignore**（BuildKit）: `-f web/Dockerfile` なら `web/Dockerfile.dockerignore` が優先。ignore をビルド単位に分割し、それぞれホワイトリスト方式を維持
- **env の使い分け**: API_URL は秘密ではない → `--set-env-vars`（Secret Manager を使わない）。秘密かどうかで置き場を変える
- **判断の対比が学び**: 参考実装（it-support-service）と同構成にしたことで、Vercel 案との取引（学習価値 vs 運用ゼロ工数）が ADR-0011 に言語化された

### ✅ベストプラクティス

- ランタイムイメージには standalone + static だけ（ソース・devDependencies・ビルドツールを残さない）

### ⚠️アンチパターン

- ローカルの node_modules ごと COPY する（1GB 超・アーキ不一致・秘密混入の三重苦）
- 300MB 級イメージで untagged を放置（無料枠 0.5GB は2世代で尽きる）

### 理解度チェック

- [ ] standalone が「小さくなる」仕組み（何をトレースするか）を言える
- [ ] Go イメージの CGO_ENABLED=0 と Node イメージの HOSTNAME=0.0.0.0 の共通点（「コンテナで動く条件」）を言える
- [ ] API_URL を Secret Manager に入れなかった理由を言える

## Phase 5 #84: CD パイプライン（Cloud Build + WIF・main マージ＝デプロイ）

### 何をした

it-support-service の型に合わせ、CD を「GHA＝起動役（`deploy.yml`）／手順の一次情報＝ルートの `cloudbuild.yaml`」の2段構成で実装。あわせて GitHub Ruleset（main 直 push 禁止 + CI 緑必須）と Artifact Registry クリーンアップポリシーを設定した。

### 概念

- **SA の二層**: GitHub Actions の身分（github-deployer＝ビルドの**発注だけ**）とビルドの身分（compute 既定SA＝run.admin 等で**デプロイを実行**）を分離。GHA 側が乗っ取られても、できるのは「ビルドの発注」まで
- **WIF（Workload Identity Federation）**: GCP のキーを GitHub に置かず、GitHub 発行の OIDC トークンを GCP が検証して SA になりすませる。`attribute-condition` でこのリポジトリだけに制限・workflow 側は `permissions: id-token: write` が必須。**キーが存在しない＝漏れるキーがない**
- **デプロイ順序が安全装置**: push 完了 → migrate Job `--wait` 成功 → api/web `services update`。migrate が失敗するとビルド全体が失敗し、**旧イメージのまま止まる**（半端な状態を作らない）
- **タグ＝コミット SHA**: 本番にいるコミットがタグだけで特定できる（`manual-1` のような連番だと Git と対応づかない）
- **required checks の paths 罠**: paths で絞った CI は対象外 PR で起動せず「Expected」のまま永遠にマージ不可。対処は GitHub 公式の型＝**同じ workflow 名・ジョブ名の「常に成功するツイン」を paths-ignore（鏡写し）で用意**する
- **クリーンアップポリシー**: Delete（untagged 即・14日超）と Keep（最新3世代）が競合したら **Keep が勝つ**
- **`.gcloudignore`**: `gcloud builds submit` のアップロード除外。`#!include:.gitignore` は**ルートの .gitignore しか取り込まない**ため、web/ 配下の大物（storybook-static 等）は明示する

### ✅ベストプラクティス

- デプロイ手順は cloudbuild.yaml 1ファイルに集約（CD からもローカルからも同一手順を発火できる＝緊急時の再現性）
- `concurrency: cancel-in-progress: false`（migrate 途中のキャンセルを防ぐ。CI の「新しい push で古いのを止める」とは逆の設定が正しい）

### ⚠️アンチパターン

- GCP のサービスアカウントキー（JSON）を GitHub Secrets に置く（漏洩リスク・ローテーション負担。WIF で置き換えるのが現代の型）
- deployer SA に run.admin まで付ける（発注役に実行権限は不要＝最小権限の分離を壊す）
- ツインワークフローの paths を本体と同期し忘れる（両方 or どちらも走らない事故。変更時は必ずセットで）

### 理解度チェック

- [ ] SA を2つに分ける理由（github-deployer に run.admin を付けない理由)を言える
- [ ] WIF がキー方式より安全な理由を「存在しないものは漏れない」で説明できる
- [ ] migrate 失敗時に本番がどういう状態で止まるか言える
- [ ] required checks + paths 絞りの罠と公式の対処を言える

## #96 余談: gotestsum（Go テストの Jest 風表示）

`go test` の素の出力が読みにくい問題は **gotestsum** で解決（`make test-api`）。
`--format testname` で日本語のサブテスト名がそのまま緑/赤の PASS/FAIL 付きで並び、末尾に `DONE n tests` サマリー。

- 導入は go.mod の **tool ディレクティブ**（sql-migrate と同じ型・版固定 v1.13.0・go install 不要）
- **CI には入れない**: gotestsum は人間の目のためのローカル用。CI のログは GitHub が整形するので素の `go test`（turbo 経由）を維持＝ローカルと CI で実行コマンドの中身は同じまま、見た目だけ変える
- testdox 形式は CamelCase 分割の仕様で日本語が1文字ずつ分かち書きになるため不採用（testname が日本語向き）
