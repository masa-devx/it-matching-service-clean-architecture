## Issue #2: DB接続とヘルスチェック（main/db/response/health）

### 何をした

Go APIの土台4ファイルを作成。godotenvで`.env`読込 → pgxドライバでDB接続（プール上限を明示）→ `GET /health` がタイムアウト付きPingでDB疎通込みの死活確認を返す（:8081）。

### 概念（todo-appからの進化点）

- **pgx ドライバ**: todo-appの`lib/pq`はメンテナンスモード。現行標準は`jackc/pgx`（`stdlib`経由で`database/sql`から利用、ドライバ名`"pgx"`）
- **godotenv**: Goは`.env`を自動で読まない → `godotenv.Load()`で読込。無ければ実環境変数を使う（本番対応）。DSN未設定は**fallbackせずfatal**（12-factor: 設定は環境から明示的に）
- **接続プールの上限**: `SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime`。無制限だと高負荷時に接続枯渇でDBを巻き込む
- **`context.WithTimeout`＋`PingContext`**: DB無応答時に無限待ちしない。`r.Context()`から派生させるとクライアント切断でも中断される
- **writeErrorの改善**: 詳細は**ログのみ**、クライアントには安全なメッセージ（todo-appは`err.Error()`をそのまま返していた→情報漏えい対策）

### ✅ ベストプラクティス

- healthはDB疎通まで確認（プロセス生存だけでは「動いているのに使えない」を検知できない）
- 200/503の使い分け（LB・監視が判定に使う）

### ⚠️ アンチパターン

- `.env`をコードに直書き／DSN未設定のまま暗黙のデフォルトで起動（環境事故の温床）
- healthで常に200（DBが死んでいても「正常」に見える）

### 理解度チェック

- [ ] pqでなくpgxを選ぶ理由を説明できる
- [ ] プール上限を設定しないと何が起きるか説明できる
- [ ] `PingContext`＋タイムアウトの意味を説明できる
- [ ] writeErrorで詳細をログのみに出す理由を説明できる

## Phase0 #3 Step2: POST /signup（バリデーション・bcrypt・重複409）

### 何をした

`auth.go` に `POST /signup` を実装。JSONデコード → email正規化（小文字化）→ バリデーション（email形式 / パスワード8〜72文字 / role列挙）→ bcryptハッシュ化 → INSERT。email重複はUNIQUE制約違反（SQLSTATE 23505）を検出して409に変換。

### 概念

- **bcrypt**: パスワード専用の遅いハッシュ。ソルト自動生成・ハッシュ文字列内に埋め込み（`$2a$10$ソルト+ハッシュ`）。コスト係数で計算量を指数的に調整（既定10）。SHA-256が不適な理由＝速すぎて総当たりに弱い
- **bcryptの72バイト制限**: 入力が72バイトを超えると黙って切り捨てられる → 超過を明示的に400で拒否するのが安全
- **SELECT事前確認ではなくINSERT+エラー変換**: 「SELECTで重複なし→INSERT」は2つのリクエストが同時に来ると両方すり抜ける（TOCTOU）。UNIQUE制約違反を `errors.As` で `*pgconn.PgError` に取り出し `Code == "23505"` を判定するのが正しい型
- **`RETURNING`**: INSERTと同時に生成値（id / created_at）を1往復で取得するPostgreSQLの構文
- **email正規化**: 大文字小文字を区別せず扱うため `strings.ToLower` + `TrimSpace` してから保存・比較

### ✅ベストプラクティス

- エラーレスポンスは共通ヘルパー経由で、内部エラー詳細はログのみ（`err.Error()`をクライアントに返さない）
- ステータスコードの使い分け: 入力不備=400 / リソース競合=409 / 想定外=500
- パスワードは平文をログにも出さない（reqのダンプ禁止）

### ⚠️アンチパターン

- SELECTで重複確認してからINSERT（TOCTOU競合）
- bcryptではなく速いハッシュ（MD5/SHA系）でパスワード保存
- `err.Error()` をそのままレスポンスに含める（DB構造の情報漏えい）

### 理解度チェック

- [ ] bcryptがSHA-256より安全な理由（速度と何の関係があるか）を説明できる
- [ ] 「SELECTで確認してからINSERT」がダメな理由を同時リクエストの時系列で説明できる
- [ ] `errors.As` が `==` 比較と違う点を説明できる
- [ ] RETURNINGを使わない場合、created_atを返すには何往復必要か説明できる

## Phase0 #4: POST /login（JWT発行・同一401）

### 何をした

`jwt.go`（HS256発行・sub/iat/exp・JWT_SECRETのfail fast起動チェック）と `auth.go` の `handleLogin`（email検索 → bcrypt照合 → JWT返却）を実装。認証失敗は理由を問わず同一の401。

### 概念

- **JWTの構造**: `ヘッダー.ペイロード.署名` のBase64三部構成。ペイロードは暗号化ではなく**エンコード**（誰でも読める→秘密情報を入れない）。署名だけが改ざん防止の保証
- **RegisteredClaims**: RFC 7519の標準クレーム。`sub`=誰のトークンか（文字列）／`iat`=発行時刻／`exp`=失効時刻。expなし＝漏えいしたら永久に有効、は事故
- **ユーザー列挙（User Enumeration）**: 「emailが存在しません」「パスワードが違います」を区別して返すと、攻撃者が登録済みemail一覧を収集できる → **同一ステータス・同一文言**で返す
- **タイミング攻撃対策のダミー照合**: 未登録emailで照合をスキップすると応答が速くなり、時間差で存在が推測できる → 未登録でも捨てハッシュとbcrypt照合して計算コストを揃える
- **`bcrypt.CompareHashAndPassword`**: ハッシュから埋め込みソルト・コストを取り出して同条件で再計算・比較。比較自体も一定時間（subtle.ConstantTimeCompare）

### ✅ベストプラクティス

- 署名鍵は環境変数＋起動時チェック（空鍵で起動させない）
- ログイン失敗の内部理由（no rows / mismatch）はログにも安易に出さない（出すなら監査目的で設計して出す）
- トークンのクレームは最小から始める（必要になってからroleを足す）

### ⚠️アンチパターン

- 「emailが存在しません」と「パスワードが違います」を区別して返す
- JWTペイロードに個人情報・秘密情報を入れる
- 無期限トークン／鍵のハードコード

### 理解度チェック

- [ ] ユーザー列挙攻撃の手口と「同一401」が防ぐ仕組みを説明できる
- [ ] 未登録emailでもダミーハッシュと照合する理由を説明できる
- [ ] CompareHashAndPasswordが「ソルト列なし」で照合できる理由を説明できる
- [ ] JWTを受け取ったクライアントがペイロードを読める理由と、それでも安全な理由を説明できる

## Phase0 #5: 認証ミドルウェア（parseToken / requireAuth / CORS）

### 何をした

`parseToken`（keyfuncでHMAC強制・exp自動検証・sub→userID）、`requireAuth`（Bearer取り出し→検証→contextへ格納・一律401）＋`userIDFrom`、`GET /me`（保護ルートの実物）、`corsMiddleware`（:3000許可リスト・プリフライト応答）を実装。

### 概念

- **ミドルウェアパターン**: `func(next http.Handler) http.Handler`。ハンドラを包んだハンドラを返し、玉ねぎ状に重ねる。401ならnextを呼ばない＝ハンドラは実行すらされない
- **algすり替え攻撃**: JWTヘッダーのalgは攻撃者が書き換え可能。`alg:none`（署名なし扱い）やRS256→HS256混同を、keyfunc内の `t.Method.(*jwt.SigningMethodHMAC)` 型アサーションで遮断。「検証側が方式を固定」が対策の本質
- **context.Context**: リクエスト1本に紐づく荷物置き場。キーは非公開の独自型（`type ctxKey int`）にして他パッケージとの衝突を構造的に防ぐ
- **IDOR対策の入口一本化**: user_idの取得は `userIDFrom(ctx)` だけ。リクエスト値のuser_idは信用しない
- **CORS**: ブラウザ専用の防御（サーバー間通信やcurlには無関係）。異なるオリジン（スキーム＋ホスト＋ポート）へのJSアクセスをブラウザが遮断し、サーバーが応答ヘッダーで明示的に許可する仕組み
- **プリフライト**: `Authorization` 等のヘッダー付きリクエストの前にブラウザが自動送信するOPTIONS。「この内容を送っていいか？」の事前確認。204+許可ヘッダーで応答しルーティングには渡さない
- **`Vary: Origin`**: Originによって応答ヘッダーが変わることをキャッシュ層に伝える（付けないとCDN等が別Origin向けの応答を使い回す事故）

### ✅ベストプラクティス

- Allow-Originは許可リスト方式（`*` にしない。Cookie認証では `*` は仕様上不可）
- CORSは最外層・認証はルート単位、と適用範囲で層を分ける
- 認証失敗の詳細はログのみ（クライアントには一律401）

### ⚠️アンチパターン

- `Access-Control-Allow-Origin: *` ＋ Credentials（そもそもブラウザが拒否）
- keyfuncで無条件に鍵を返す（algすり替え素通り）
- 「CORSがあるから安全」という誤解（curlやサーバーからは素通し。認証・認可こそが防御）

### 理解度チェック

- [ ] ミドルウェアが「包む」構造と、401時にハンドラが実行されない理由を説明できる
- [ ] alg:none攻撃がどのコード行で弾かれるか指させる
- [ ] プリフライトが飛ぶ条件と、OPTIONSで204を返す理由を説明できる
- [ ] CORSが「ブラウザだけの防御」である意味（curlには効かない）を説明できる

## Phase0 #24: golangci-lint 導入

### 何をした

golangci-lint v2 を導入（`api/.golangci.yml`）。標準セット＋gosec/errorlint/exhaustive/usestdlibvars等を有効化し、検出された実問題を修正（`defer db.Close()` のエラー破棄明示・gosec 2件へ理由付きnolint）。ついでに追跡され続けていたビルドバイナリを `git rm --cached` で解除。

### 概念

- **golangci-lint = linterのランナー**: govet/staticcheck/errcheck等を束ねて並列実行。go vet は内包されるのでCIはこれ一本に集約できる
- **errcheck**: エラー戻り値の無視を検出。「うっかり無視」と「判断して無視（`_ =`＋理由コメント）」をコードで区別する
- **gosec**: セキュリティlinter。G114（タイムアウト無しListenAndServe）という本物の指摘を初回実行で検出→#29で修正予定をnolintコメントに明記
- **nolintの作法**: `//nolint:linter名 // 理由` 形式。理由なしのnolintは「黙らせただけ」で監査不能
- **exhaustive**: 列挙値switchの網羅漏れ検出。Phase 3以降の状態機械（遷移表）で本領発揮する布石
- **check-blank無効の判断**: `_ = f()` を意図表明の慣習として維持（有効化すると全箇所nolint必須になる。厳格さと引き換えに冗長）

### ✅ベストプラクティス

- lint設定はリポジトリにコミットし、ローカルとCIで同一設定を参照
- linterは標準セットから始めて必要に応じて追加（最初から全部有効は警告の洪水で形骸化する）

### ⚠️アンチパターン

- 理由なしの `//nolint`／.gitignoreに書いただけで追跡済みファイルが除外されたと思い込む（`git rm --cached` が必要）

### 理解度チェック

- [ ] golangci-lint と go vet の関係を説明できる
- [ ] `_ = db.Close()` が表明していることを言える
- [ ] nolintに理由を書く意味を言える

## Phase0 #29: サーバー基礎体力（リクエストログ・タイムアウト・graceful shutdown）

### 何をした

`loggingMiddleware`（statusRecorderでステータス捕捉・strconv.Quoteでログインジェクション対策）を最外層に追加。`http.ListenAndServe` を `http.Server`（4種タイムアウト設定）に置き換え、SIGINT/SIGTERMで処理中リクエストを待つ graceful shutdown を実装。#24から持ち越した gosec G114 の nolint を解消。

### 概念

- **statusRecorder（構造体埋め込みラップ）**: ResponseWriterには「何を書いたか」を読む手段がない→埋め込みで全メソッド継承し、WriteHeaderだけ上書きして記録。デコレータパターンのGo流
- **ログインジェクション（gosec G706）**: パスに改行を含めると偽のログ行を捏造できる→ユーザー入力は strconv.Quote でエスケープしてからログへ（%qではgosecのtaint解析が解除されず、明示的なサニタイズ関数が必要だった）
- **Slowloris攻撃と4種タイムアウト**: ヘッダを1バイトずつ送って接続を占有する攻撃。ReadHeaderTimeout（ヘッダ読み切り）/ ReadTimeout（ボディ込み）/ WriteTimeout（レスポンス書き込み）/ IdleTimeout（Keep-Alive遊休）で接続の寿命を区切る
- **graceful shutdown 三点セット**: `signal.NotifyContext`（シグナルをctxに変換）→ サーバーはgoroutineで起動し `<-ctx.Done()` で待機 → `srv.Shutdown(timeout付きctx)`（新規受付停止＋処理中を待つ）。Shutdown起因の `http.ErrServerClosed` は正常終了として除外
- **なぜ本番で重要か**: デプロイ・スケールイン時はSIGTERM→猶予→SIGKILL の順で止められる（Cloud Run等）。gracefulが無いと処理中のリクエストがぶった切られる

### ✅ベストプラクティス

- ロギングは最外層（401やプリフライトも全部記録）
- タイムアウトは「無限を許さない」が原則。値は用途に応じて調整（ファイルアップロード等があればReadTimeoutを伸ばす）

### ⚠️アンチパターン

- 素の `http.ListenAndServe`（全タイムアウト無限＝Slowloris無防備）を本番に置く
- SIGKILL前提の停止運用（graceful を実装していても待ち時間より長い処理は切れる。Shutdownのtimeoutは猶予期間より短く）

### 理解度チェック

- [ ] statusRecorder が必要な理由を ResponseWriter の性質から説明できる
- [ ] Slowloris の手口と ReadHeaderTimeout の関係を言える
- [ ] Shutdown と即時終了の違い（処理中リクエストの扱い）を言える
- [ ] ErrServerClosed をエラー扱いしない理由を言える

## Phase1 #49: 構造化ログ（log/slog）へ移行

### 何をした

`log.Printf` の平文ログを Go 標準の log/slog へ移行。`logger.go` で LOG_FORMAT（text/json）・LOG_LEVEL を切り替え、アクセスログとエラーログを属性つきで出力。ステータスに応じて 5xx=Error / 4xx=Warn / それ以外=Info に出し分け。

### 概念

- **構造化ログ**: メッセージに値を埋め込まず「key=value の属性」で渡す。ログ基盤がフィールド単位で検索・集計・アラートできる（`status=500` の件数監視など）。平文は grep しかできない
- **Logger と Handler の分離**: 「何を書くか」と「どう出すか」が別。コードは `slog.Info("msg", "key", v)` だけ書き、形式の切り替えは起動時の1箇所
- **出力先は常に標準出力**（12-Factor）: アプリはファイルに書かない。ローテーション・収集・保存は Docker / Cloud Run / ログ基盤の仕事。「どこに出すか」ではなく「どんな形式か」がアプリの責任
- **レベル設計**: 5xx=Error（要対応・アラート対象）/ 4xx=Warn（クライアント起因・調査の手がかり）/ 2xx=Info。混ぜると「エラーが多すぎて誰も見ない」状態になる
- **`slog.LogAttrs`**: 属性を型付きで渡す最速の書き方（`slog.String` / `slog.Int`）。可変長 any の `slog.Log` よりアロケーションが少ない
- **ログインジェクション対策が構造的に解決**: 属性方式ではフォーマット文字列に値を埋めないため、改行入りパスで偽のログ行を捏造できない。#29 で入れた `strconv.Quote` は不要になり削除（gosec も再発せず）
- **不正な LOG_LEVEL で起動を止めない**: 「間違っていても安全に動く設定」は既定値へフォールバック（DATABASE_URL の fail fast とは扱いを分ける・#28の基準）

### ✅ベストプラクティス

- `log.Fatal` は slog の形式に乗らないため、`slog.Error` + `os.Exit(1)` のヘルパーに置き換える
- エラー応答は err が nil でもログに残す（監視で 4xx/5xx の件数を追えるようにする）

### ⚠️アンチパターン

- メッセージ文字列に値を連結する（`fmt.Sprintf("user %d failed", id)`）→ 検索・集計ができない
- すべて Error レベルで出す／ログをファイルに書いて自前ローテーション

### 理解度チェック

- [ ] 構造化ログが平文より優れる点を「検索・集計」の観点で説明できる
- [ ] アプリがログをファイルに書かない理由を言える
- [ ] 4xx と 5xx でレベルを分ける理由を言える
- [ ] 属性方式がログインジェクションを防ぐ仕組みを説明できる

## Phase1 #50: リクエストID（相関ID）とエラーの突き合わせ

### 何をした

`requestIDMiddleware` でリクエストごとに一意のIDを発行し、context・レスポンスヘッダ（X-Request-ID）・アクセスログ・エラーログ・エラーレスポンスボディの5か所に伝播。`writeError` に ctx を渡す形へ変更（27箇所）し、認証済みなら user_id もログに残す。

### 概念

- **相関ID（Correlation ID）**: 1回のリクエストで発生する複数のログを1本の線で束ねるID。同時アクセス時に「どのエラーがどのリクエストか」を判別できる。分散システムでは複数サービス横断で追う仕組み（トレーシング）の入口
- **受信ヘッダの尊重**: `X-Request-ID` が来ていれば引き継ぐ（ロードバランサ/フロント/上流サービスが採番したIDでつながる）。無ければ自分で採番
- **crypto/rand による採番**: UUIDライブラリを足さず 16バイト→hex 32文字。相関IDに必要なのは一意性だけで、UUIDの版番号・書式は不要
- **外部入力の検証**: X-Request-ID は誰でも送れる値をログとヘッダに載せる経路。長さ64・英数字/-/_ に制限して汚染・インジェクションを防ぐ（信頼できない入力は境界で検証）
- **`slog.Logger.With` の子ロガー**: 属性を固定したロガーを作り、以降のログに自動で付与。呼び出し側が毎回IDを渡さなくてよい
- **ユーザーへの相関IDの提示**: エラーレスポンスに request_id を含めると、「この画面にこのIDが出た」という報告だけでログを特定できる（実務のサポート導線）
- **ミドルウェアの順序**: requestID を最外に置く（内側だとアクセスログがIDを取得できない）

### ✅ベストプラクティス

- ログ・レスポンス・ヘッダの3方向に同じIDを流す（内部調査と外部報告の両方が繋がる）
- 認証済みリクエストは user_id も添える（誰の操作で失敗したかの手がかり）
- 引数に `context.Context` を先頭で受ける関数シグネチャに揃える（Goの慣習）

### ⚠️アンチパターン

- 外部から来たIDを無検証でログ・ヘッダに載せる
- リクエストIDを毎回手で引き回す（context + 子ロガーで自動化する）
- 相関IDを付けずに「エラーログだけ」を眺める（同時アクセス時に無力）

### 理解度チェック

- [ ] 相関IDが無いと何が困るか、同時アクセスの例で説明できる
- [ ] X-Request-ID をサニタイズする理由を言える
- [ ] requestID ミドルウェアを最外に置く理由を言える

## Phase1 #51: panic recovery ミドルウェア

### 何をした

`recoverMiddleware` を追加し、ハンドラ内の panic を回復してスタックトレース・相関ID付きで Error ログに記録し、500 を返す。`httptest` によるテスト4ケースを追加。

### 概念

- **panic / recover**: Goの panic は例外ではなく「回復不能な異常」の通知。`recover()` は **defer した関数の中でしか効かない**（panicで巻き戻る途中に実行されるため）
- **なぜ自前で捕まえるか**: net/http も panic を捕捉するが、標準エラーへ素で出るだけで構造化ログにも相関IDにも乗らない。自前で捕まえて `slog.Error` にすることで、監視・アラート・調査の導線に統合される
- **`http.ErrAbortHandler` の特別扱い**: クライアント切断時に net/http 自身が投げる正常系の合図。捕まえるとログが汚れるため再パニックで素通しする（標準の作法）
- **`debug.Stack()`**: panic 発生時点のスタックトレースを取得。「どこで落ちたか」が分かる唯一の手がかり
- **panicの内容をクライアントに返さない**: 変数の中身やコード構造が漏れるため、レスポンスは定型文の500のみ（ログには全部残す）
- **ミドルウェアの配置**: requestID（外・IDは常に必要）→ recover → logging（内・500になった結果をアクセスログに残す）。recoverをloggingの外に置くとpanic時のアクセスログが消える
- **`httptest`**: 実サーバーを起動せずミドルウェア/ハンドラを検証できる標準パッケージ。`httptest.NewRequest` + `NewRecorder` で組み立て、`ServeHTTP` を直接呼ぶ

### ✅ベストプラクティス

- panic は握りつぶさず必ず記録する（バグの存在を隠さない）
- テストで「panicしても落ちない」ことを保証する（回帰テストとして永続化・一時的な検証ハンドラをコミットしない）
- 秘密が漏れないことをテストで固定する（TestRecoverMiddlewareHidesPanicDetail）

### ⚠️アンチパターン

- `recover()` を defer の外で呼ぶ（何も起きない）／panic を回復して何もログに残さない
- panic の値をそのままレスポンスに含める（情報漏えい）
- ErrAbortHandler まで捕まえて「エラー」として記録する（正常な切断がノイズになる）

### 理解度チェック

- [ ] recover が defer の中でしか効かない理由を説明できる
- [ ] net/http 標準の回復では不十分な理由を言える
- [ ] recover を logging の外側に置くと何が起きるか言える

## Phase1 #9: 案件CRUD（認可・パスパラメータ・N+1回避・ページネーション）

### 何をした

projects テーブルと、POST /projects（企業のみ）・GET /projects（一覧）・GET /projects/{id}（詳細）を実装。認可ミドルウェア `requireRole` を追加。

### 概念

- **認証と認可の分離**: 認証=あなたは誰か（失敗401・requireAuth）／認可=それをしてよいか（失敗403・requireRole）。ミドルウェアを分けて `requireAuth(requireRole(role)(handler))` と重ね掛けする
- **ロールはトークンでなくDBから引く**: JWTに入れれば1クエリ節約できるが、発行後にロールが変わってもexpまで反映されない。認可は「今の権限」で判断する
- **N+1問題**: 一覧のループ内で親（会社）を1件ずつ引くと 1+N クエリになる。**JOINで1回**にまとめる。個々のクエリは速いためスロークエリログに出ず発見が遅れる。レビュー観点は「ループ内に db.Query があったら赤信号」
- **Go 1.22 のパスパラメータ**: ルート `"GET /projects/{id}"` の値を `r.PathValue("id")` で取得（フレームワーク不要になった理由のひとつ）
- **LIMIT/OFFSET ページネーション**: 上限をクランプしないと `limit=100000` で全件取得される。深いページで OFFSET が遅くなる問題は、件数が増えたら seek 方式（`WHERE created_at < 前ページ末尾`）へ移行
- **一覧レスポンスは配列を包む**: `{"projects":[...],"limit":n,"offset":n}`。後からページング情報（総件数・次ページ有無）を足せる
- **`rows.Err()`**: ループ後に必ず確認する。ループ中に起きた通信エラーは `rows.Next()` が false を返すだけで、Err() を見ないと成功と区別できない
- **存在しないと未公開を区別せず404**: 下書きの存在を外部に漏らさない（列挙攻撃対策の考え方は login の同一401と同じ）
- **`scanner` インターフェース**: `*sql.Row` と `*sql.Rows` の共通部分（Scanのみ）を最小インターフェースで抽象化し、一覧と詳細でスキャン処理を共有する

### ✅ベストプラクティス

- リクエストに company_id を定義しない（トークン→userID→companies で引く＝IDORの余地を作らない）
- DBのCHECK制約と同じルールをアプリ側でも検証し、意味のあるメッセージを返す（DBは最後の砦・アプリは親切な案内）
- エラー文言は「次に何をすればよいか」を書く（例: 先に企業プロフィールを登録してください）

### ⚠️アンチパターン

- ループ内での単発クエリ（N+1）／limit の上限を設けない／`rows.Err()` を見ない
- 認可をハンドラ内に散らす（ミドルウェアで宣言的に表現する）

### 理解度チェック

- [ ] 401と403の使い分けを説明できる
- [ ] N+1が「個々は速いのに全体が遅い」理由を説明できる
- [ ] LIMIT/OFFSET の限界と seek 方式への移行条件を言える
- [ ] 未公開の案件を404にする理由を言える

## Phase1 #83: 応募API（エラーコードの設計と errors.As）

### 何をした

`POST /projects/{id}/applications` を実装。**認可をミドルウェアで完結**させ、二重応募は**UNIQUE違反を拾って409**で返す形にした。

### 概念

- **`errors.As`**: エラーの連鎖（`%w` でラップされた中身）をたどり、**指定した型のエラーを取り出す**。`errors.Is` が「値が同じか」なのに対し、`As` は「その型か」を見て変数に代入する
  ```go
  var pgErr *pgconn.PgError
  return errors.As(err, &pgErr) && pgErr.Code == "23505"
  ```
- **SQLSTATE**: `23505`（一意制約違反）は**SQL標準で定義されたコード**。`err.Error()` にメッセージが含まれるかで判定すると、DBのバージョンやロケール変更で静かに壊れる
- **ステータスコードの使い分け**（今回の設計判断）:

  | 状況               | コード  | 理由                                        |
  | ------------------ | ------- | ------------------------------------------- |
  | 志望動機が空       | 400     | 入力値そのものが不正                        |
  | 案件が無い・未公開 | 404     | **存在を漏らさない**（403だと存在がバレる） |
  | 企業ロールで応募   | 403     | 認証は通るが権限が無い                      |
  | プロフィール未登録 | 400     | 入力は正しいが前提条件が未達                |
  | **二重応募**       | **409** | 入力も権限も正しいが**現在の状態と衝突**    |

  → 409 は「リソースの現在の状態と矛盾」を表す。状態遷移APIの不正遷移でも同じ考え方を使う

- **認可をミドルウェアで完結させる**: 「自社案件への応募を拒否」という要件を、ハンドラの条件分岐ではなく `requireRole(roleTalent)` で満たした。**判定を書かずに要件が満たされる**形は、分岐で解くより壊れにくい（ただし意図はテストで固定する必要がある）
- **`SELECT EXISTS (...)`**: 存在確認だけなら行の中身を運ばない
- **lint が YAGNI を強制する**: 「#84 で使うから」と status 定数を先に書いたら `unused` で全部指摘され、削除した。使うときに足す

### ✅ベストプラクティス

- エラー判定に**メッセージ文字列を使わない**（型・コードで判定）
- 一意性違反はDBに判定させ、業務上の意味（409）に翻訳する
- `sql.ErrNoRows` を500ではなく**業務上の状態**に翻訳する（「先にプロフィールを登録してください」）
- 未公開リソースは404（403だと存在が推測できる）

### ⚠️アンチパターン

- `strings.Contains(err.Error(), "duplicate")`
- リクエストボディの ID を信用する（IDOR）
- 使う予定があるからと未使用の定数を先に書く

### 理解度チェック

- [ ] `errors.Is` と `errors.As` の使い分けを言える
- [ ] 二重応募が400ではなく409である理由を言える
- [ ] 未公開案件に404を返す理由を言える

## Phase1 #84: 状態遷移表と楽観ロック（状態機械①）

### 何をした

`api/application_status.go` に**遷移表**を作り、`PATCH /applications/{id}/status` を実装した。遷移の可否判定はコード上の1箇所に集約し、更新は**楽観ロック**で競合を検知する。

### 遷移表（状態機械①）

```
applied ─┬─[企業:オファー]→ offered ─┬─[人材:承諾]→ accepted ★成立
         │                          ├─[人材:辞退]→ declined
         │                          └─[人材:取下げ]→ withdrawn
         ├─[企業:見送り]→ rejected
         └─[人材:取下げ]→ withdrawn
```

```go
var applicationTransitions = map[statusTransition]string{
    {from: applied, to: offered}:   roleCompany,
    ...
    {from: offered, to: accepted}:  roleTalent,  // ★ accepted はこの1行だけ
}

func canTransition(from, to, role string) bool {
    actor, ok := applicationTransitions[statusTransition{from: from, to: to}]
    return ok && actor == role
}
```

### 概念

- **状態遷移表を単一の真実にする**: 判定を if/switch でハンドラに書くと**動きはする**が、後から別の経路（一括操作API等）を足した人が条件を書き写して1箇所間違えると、**その経路からだけ不正な状態になれる**。表に集約すれば、新しいエンドポイントが `canTransition` を呼ぶ限り仕様が守られる
- **構造体を map のキーにする**: 比較可能な構造体はキーにできる。`map[string]map[string]string` の入れ子より、`{from, to} → 実行者` のほうが**表がそのままコードの見た目になる**
- **ホワイトリスト方式**: 終端状態（accepted/rejected/withdrawn/declined）を禁止する記述は書いていない。**from として表に現れないので引いた時点で false** になる。禁止リストは新しい状態を足したときに書き漏らす
- **ダブルオプトインが表に埋まっている**: `accepted` への行が「offered から・人材のみ」の1つだけ ＝ 企業は構造的に成立させられない。**仕様が目視で確認できる**
- **楽観ロック**: 事前にロックを取らず、`WHERE id = $2 AND status = $3`（**読み取り時の状態**）を条件に含めて更新する。他者が先に変更していたら0行更新 → `RETURNING` が空 → `sql.ErrNoRows` → **409**
  - これが無いと: 企業が「applied」を読む → 人材が取り下げる → 企業の UPDATE が通り、**取り下げ済みの応募にオファーが成立する**
  - 悲観ロック（`SELECT ... FOR UPDATE`）と違い待ちが発生しないため、競合が稀なケースでは有利
- **`RETURNING`**: 更新と同時に更新後の行を取得できる（再SELECT不要・原子的）。`RowsAffected() == 0` でも競合検知はできるが、レスポンス用の再取得が必要になる
- **プレースホルダは値専用**: `SET $1 = now()` のように**列名には使えない**。実行者側の列だけ更新するため `CASE WHEN $4 = 'company' THEN now() ELSE company_acted_at END` で選ぶ。`"SET " + role + "_acted_at"` の連結は今回は安全な値だが、**「SQLに文字列を連結しない」に例外を作らない**
- **認可の3層**: 認証（requireAuth＝誰か）→ **所有**（取得クエリのJOIN/WHEREに自分のIDを入れる）→ **遷移可否**（canTransition＝今それをしてよいか）
- **所有チェックはWHEREに埋め込む**: 「取得してから `if app.CompanyID != mine` で弾く」形は、**1箇所書き忘れると権限昇格**になる。WHEREに入れれば他人の行はそもそも返らない（返らなければ404＝存在を漏らさない）
- **入口で塞ぐ認可 vs 操作ごとの認可**: 応募API(#83)は `requireRole(roleTalent)` で企業を入口から締め出したが、状態更新は**両ロールが使う**ため requireRole を付けない。「企業はオファーだけ・人材は承諾だけ」という粒度はミドルウェアでは表現できない

### ✅ベストプラクティス

- 状態遷移は**表で定義し、判定関数を1つだけ**用意する
- 許可を列挙し、残りは自動的に禁止（ホワイトリスト）
- 更新は楽観ロックで競合を検知し、「画面を更新してください」と伝える
- 所有チェックは取得クエリに埋め込む
- 安全な値でもSQLに文字列を連結しない

### ⚠️アンチパターン

- 遷移条件を if/switch でハンドラに散らす
- 禁止リストで状態を守る
- `WHERE id = $1` だけで更新する（読み取り→更新の競合を素通し）
- 他人のリソースに403（存在が漏れる）

### 理解度チェック

- [ ] 終端状態を禁止する記述が無いのに遷移できない理由を説明できる
- [ ] 楽観ロックが無いと何が起きるか、2リクエストの流れで説明できる
- [ ] 所有チェックを後から判定する形の危険性を言える
- [ ] 遷移表を見て「企業は成立させられない」と読み取れる

## Phase1 #85: 視点別の一覧API（N+1回避・taint analysis・境界の型変換）

### 何をした

応募一覧を**視点別**に2本実装した（人材＝自分の応募履歴 / 企業＝自社案件への応募者）。あわせて `talents.display_name` を追加し、企業が応募者を識別できるようにした。

### 概念

- **同じテーブルに対する2つの読み取りモデル**: 書き込みは1つでも、読み取りは用途ごとに最適な形にしてよい（CQRS の入口）。無理に共通化すると**どちらにとっても使いにくい中間物**ができる

  |              | 人材の応募履歴               | 企業の応募者一覧                  |
  | ------------ | ---------------------------- | --------------------------------- |
  | 結合         | projects, companies          | talents                           |
  | 絞り込み     | `t.user_id`（自分の応募）    | `a.project_id`（指定案件）        |
  | 所有チェック | **結合に埋め込む**           | **先に別クエリで確定**            |
  | 使われる索引 | `applications_talent_id_idx` | `applications_project_status_idx` |
  | 返す情報     | 案件名・企業名               | 表示名・スキル・意思表示の時刻2つ |

- **N+1の回避**: 一覧20件で関連を都度引くと 1+20+20=41回。JOIN なら1回。**実行計画（EXPLAIN）で JOIN 1回になっていることを確認する**
- **所有チェックの2つの形**:
  - _結合に埋め込む_（人材側）: `JOIN talents t ... WHERE t.user_id = $1`。他人の行に到達できない。表示用の結合が認可も兼ねる
  - _先に確定させる_（企業側）: 他社の案件IDを指定したことを**明示的に検知して404**にしたいため。一覧クエリに埋めると「応募0件の自社案件」と区別がつかず、空配列が返るだけになる
- **taint analysis（汚染解析）**: gosec の G701 は「ユーザー入力に触れた値がSQL実行関数まで届く経路」を静的に追跡する。**値をプレースホルダに渡していても、入力によってSQL文字列が変わる形（`if status != "" { sql += ... }`）は指摘される**
  - 対処は `#nosec` ではなく**設計で解く**: `AND ($2 = '' OR a.status = $2)` と書けば**SQLは完全な定数**になり、連結の余地が消える。`fmt.Sprintf` でのプレースホルダ番号計算も不要になりコードが短くなった
  - ただし条件が多い場合（projects.go の6条件）は `($n = '' OR ...)` を並べると**プランナが索引を選びにくくなる**ため動的組み立てが妥当。**条件が1つならこの書き方、多いなら動的**
- **API設計でセキュリティを担保する**: 応募者一覧に `users.email` は**含めない**（JOINすれば取れるが取らない）。連絡先マスキングは事業の生命線であり、**APIが返さなければフロントの実装ミスでも漏れない**
- **DB境界の型をAPI境界の型に変換する**: `sql.NullTime` をそのままJSONにすると `{"Time":...,"Valid":true}` と内部構造が漏れる。`*time.Time` に変換して null を表現する（`time.Time` で受けると NULL が西暦1年になる）
- **既存テーブルへの NOT NULL 列追加**: 既存行があるため `DEFAULT ''` が必要。「DBは空を許す／アプリで必須」の**段階的な必須化**（本番運用中なら、既存行を埋めてから `SET NOT NULL` する2段階が定石）
- **シードは安定キーで結合する**: `INSERT ... SELECT ... FROM users JOIN (VALUES ...) ON email` の形にして、**連番IDを決め打ちしない**（採番がずれても壊れない）

### ✅ベストプラクティス

- 一覧の表示に必要な関連は**JOINで一度に取る**／索引が効いているか実行計画で確認する
- **返す必要のない個人情報は最初からSELECTしない**
- lint の指摘は**抑制する前に設計で解けないか考える**（今回はコードが短くなった）
- 視点が違うなら**型もSQLも分ける**

### ⚠️アンチパターン

- ループ内でクエリを発行する（N+1）
- `#nosec` で機械的に黙らせる
- 「あとでフロントで隠す」前提で個人情報を返す
- NULL可能な時刻を `time.Time` で受ける
- シードで `VALUES (1, ...)` とIDを直書きする

### 理解度チェック

- [ ] N+1 が起きる書き方と JOIN 1回の違いを件数で言える
- [ ] taint analysis が何を見て指摘したのか説明できる
- [ ] `($2 = '' OR col = $2)` の利点と、条件が多いときに使わない理由を言える
- [ ] 人材側と企業側で所有チェックの形が違う理由を言える
- [ ] `sql.NullTime` を `*time.Time` に変換する理由を言える

## Phase1 #97: 掲載状態の遷移と内容の編集

### 何をした

案件の**内容の編集**（`PUT /projects/{id}`）と**掲載状態の変更**（`PATCH /projects/{id}/status`）を、責務ごとに2本のエンドポイントとして実装した。**遷移表を持つ機能としては2つ目**（1つ目は応募）。

> **番号について**: 番号付きの状態機械（①選考 / ②契約 / ③決済）は**取引の進行**を表す本筋。
> 掲載状態は案件の公開範囲を切り替える**補助的なもの**なので、番号は振らない。

### なぜエンドポイントを2本に分けたか

当初 Issue は `PUT` 1本の想定だったが、以下の理由で分けた。

- **「保存」と「公開」は別の意思決定**。文言を直しただけで意図せず公開されるのは事故
- 一覧から状態だけ変えたいとき、PUT 1本だと**全フィールドを送り直す必要がある**（PUTは全体置換なので、送らない項目は空になる）
- 状態変更のハンドラが**常に遷移表を通る**（「statusが変わったか」の分岐が不要）
- **M2（契約成立時に案件を自動で募集終了にする）で、状態変更の関数をそのまま呼べる**

### 2つの遷移表の比較

|          | ①応募 `applications`（状態機械①）                  | 案件の掲載状態 `projects`       |
| -------- | -------------------------------------------------- | ------------------------------- |
| 表の型   | `map[statusTransition]**string**`（ロール）        | `map[statusTransition]**bool**` |
| なぜ     | 企業と人材で実行できる操作が違う                   | **常に所有企業だけ**が操作する  |
| 判定関数 | `actor, ok := m[k]; return ok && actor == role`    | `return m[k]`（**1行**）        |
| 終端状態 | あり（accepted / rejected / withdrawn / declined） | **なし**（closed からも戻れる） |
| 遷移数   | 6                                                  | 4                               |

- **`statusTransition` 構造体は共用**し、**値の型で差を表す**。同じ「状態機械」でも必要な情報はドメインによって違う
- 1本目をコピーして値を全部 `roleCompany` にしても動くが、**「ロールで分岐する必要がない」という設計上の事実が表現されない**。型は最も短いドキュメント
- `map[K]bool` は存在しないキーに**ゼロ値 `false`** を返すので、`v, ok :=` の2段階が要らない

### 概念

#### 「できないようにする」より「できる形が存在しない」

status を更新させない方法は3つあり、強度が違う。

| 方法                             | 強度                                |
| -------------------------------- | ----------------------------------- |
| バリデーションで弾く             | 弱い（弾き忘れる）                  |
| リクエスト型から `Status` を消す | 中（型で防げるが、SQLは書ける）     |
| **SET句に書かない**              | **強い（更新するSQLが存在しない）** |

同じ発想が所有チェックにも効く。「判定する」のではなく「他社の行にはそもそも到達しない」形にする（#83 の UNIQUE 制約から一貫）。

#### `UPDATE ... FROM` — 所有チェックを更新文に埋め込む

```sql
UPDATE projects p
SET title = $1, ...
FROM companies c
WHERE p.id = $8 AND c.id = p.company_id AND c.user_id = $9
RETURNING p.id, ..., c.name, ...
```

- PostgreSQL で「更新対象を別テーブルと結合して絞り込む」構文
- 他社の案件は**1行も更新されず** `RETURNING` が空 → `sql.ErrNoRows` で 404 に変換
- **取得 → 判定 → 更新の3段階は書かない**（隙間があるうえ、判定を1箇所書き忘れたら権限昇格になる）
- 更新していない `p.status` も RETURNING に含める（クライアントは保存後の状態を知る必要がある）

#### バリデーションは用途で分ける

作成は初期状態を指定できるので status も検証するが、更新は status を扱わない。
`validateProject`（作成用）が `validateProjectContent`（共通）を呼ぶ形にして、**内容の検証ルールは1箇所**に保つ。

### テーブル駆動テストの網羅を「検算」する

テーブル駆動テストの弱点は **「ケースを書き忘れても気づけない」** こと。全ケースがPASSしていても、書いていないケースは検証されない。

```go
// 状態を増やしたときにケースの追加を忘れると、網羅していないのに通ってしまう
if want := len(projectStatuses) * len(projectStatuses); len(tests) != want {
    t.Errorf("ケース数 = %d, want %d（状態を追加したらテストケースも追加すること）", len(tests), want)
}
```

- 状態の数から**期待されるケース数を計算**し、実際のケース数と突き合わせる
- 将来 `archived` を足すと `3×3=9` が `4×4=16` になり、**テストが「追加してください」と落ちて教えてくれる**

**ホワイトリストであること自体もテストで固定する**:

```go
// 表の値が false の項目があると「登録されているのに不許可」という紛らわしい状態になる
for transition, allowed := range projectTransitions {
    if !allowed { t.Errorf("...許可しない遷移は表から削除すること") }
}
```

- 許可された遷移の数（4）も検査する。遷移を足すときにこの数字も更新することになり、**レビューで「本当に追加していいか」を必ず考える**

### ✅ベストプラクティス

- 更新してはいけない列は**SQLに書かない**（バリデーションに頼らない）
- 所有チェックは **UPDATE/DELETE の WHERE に埋め込む**
- テーブル駆動テストには**網羅の検算**を入れる
- 状態遷移は**ホワイトリスト**で定義し、それをテストでも固定する

### ⚠️アンチパターン

- 1本目の状態機械を思考停止でコピーする（違いが型に表現されない）
- `map[...]bool` に `false` を登録する（禁止の表現が2種類になる）
- 取得 → 所有を判定 → 更新（隙間があり、判定漏れが権限昇格になる）
- テストケースを書き忘れたまま「全部PASSしている」と安心する

### 理解度チェック

- [ ] 応募の遷移表が `map[...]string`、案件が `map[...]bool` である理由を言える
- [ ] status を更新させない3つの方法の強度の違いを言える
- [ ] `UPDATE ... FROM` で所有チェックを埋め込む利点を言える
- [ ] テストケース数の検算が防いでいる事故を言える

## Phase2 #104: 契約の状態遷移（状態機械②）— 遷移表3本目の比較

### 何をした

契約の遷移表と `PATCH /contracts/{id}/status` を実装し、**50通り（5状態 × 5遷移先 × 2ロール）を網羅**するテストを書いた。あわせて結果を確認するための `GET /me/contracts/{id}` を用意した。

### 3本の遷移表の比較

|              | ①応募                          | 案件の掲載状態    | **②契約**                             |
| ------------ | ------------------------------ | ----------------- | ------------------------------------- |
| 値の型       | `map[..]**string**`（1ロール） | `map[..]**bool**` | `map[..]**[]string**`（ロールの集合） |
| なぜ         | 遷移ごとに実行者が1人          | 常に所有企業だけ  | **中止だけが2ロール**から実行できる   |
| 判定         | `ok && actor == role`          | `return m[k]`     | `ok && slices.Contains(actors, role)` |
| **戻る遷移** | なし                           | あり（再募集）    | **あり（差し戻し）**                  |
| 終端         | あり                           | なし              | あり                                  |
| 遷移数       | 6                              | 4                 | 7                                     |

- **`statusTransition` 構造体は3本とも共用**し、**値の型で差を表している**
- 7行のうち4行は要素1つの配列になるが、**中止の3行のために型を揃える必要がある**——この理由をコメントに書かないと「なぜ全部配列？」と思われる

### 概念

#### 「誰ができるか」は表から読めるが、「なぜその人か」は読めない

各行にコメントを添えた。特に重要なのは検収:

```go
// 検収の可否は企業が判断する。人材が自分で完了させられないことが、
// 「成果を確認してから完了する」という検収の意味そのもの
{from: reviewing, to: completed}: {roleCompany},
```

ここが崩れると**人材が自分で「完了」にして報酬を確定できる**。表の形だけでは、この行が仕組みの根幹だと分からない。

#### 戻る遷移があると「単調に進む」前提が壊れる

`reviewing → working`（差し戻し）はこのプロジェクトで初めての**時間を巻き戻す遷移**。何度でも往復しうる（検収→差し戻し→検収…）。

**`COALESCE` で開始日を守る**:

```sql
started_at = CASE WHEN $1 = 'working' THEN COALESCE(started_at, now()) ELSE started_at END
```

- `COALESCE(a, b)` は「a が NULL なら b」。初回は `now()`、差し戻し後は**既存値のまま**
- **差し戻しは再開であって、開始し直しではない**。単純に `THEN now()` と書くと、差し戻しのたび開始日が後ろにずれる
- この注意は `updateContractStatus` だけでなく**遷移表のコメントにも書いた**（そこを先に読むため）

#### 前のIssueの設計が効く

所有チェックがロールで変わる（企業・人材の両方が当事者）が、**#103 で `company_id` / `talent_id` を契約に直接持たせた**ため、どちらも**JOIN 1回**で済む。持たせていなければ企業側は `contracts → applications → projects → companies` と3回結合が必要だった。

#### 既存ルールを適用しない判断も記録する

#85 で「視点が違えば型もSQLも分ける」と決めたが、契約では**分けなかった**。

|                  | 応募             | 契約               |
| ---------------- | ---------------- | ------------------ |
| 段階             | **相手を選ぶ**   | **一緒に進める**   |
| 人材が見たいもの | 案件名・企業名   | 合意内容と進み具合 |
| 企業が見たいもの | 応募者名・スキル | 合意内容と進み具合 |
| 判断             | 分ける           | **分けない**       |

- ルールの目的は「使う側が判断に迷わないこと」。中身がほぼ同じ型を2つ作ると、むしろ迷わせる
- **ルールに従わない判断をしたら、理由をコメントの一番上に書く**（後任が「ルール違反では？」と思わないように）
- ロールで返す項目も変えない。**両方返して使う側が選ぶ**ほうが、画面側に分岐が生まれない

#### 表示のための JOIN が所有チェックにも使える

相手の名前を出すために `companies` / `talents` を結合しているので、所有チェックの条件（`co.user_id = $2`）を足すだけで済む。**結合が一石二鳥**になっている。

### テストの書き方：50ケースを7行から生成する

手で50ケース書くのは現実的でないため、**期待値を「許可リスト」として宣言し、ループで組み合わせを生成**する。

```go
allowed := map[statusTransition][]string{ ... 7行 ... }
for _, from := range contractStatuses {
    for _, to := range contractStatuses {
        for _, role := range roles {
            want := (allowed に含まれるか)
```

- テスト名を `active→working/talent` のように組み立てると、失敗時にどの組み合わせか即座に分かる
- 最後に**組み合わせ数を検算**する（状態を増やしたときの書き漏れを検出）

**振る舞いのテストには弱点がある**: 期待値をテスト側の表から導いているため、**実装とテストの両方を同時に書き換えると気づけない**。そこで表そのものを検査する2つ目のテストを追加した:

- 許可された遷移の**数**（7）を固定 → 遷移を足すとこの数字の更新が必要になり、**レビューで必ず目に入る**
- **実行者が空の行が無いこと**（表にあるのに誰も実行できない、という紛らわしい状態を禁じる）
- **終端状態が from として現れないこと**（完了した取引が後から覆らない）

### ✅ベストプラクティス

- 遷移表には**「なぜその人か」**を書く
- **他ファイルへの注意も、読まれる場所に書く**（`started_at` の警告を遷移表に）
- 網羅テストは**期待値を宣言的に**書き、ループで生成する
- **「〜が無いこと」を性質として検査する**
- 既存ルールを適用しない判断は、理由をコメントの一番上に

### ⚠️アンチパターン

- 「なぜ配列なのか」を書かずに `[]string` にする
- 差し戻しで `started_at` を上書きする
- 50ケースを手で列挙する（書き漏らす・保守できない）
- ルールを機械的に適用して中身が同じ型を量産する

### 理解度チェック

- [ ] 3本の遷移表の値の型が違う理由をそれぞれ言える
- [ ] `reviewing → completed` を企業だけに限っていることが守っているものを言える
- [ ] `COALESCE(started_at, now())` が防いでいる問題を言える
- [ ] 振る舞いのテストの弱点と、2つ目のテストが補っているものを言える
- [ ] 応募では型を分け、契約では分けなかった理由を言える

## Phase3 #116: 連絡先マスキング — 完璧を目指さない設計

### 何をした

`messages` テーブルと、メッセージ本文から連絡先を伏せる処理を実装した。**このサービスの生命線**（直接取引を防げないと、手数料が入らないだけでなくトラブル時の保護がすべて効かなくなる）。

### この機能の目標設定

**完璧な検出は不可能**である。「ゼロキュウゼロのイチニイ…」と書かれたら検出できないし、全角・記号の混入・分割送信など抜け道はいくらでもある。

目指すのは **「簡単にはできなくする」**——コピペで連絡先を送れないようにすることで大半の直接取引を防ぐ。抜け道を探す相手には、**規約と原文の保存（監査）**で対処する。

**この目標設定をコメントに書かないと、後任が「抜け道があるのはバグだ」と判断して正規表現を強化し、誤検知だらけにする。**

### トレードオフの向きを決める

検知漏れ（連絡先が通る）と誤検知（正常な文が伏せられる）は**両立しない**。

このプロジェクトでは **誤検知を減らす方向に倒す**——「10時から18時」「1-2週間」が伏せられて正常なやり取りが阻害されるほうが実害が大きいため。

判断に迷ったとき（「この表記も拾うべきか？」）の基準になる。

### 概念

#### 正規表現で抽出、判定はコードで

正規表現だけでは「区切り記号を無視した数字の合計桁数」を表現できない。無理に書くと読めない代物になる。

```go
phonePattern.ReplaceAllStringFunc(body, func(candidate string) string {
    if !looksLikePhoneNumber(candidate) {
        return candidate   // 条件に合わなければ元のまま返す（伏せない）
    }
    return maskedPlaceholder
})
```

- **`ReplaceAllStringFunc`**: マッチ部分を関数で加工できる。「マッチしたが条件に合わないので元のまま」が書ける
- 抽出と判定を分けると、それぞれが単純になり、**「なぜこの文字列は電話番号ではないのか」をテストで説明しやすい**

#### ドメイン知識を条件に落とす

日本の電話番号は **0 始まりで10〜11桁**。この制約で誤検知を防ぐ:

| 文字列               | 除外される理由         |
| -------------------- | ---------------------- |
| `2026-08-07`（日付） | **2始まり**（0でない） |
| `1-2週間`            | 2桁（10〜11桁でない）  |
| `10時から18時`       | 4桁                    |
| `5000-8000円`        | 8桁                    |

**汎用的な正規表現より、ドメイン知識を使ったほうが正確**になる。

#### 処理順序に意味がある

```go
masked = urlPattern.ReplaceAllString(...)      // ① URL
masked = emailPattern.ReplaceAllString(...)    // ② メール
masked = maskPhoneNumbers(masked)              // ③ 電話
```

URLの中にメールらしき文字列や数字列が含まれることがある（`https://example.com/user@id/09012345678`）。
メールを先に処理すると `https://example.com/[伏せ字]/...` という中途半端な結果になるため、**URLを丸ごと先に伏せる**。

#### 伏せ字は「何が起きたか」を伝える文言に

`****` だと文字化けやバグと区別がつかない。`[連絡先は表示できません]` のように**伏せ字自身が説明する**。

#### スキーム無しのURLは検出しない

`example.com` まで拾うと「詳細は example.com の資料をご覧ください」のような正常な文が伏せられる。
`https://` `http://` 付きだけに絞る（**誤検知を減らす方針**の適用）。

### テーブル設計

#### 原文と表示用を両方持つ

| 列            | 存在理由                                                                                      |
| ------------- | --------------------------------------------------------------------------------------------- |
| `body`        | **監査・紛争時の証跡**（「規約違反があった」と主張するには原文が要る）。**APIからは返さない** |
| `masked_body` | 表示用。**保存時に一度だけ生成する**                                                          |
| `masked`      | 伏せ字が入ったか。UIで理由を伝えるために使う                                                  |

#### 表示のたびに計算しない理由

正規表現は今後改善する。表示のたびに計算すると**過去のメッセージの見え方まで変わる**:

```
08-07: 「連絡先は 090-1234-5678 です」→ 検知漏れで表示された
09-01: 正規表現を改善
09-02: 同じメッセージが伏せ字になっている
```

紛争時に「相手に何が見えていたか」を再現できなくなる。**保存時に確定させれば、そのときの判定結果が記録として残る**（表示のたびの負荷もなくなる）。

#### 送信者をロールで持つ

`user_id` ではなく `sender_role`（company / talent）。契約が当事者を持つため、**ロールが決まれば送信者が一意に定まる**。
`user_id` を持つと「契約の当事者でない user_id が入る」余地が生まれるが、ロールならその可能性が無い。

#### 索引は昇順

会話は上から下へ読むので `(contract_id, created_at)` の昇順。稼働報告（#105）は新しい週から見るので DESC だった。**同じ「一覧」でも並び順は用途で決まる**。

### テストの設計

**守るものごとに分けた**:

| テスト                                       | 守るもの                           |
| -------------------------------------------- | ---------------------------------- |
| `TestMaskContactsDetects`（13ケース）        | **事業モデル**（直接取引の防止）   |
| `TestMaskContactsDoesNotOverMask`（9ケース） | **正常なやり取り**（誤検知の防止） |
| `TestMaskContactsKeepsSurroundingText`       | **文脈**（連絡先だけを伏せる）     |
| `TestLooksLikePhoneNumber`（6ケース）        | **判定基準**（桁数の境界）         |

- **検出のテストだけでは誤検知は見つからない**。「伏せられること」と「伏せられないこと」は別のテストで固定する
- **判定関数を単体でもテストする**理由: `maskContacts` 経由だと「正規表現で候補にならなかった」のか「候補にはなったが桁数で除外された」のかが区別できない

### ✅ベストプラクティス

- **目標設定とトレードオフの向きをコメントに書く**（後任が判断できる）
- 正規表現は**抽出まで**にして、複雑な判定はコードで
- **ドメイン知識を条件に落とす**（日本の電話番号は0始まり10〜11桁）
- 伏せ字は**何が起きたか伝わる文言**に
- **記録として残すものは、判定時の結果を保存する**

### ⚠️アンチパターン

- 完璧を目指して正規表現を複雑にする（誤検知で実害が出る）
- `****` のような無意味な伏せ字（バグと区別がつかない）
- **検出のテストだけ書く**（誤検知は検出テストでは見つからない）
- 表示のたびにマスキングを計算する（過去の表示が変わる）

### 理解度チェック

- [ ] 「完璧を目指さない」という目標設定が防いでいることを言える
- [ ] 正規表現だけで桁数を判定しなかった理由を言える
- [ ] 「2026-08-07」が伏せられない理由を言える
- [ ] 表示のたびに計算しない理由を言える
- [ ] 検出のテストだけでは不十分な理由を言える

## Phase3 #117: メッセージAPI — 原文を3層で守る

### 何をした

契約の当事者同士がメッセージをやり取りするAPIを実装した。#116 で作ったマスキングを適用し、**原文（`body`）がAPIから漏れない構造**をテストで固定した。

### 原文を守る3つの層

マスキング関数を作っただけでは守れない。**それを使わない経路**（原文を返すAPI）があれば意味がないため、3層で守る。

| 層             | 方法                                                                 |
| -------------- | -------------------------------------------------------------------- |
| ① レスポンス型 | **原文用のフィールドを作らない**（`Body` に `masked_body` を入れる） |
| ② SQL          | **`body` 列を SELECT しない**（アプリのメモリにも乗らない）          |
| ③ テスト       | **リフレクションでフィールド名を検査**（将来の変更への防御）         |

**「返さない」より「取らない・持たない」**。#97 で status を SET 句に書かなかったのと同じ守り方で、**うっかり詰め込む余地を消す**。

| 守り方                     | 強度                         |
| -------------------------- | ---------------------------- |
| 返す前に消す               | 弱い（消し忘れる）           |
| フィールドを持つが空にする | 中                           |
| **フィールドを作らない**   | **強い（入れる場所が無い）** |

### 概念

#### リフレクションで「型の形」をテストする

```go
forbidden := []string{"RawBody", "OriginalBody", "PlainBody", "UnmaskedBody"}
for field := range reflect.TypeOf(messageResponse{}).Fields() { ... }
```

値ではなく**構造**をテストする珍しい形。**完璧ではない**（`Original` という名前なら通る）が、**原文を足そうとした人が一度立ち止まる**効果がある。テストが落ちれば、コメントを読んで理由を知ることになる。

**守りたい構造はテストで固定する**——コメントだけでは守れない。

#### `reflect.Type.Fields()`（Go 1.24+）

`golangci-lint` の `modernize` が教えてくれた。添字ループより読みやすい:

```go
// 旧
for i := 0; i < t.NumField(); i++ { ... t.Field(i) ... }
// 新
for field := range reflect.TypeOf(v).Fields() { ... }
```

#83 では `unused` が YAGNI を強制したが、`modernize` は**言語の新機能を教えてくれる**。

#### 似た機能でも「使う場面」が違えば条件も違う

|                | 稼働報告（#105）                                 | メッセージ（#117）                                           |
| -------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| 送信できる状態 | **working のみ**                                 | **active / working / reviewing**                             |
| 理由           | 「いつの作業か」が契約の進行と食い違わないように | **条件の相談は稼働前にも起きる**                             |

同じ形の機能に**機械的に同じ条件を適用しない**。

#### `CASE` で行ごとに値を選ぶ

送信者名は企業なら `companies.name`、人材なら `talents.display_name`。
一覧には**両者の発言が混在する**ため、ロールごとにクエリを分けられない。両方を結合しておいて `CASE` で行ごとに選ぶ。

#### 送信者のロールはトークンから引く

`sender_role` はリクエストで受け取らず `fetchRole(userID)` で取得する（クライアント供給値を信用しない＝なりすまし防止）。

#### 会話は古い順・ページネーションなし

- 並びは `ORDER BY created_at, id` の**昇順**（会話は上から下へ読む）。稼働報告が新しい週から並ぶのとは逆

## Phase 3 #43: talent の公開案件一覧（seek ページネーション）

### 何をした

`GET /talent/projects` を seek 法で実装。usecase が limit クランプ（既定20・上限50）・空 skills の nil 正規化・**n+1 テクニック**（limit+1 件取得 → 余り1件の id が next_cursor）を担当。実DBテストの主役は**挿入ズレ耐性**（1ページ目取得 → 新規公開が割り込み → 2ページ目がズレない）。

### 概念

- **seek 法**: `id <= cursor ORDER BY id DESC LIMIT n+1`。OFFSET は「先頭から数える」ので挿入で全ページがズレ、深いページほど遅い。seek は「id という不動の座標」から読むので両方解決
- **n+1 テクニック**: 1件余分に取る → 余りの有無＝次ページの有無、余った行の id ＝次の cursor。`COUNT(*)` 不要
- **カーソルは不透明な値**: サーバーが計算して渡し、クライアントはそのまま返すだけ（計算させると境界バグが再生産される）
- **limit はサーバーでクランプ**: 仕様に「最大50」と書いてもクライアントは守らない前提（信頼境界は仕様書でなくコード）
- **未公開=不存在（同一404）**: draft の存在が id 総当たりで漏れない（#42 の「他社=不存在」と同じ思想）
- **Go 1.26 の `new(expr)`**: `new` が式を取れるようになり `ptr()` 自作ヘルパー不要に／gosec G115 は比較の向きを拡大方向（`len(rows) > int(limit)`）にして回避

### ✅ベストプラクティス

- 「seek 法を選んだ理由」自体をテストにする（OFFSET 実装に書き換えるとズレ耐性テストが必ず落ちる）

### ⚠️アンチパターン

- 一覧に OFFSET を使う（少量なら動くが、書き込みのあるリストでは重複・欠落が仕様バグとして現れる）

### 理解度チェック

## Phase 4 #56: talent の応募API（INSERT...SELECT・遷移表からの WHERE 導出）

### 何をした

応募の作成・一覧・取り下げを実装。作成は **INSERT...SELECT による条件付き INSERT**（公開中のみ）、取り下げは**遷移元リストを遷移表から導出して渡す**条件付き UPDATE + **UPDATE...FROM**（JOIN でタイトル込みの RETURNING）。

### 概念

- **INSERT...SELECT（条件付き INSERT）**: 「公開中の案件が存在するときだけ挿入」を1文で原子的に。SELECT→INSERT の2文だと確認と挿入の間に非公開化される窓が空く（条件付き UPDATE の挿入版）。0行 = 未公開 or 不存在（区別せず404）
- **エラーの出どころを DB に寄せる**: 未公開404（0行）・二重応募409（23505）・所有404（WHERE talent_id）——アプリ側の if でなく SQL の形と制約が防ぐ
- **遷移表から SQL パラメータを導出**: `WHERE status = ANY(@from_statuses::text[])` に渡すリストを `CanTransitApplication(ActorTalent, from, withdrawn)` の全走査で作る。遷移表（shared/domain）が一次情報のまま WHERE に反映され、表を変えれば SQL の挙動も変わる
- **UPDATE...FROM**: UPDATE に JOIN を付けて RETURNING で結合先の列（project_title）を返す。レスポンス組み立ての追加クエリを消す
- **0行更新の後の区別**: 条件付き UPDATE が0行 → 再取得して「不存在/他人=404」と「遷移不可=409（現在の状態つき）」を分ける（#42 company と同じ型）
- **`= ANY(@param::text[])`**: IN 句のパラメータ化（PostgreSQL の定石）
- **UNIQUE と状態機械の相互作用**: withdrawn 後の再応募は UNIQUE(project_id, talent_id) により 409。「取り下げたら再応募できる」仕様にするなら部分 UNIQUE インデックス（WHERE status NOT IN (...)）が必要になる——現仕様は「1案件1応募（履歴含む）」を意図的に選択

### ✅ベストプラクティス

- 「〜のときだけ作成できる」系の前提条件は INSERT 文の中（SELECT / 制約）に埋め込む。アプリ側 if は UX のため、DB が最後の砦

### ⚠️アンチパターン

- SELECT で確認してから INSERT（TOCTOU・手元で再現しない典型）
- 遷移元リストを SQL にハードコード（遷移表と食い違っていく）

### 理解度チェック

- [ ] INSERT...SELECT が2文方式より安全な理由を時系列で言える
- [ ] withdraw の WHERE の3条件（id・talent_id・from_statuses）がそれぞれ何を防ぐか言える

## Phase 4 #58: talent の応諾API（rule of three・ダブルオプトインの完成）

### 何をした

accept / decline を追加し、talent 側の遷移を `UpdateApplicationStatusForTalent`（to_status パラメータ）・usecase の `changeStatus`・handler の共通ヘルパーに**3層まとめて共通化**。ダブルオプトイン一巡の統合テストで Phase 4 の API が完成。

### 概念

- **rule of three**: 同形が3つ（withdraw / accept / decline）揃ってから共通化。#56 の時点（1つ）で to_status をパラメータ化しなかったのは意図的 —「2つは偶然、3つはパターン」。早すぎる抽象化は形の観察を打ち切ってしまう
- **表がそのまま挙動になる**: accept の遷移元は `changeableFrom(accepted)` が表から `[offered]` を導出 → 「applied のまま承諾できない（ダブルオプトインの片翼防止）」に**専用の if が1行も存在しない**
- **リファクタの安全網**: クエリ・usecase を書き換えても既存の withdraw テストが（エラー名のリネーム以外）無修正で通る＝挙動が変わっていない証拠。実DBテストがリファクタの免許証になる
- **統合テストで状態機械を一巡**: applied → (accept拒否) → offered → accepted → (全操作拒否=終端)。単体（遷移表72通り・#55）は「表が正しい」、統合は「表が実装に正しく写っている」を保証する——2層で意味が違う
- **両視点の対称完成**: talent（withdraw/accept/decline × WHERE talent_id）と company（offer/reject × JOIN 越し company_id）が同名の changeableFrom / changeStatus / changeApplicationStatus を持つ。遷移表の6行が2つの対称な実装に写像された

### ✅ベストプラクティス

- リファクタと機能追加を同じ Issue でやるときは「リファクタで既存テスト緑」→「追加分のテスト」の順に刻む（どちらが壊したか常に分かる）

### ⚠️アンチパターン

- 1つ目の実装から「将来のために」ジェネリックにする
- 統合テストを省いて「単体（表のテスト）があるから大丈夫」とする（表と実装の間の写し間違いは単体では出ない）

### 理解度チェック

- [ ] rule of three の判断（いつ共通化するか・なぜ2つでは早いか）を言える
- [ ] applied で accept できない保証がどこにあるか（if 文ではない）を言える

## Phase 5 #80: デプロイ前の運用土台（slog・request_id・graceful shutdown）

### 何をした

`shared/middleware` を新設（RequestID / AccessLog+ロガー / Recovery）し、全 handler の log.Printf（21箇所）を slog.ErrorContext へ置換。SIGTERM/SIGINT の graceful shutdown を実装。CORS は「不要」と判断して記録。

### 概念

- **slog の Handler デコレータ**: Logger→Handler の2層構造を利用し、JSON ハンドラを包んだ contextHandler が `Handle(ctx, record)` の瞬間に context から request_id を拾って属性追加。**handler 側は ctx を渡すだけ**で ID を引数で回さない。`WithAttrs`/`WithGroup` もラップし直す（忘れると With した logger からデコレータが剥がれる）
- **request_id はレスポンスヘッダにも返す**（X-Request-ID）: 問い合わせの値でログを一発検索できる＝運用の生命線
- **ミドルウェアの玉ねぎ構造**: 外側ほど先に実行。RequestID を最外に置く＝ panic ログ（Recovery）にも ID が付く。「何が何のログに載るか」は包む順序で決まる
- **statusRecorder**: ResponseWriter は書き込んだ status を後から読めない → WriteHeader を埋め込みオーバーライドで横取り（アクセスログの定石）
- **graceful shutdown**: `signal.NotifyContext` → `srv.Shutdown(timeoutCtx)`。新規受付を止め処理中を完了させてから終了。タイムアウトは Cloud Run の SIGKILL 猶予より短く。ListenAndServe は goroutine に逃し select で「起動失敗 or シグナル」を待つ
- **CORS は不要（判断の記録）**: このアーキテクチャでは**ブラウザが Go を直接呼ぶ経路が存在しない**（トークンは httpOnly Cookie・全通信は Server Actions / RSC のサーバー間 fetch）。CORS はブラウザの同一オリジン制約の仕組みなので、サーバー間通信には関与しない。ミドルウェアを足すと「ブラウザから呼べる余地がある」という誤ったシグナルにもなるため入れない。WEB_ORIGIN が必要になるのは「ブラウザ→Go 直接呼び出し」を導入するときで、その時に改めて設計する

### ✅ベストプラクティス

- ロガーの初期化は main の最初の1行（それ以前のログは構造化されない）
- エラーの詳細はログのみ・クライアントには一般文言（panic の stack も同様）— 初期からの原則を panic 経路にも貫通

### ⚠️アンチパターン

- request_id を関数引数で全層に引き回す（context + Handler デコレータで消せる配管）
- SIGTERM を無視する（Cloud Run の入替のたびに処理中リクエストが切断される）
- 「念のため」で CORS ミドルウェアを入れる（不要な attack surface と誤ったアーキテクチャのシグナル）

### 理解度チェック

- [ ] handler に request_id が登場しないのに全ログへ付く経路を言える
- [ ] RequestID を最外に置いた理由を玉ねぎ構造で言える
- [ ] CORS が不要な理由を「どの通信がブラウザ発か」で説明できる
- [ ] Shutdown のタイムアウトを SIGKILL 猶予より短くする理由を言える

### ⚠️アンチパターン

- fixture データを SQL の UPDATE で任意の状態に直接書く（遷移表が守っている不変条件を世界が破る）

## Phase 6 #95: e2e fixture 基盤（Step 3: make e2e-dump と Load）

### 何をした

`make e2e-dump`（DB 再作成 → seed → pg_dump）で dump.sql（19行・生成物）を生成し、`load.go` でテストの Tx 内に読み込む仕組みを作った。**2回生成して diff ゼロ（再現性）**・Load テスト緑・並列 Load の共存も確認。

### 概念

- **pg_dump のフラグ設計**: `--data-only`（スキーマは migrations の担当と分離）・`--column-inserts`（1行1INSERT + 列名明示 = diff がレビュー可能・列順変更に頑健）。テーブルは **FK の依存順に明示列挙**（pg_dump のテーブル順はカタログ順で、依存順の保証がない）
- **`OVERRIDING SYSTEM VALUE`**: IDENTITY 列に明示 ID を入れる pg_dump の出力。これで固定 ID の世界が再現される
- **go:embed**: dump.sql をバイナリに埋め込み、テストの実行場所（CI/ローカル・cwd）に依存しないロードにする
- **シーケンスは非トランザクショナル**: setval/nextval は ROLLBACK で戻らない。dump が ID 明示 INSERT するため、Load 後に**前方にのみ**（GREATEST）シーケンスを進める。無邪気に `setval(max(id))` すると並列テストのシーケンスを巻き戻して衝突・ロック待ちの温床になる
- **「1行=1文」を規約にしてパーサを消す**: 参考にした実務プロダクトは dump を独自パーサで分割していたが、こちらは pg_dump のフラグと「基準世界のデータに改行を入れない」規約で行単位実行にできる。規約破りは Load が即検出する（前提を守らせるコードを添える）

### ✅ベストプラクティス

- 生成targets には検証を同居させる（`test -s` で空 dump を検出・seed の expect で ID ズレを検出 — 生成が成功したように見えて壊れている、を防ぐ）

### ⚠️アンチパターン

- dump.sql を手で直す（生成物。直すのは seed.go）
- Load 後のシーケンス調整を忘れる（fixture の固定 ID と新規 INSERT が衝突し「たまに落ちるテスト」になる）

### 理解度チェック

- [ ] テーブルを明示列挙して dump する理由（FK 依存順）を言える
- [ ] シーケンスが非トランザクショナルであることが、なぜ「前方にのみ進める」設計につながるか言える
- [ ] 独自パーサを書かずに済んだ理由（何を規約にしたか）を言える

## Phase 6 #93: API 統合テスト基盤（Step 1: composition root の抽出）

### ⚠️アンチパターン

- テスト用に「本番と少し違う組み立て」を作る（配線のズレは統合テストの検証対象外になり、本番だけで壊れる）

## Phase 6 #93: API 統合テスト基盤（Step 2: apitest と認可の通し）

### 何をした

### 概念

- **NewServer の3層**: NewTestTx（Tx分離）→ e2efixture.Load（基準世界）→ app.NewRouter（本番と同一配線）→ httptest.Server。片付けは t.Cleanup と ROLLBACK に任せ、テスト本体には後始末が1行も無い
- **httptest.Server**: 本物の TCP で listen する使い捨てサーバー。ポートは自動割当（並列でも衝突しない）。in-process なのに「HTTP を本当に喋る」ため、ルーティング・ヘッダー・ステータスコードまで検証対象になる

- **401 と 403 の区別をテスト名で語る**: 401=誰か分からない／403=誰かは分かるが権限が無い。「改ざんトークンとヘッダー無しが同一応答（理由を漏らさない）」もケースとして固定

## Phase 6 #97: 応募 API の統合テスト（Step 1: talent 視点）

### 何をした

talent 視点の応募テスト4本（応募・一覧・遷移3種・異常系ガード）。途中で **Tx 内サーバー方式の既知の制約**を実地で踏んだ（下記）。

### 概念

- **25P02（transaction aborted）— Tx 内サーバーの構造的な制約**: 二重応募の UNIQUE 違反（本物の SQL エラー）が起きると、テストを包むトランザクション全体が aborted になり、**以降の全リクエストが 500** になる。本番は各リクエストを包む Tx が無いので無害＝**テストでしか起きない現象**。対処は「SQL エラーを起こすケースは各テストの最後に置く」（apitest のパッケージコメントにルール化）。なお INSERT...SELECT の0行（draft への応募404）は SQL エラーではないので Tx を汚さない — 「クライアント側の ErrNoRows」と「サーバー側の SQL エラー」の違いがここで効く
- **独立世界の再利用**: 同じ基準世界の Offered(id=2) を、accept テストと decline テストが**それぞれ別の運命に導く**。テストごとに世界がリセットされる（Tx 分離）からできる、dump 方式で最も気持ちいい瞬間
- **UNIQUE 制約が世界の形を決める**: 基準世界では両 talent が公開3件すべてに応募済みのため、新規応募のテストには API 経由の新案件が必要。制約がテストデータ設計を規定する
- **500 を見たらまずサーバーログ**: ステータスだけ見て悩まず、slog の ERROR 行（err="..."）を見れば SQLSTATE まで一発で分かる（#80 の構造化ログが自分のテストデバッグに効いた）

### ✅ベストプラクティス

- エラーメッセージの契約（409 に現在の状態が含まれる）を strings.Contains で固定（画面がそのまま表示できる保証）

### ⚠️アンチパターン

- Tx 内サーバーで SQL エラー系ケースの後に正常系を続ける（謎の500の温床。順序をルール化する）

### 理解度チェック

- [ ] 25P02 が「テストでしか起きない」理由を本番との差で言える
- [ ] draft への応募404 が Tx を汚さない理由（ErrNoRows と SQL エラーの違い）を言える
- [ ] 同じ fixture 行を複数テストで別の状態に導ける理由を言える
