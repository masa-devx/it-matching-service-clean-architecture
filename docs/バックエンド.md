## Issue #2: DB接続とヘルスチェック（main/db/response/health）

### 何をした
Go APIの土台4ファイルを作成。godotenvで`.env`読込 → pgxドライバでDB接続（プール上限を明示）→ `GET /health` がタイムアウト付きPingでDB疎通込みの死活確認を返す（:8081）。

### 概念（todo-appからの進化点）
- **pgx ドライバ**: todo-appの`lib/pq`はメンテナンスモード。現行標準は`jackc/pgx`（`stdlib`経由で`database/sql`から利用、ドライバ名`"pgx"`）
- **godotenv**: Goは`.env`を自動で読まない → `godotenv.Load()`で読込。無ければ実環境変数を使う（本番対応）。DSN未設定は**fallbackせずfatal**（12-factor: 設定は環境から明示的に）
- **接続プールの上限**: `SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime`。無制限だと高負荷時に接続枯渇でDBを巻き込む
- **`context.WithTimeout`＋`PingContext`**: DB無応答時に無限待ちしない。`r.Context()`から派生させるとクライアント切断でも中断される
- **writeErrorの改善**: 詳細は**ログのみ**、クライアントには安全なメッセージ（todo-appは`err.Error()`をそのまま返していた→情報漏えい対策）

### ✅ ベストプラクティス
- healthはDB疎通まで確認（プロセス生存だけでは「動いているのに使えない」を検知できない）
- 200/503の使い分け（LB・監視が判定に使う）

### ⚠️ アンチパターン
- `.env`をコードに直書き／DSN未設定のまま暗黙のデフォルトで起動（環境事故の温床）
- healthで常に200（DBが死んでいても「正常」に見える）

### 理解度チェック
- [ ] pqでなくpgxを選ぶ理由を説明できる
- [ ] プール上限を設定しないと何が起きるか説明できる
- [ ] `PingContext`＋タイムアウトの意味を説明できる
- [ ] writeErrorで詳細をログのみに出す理由を説明できる

## Phase0 #3 Step2: POST /signup（バリデーション・bcrypt・重複409）

### 何をした
`auth.go` に `POST /signup` を実装。JSONデコード → email正規化（小文字化）→ バリデーション（email形式 / パスワード8〜72文字 / role列挙）→ bcryptハッシュ化 → INSERT。email重複はUNIQUE制約違反（SQLSTATE 23505）を検出して409に変換。

### 概念
- **bcrypt**: パスワード専用の遅いハッシュ。ソルト自動生成・ハッシュ文字列内に埋め込み（`$2a$10$ソルト+ハッシュ`）。コスト係数で計算量を指数的に調整（既定10）。SHA-256が不適な理由＝速すぎて総当たりに弱い
- **bcryptの72バイト制限**: 入力が72バイトを超えると黙って切り捨てられる → 超過を明示的に400で拒否するのが安全
- **SELECT事前確認ではなくINSERT+エラー変換**: 「SELECTで重複なし→INSERT」は2つのリクエストが同時に来ると両方すり抜ける（TOCTOU）。UNIQUE制約違反を `errors.As` で `*pgconn.PgError` に取り出し `Code == "23505"` を判定するのが正しい型
- **`RETURNING`**: INSERTと同時に生成値（id / created_at）を1往復で取得するPostgreSQLの構文
- **email正規化**: 大文字小文字を区別せず扱うため `strings.ToLower` + `TrimSpace` してから保存・比較

### ✅ベストプラクティス
- エラーレスポンスは共通ヘルパー経由で、内部エラー詳細はログのみ（`err.Error()`をクライアントに返さない）
- ステータスコードの使い分け: 入力不備=400 / リソース競合=409 / 想定外=500
- パスワードは平文をログにも出さない（reqのダンプ禁止）

### ⚠️アンチパターン
- SELECTで重複確認してからINSERT（TOCTOU競合）
- bcryptではなく速いハッシュ（MD5/SHA系）でパスワード保存
- `err.Error()` をそのままレスポンスに含める（DB構造の情報漏えい）

### 理解度チェック
- [ ] bcryptがSHA-256より安全な理由（速度と何の関係があるか）を説明できる
- [ ] 「SELECTで確認してからINSERT」がダメな理由を同時リクエストの時系列で説明できる
- [ ] `errors.As` が `==` 比較と違う点を説明できる
- [ ] RETURNINGを使わない場合、created_atを返すには何往復必要か説明できる

## Phase0 #4: POST /login（JWT発行・同一401）

### 何をした
`jwt.go`（HS256発行・sub/iat/exp・JWT_SECRETのfail fast起動チェック）と `auth.go` の `handleLogin`（email検索 → bcrypt照合 → JWT返却）を実装。認証失敗は理由を問わず同一の401。

### 概念
- **JWTの構造**: `ヘッダー.ペイロード.署名` のBase64三部構成。ペイロードは暗号化ではなく**エンコード**（誰でも読める→秘密情報を入れない）。署名だけが改ざん防止の保証
- **RegisteredClaims**: RFC 7519の標準クレーム。`sub`=誰のトークンか（文字列）／`iat`=発行時刻／`exp`=失効時刻。expなし＝漏えいしたら永久に有効、は事故
- **ユーザー列挙（User Enumeration）**: 「emailが存在しません」「パスワードが違います」を区別して返すと、攻撃者が登録済みemail一覧を収集できる → **同一ステータス・同一文言**で返す
- **タイミング攻撃対策のダミー照合**: 未登録emailで照合をスキップすると応答が速くなり、時間差で存在が推測できる → 未登録でも捨てハッシュとbcrypt照合して計算コストを揃える
- **`bcrypt.CompareHashAndPassword`**: ハッシュから埋め込みソルト・コストを取り出して同条件で再計算・比較。比較自体も一定時間（subtle.ConstantTimeCompare）

### ✅ベストプラクティス
- 署名鍵は環境変数＋起動時チェック（空鍵で起動させない）
- ログイン失敗の内部理由（no rows / mismatch）はログにも安易に出さない（出すなら監査目的で設計して出す）
- トークンのクレームは最小から始める（必要になってからroleを足す）

### ⚠️アンチパターン
- 「emailが存在しません」と「パスワードが違います」を区別して返す
- JWTペイロードに個人情報・秘密情報を入れる
- 無期限トークン／鍵のハードコード

### 理解度チェック
- [ ] ユーザー列挙攻撃の手口と「同一401」が防ぐ仕組みを説明できる
- [ ] 未登録emailでもダミーハッシュと照合する理由を説明できる
- [ ] CompareHashAndPasswordが「ソルト列なし」で照合できる理由を説明できる
- [ ] JWTを受け取ったクライアントがペイロードを読める理由と、それでも安全な理由を説明できる

## Phase0 #5: 認証ミドルウェア（parseToken / requireAuth / CORS）

### 何をした
`parseToken`（keyfuncでHMAC強制・exp自動検証・sub→userID）、`requireAuth`（Bearer取り出し→検証→contextへ格納・一律401）＋`userIDFrom`、`GET /me`（保護ルートの実物）、`corsMiddleware`（:3000許可リスト・プリフライト応答）を実装。

### 概念
- **ミドルウェアパターン**: `func(next http.Handler) http.Handler`。ハンドラを包んだハンドラを返し、玉ねぎ状に重ねる。401ならnextを呼ばない＝ハンドラは実行すらされない
- **algすり替え攻撃**: JWTヘッダーのalgは攻撃者が書き換え可能。`alg:none`（署名なし扱い）やRS256→HS256混同を、keyfunc内の `t.Method.(*jwt.SigningMethodHMAC)` 型アサーションで遮断。「検証側が方式を固定」が対策の本質
- **context.Context**: リクエスト1本に紐づく荷物置き場。キーは非公開の独自型（`type ctxKey int`）にして他パッケージとの衝突を構造的に防ぐ
- **IDOR対策の入口一本化**: user_idの取得は `userIDFrom(ctx)` だけ。リクエスト値のuser_idは信用しない
- **CORS**: ブラウザ専用の防御（サーバー間通信やcurlには無関係）。異なるオリジン（スキーム＋ホスト＋ポート）へのJSアクセスをブラウザが遮断し、サーバーが応答ヘッダーで明示的に許可する仕組み
- **プリフライト**: `Authorization` 等のヘッダー付きリクエストの前にブラウザが自動送信するOPTIONS。「この内容を送っていいか？」の事前確認。204+許可ヘッダーで応答しルーティングには渡さない
- **`Vary: Origin`**: Originによって応答ヘッダーが変わることをキャッシュ層に伝える（付けないとCDN等が別Origin向けの応答を使い回す事故）

### ✅ベストプラクティス
- Allow-Originは許可リスト方式（`*` にしない。Cookie認証では `*` は仕様上不可）
- CORSは最外層・認証はルート単位、と適用範囲で層を分ける
- 認証失敗の詳細はログのみ（クライアントには一律401）

### ⚠️アンチパターン
- `Access-Control-Allow-Origin: *` ＋ Credentials（そもそもブラウザが拒否）
- keyfuncで無条件に鍵を返す（algすり替え素通り）
- 「CORSがあるから安全」という誤解（curlやサーバーからは素通し。認証・認可こそが防御）

### 理解度チェック
- [ ] ミドルウェアが「包む」構造と、401時にハンドラが実行されない理由を説明できる
- [ ] alg:none攻撃がどのコード行で弾かれるか指させる
- [ ] プリフライトが飛ぶ条件と、OPTIONSで204を返す理由を説明できる
- [ ] CORSが「ブラウザだけの防御」である意味（curlには効かない）を説明できる

## Phase0 #24: golangci-lint 導入

### 何をした
golangci-lint v2 を導入（`api/.golangci.yml`）。標準セット＋gosec/errorlint/exhaustive/usestdlibvars等を有効化し、検出された実問題を修正（`defer db.Close()` のエラー破棄明示・gosec 2件へ理由付きnolint）。ついでに追跡され続けていたビルドバイナリを `git rm --cached` で解除。

### 概念
- **golangci-lint = linterのランナー**: govet/staticcheck/errcheck等を束ねて並列実行。go vet は内包されるのでCIはこれ一本に集約できる
- **errcheck**: エラー戻り値の無視を検出。「うっかり無視」と「判断して無視（`_ =`＋理由コメント）」をコードで区別する
- **gosec**: セキュリティlinter。G114（タイムアウト無しListenAndServe）という本物の指摘を初回実行で検出→#29で修正予定をnolintコメントに明記
- **nolintの作法**: `//nolint:linter名 // 理由` 形式。理由なしのnolintは「黙らせただけ」で監査不能
- **exhaustive**: 列挙値switchの網羅漏れ検出。Phase 3以降の状態機械（遷移表）で本領発揮する布石
- **check-blank無効の判断**: `_ = f()` を意図表明の慣習として維持（有効化すると全箇所nolint必須になる。厳格さと引き換えに冗長）

### ✅ベストプラクティス
- lint設定はリポジトリにコミットし、ローカルとCIで同一設定を参照
- linterは標準セットから始めて必要に応じて追加（最初から全部有効は警告の洪水で形骸化する）

### ⚠️アンチパターン
- 理由なしの `//nolint`／.gitignoreに書いただけで追跡済みファイルが除外されたと思い込む（`git rm --cached` が必要）

### 理解度チェック
- [ ] golangci-lint と go vet の関係を説明できる
- [ ] `_ = db.Close()` が表明していることを言える
- [ ] nolintに理由を書く意味を言える

## Phase0 #29: サーバー基礎体力（リクエストログ・タイムアウト・graceful shutdown）

### 何をした
`loggingMiddleware`（statusRecorderでステータス捕捉・strconv.Quoteでログインジェクション対策）を最外層に追加。`http.ListenAndServe` を `http.Server`（4種タイムアウト設定）に置き換え、SIGINT/SIGTERMで処理中リクエストを待つ graceful shutdown を実装。#24から持ち越した gosec G114 の nolint を解消。

### 概念
- **statusRecorder（構造体埋め込みラップ）**: ResponseWriterには「何を書いたか」を読む手段がない→埋め込みで全メソッド継承し、WriteHeaderだけ上書きして記録。デコレータパターンのGo流
- **ログインジェクション（gosec G706）**: パスに改行を含めると偽のログ行を捏造できる→ユーザー入力は strconv.Quote でエスケープしてからログへ（%qではgosecのtaint解析が解除されず、明示的なサニタイズ関数が必要だった）
- **Slowloris攻撃と4種タイムアウト**: ヘッダを1バイトずつ送って接続を占有する攻撃。ReadHeaderTimeout（ヘッダ読み切り）/ ReadTimeout（ボディ込み）/ WriteTimeout（レスポンス書き込み）/ IdleTimeout（Keep-Alive遊休）で接続の寿命を区切る
- **graceful shutdown 三点セット**: `signal.NotifyContext`（シグナルをctxに変換）→ サーバーはgoroutineで起動し `<-ctx.Done()` で待機 → `srv.Shutdown(timeout付きctx)`（新規受付停止＋処理中を待つ）。Shutdown起因の `http.ErrServerClosed` は正常終了として除外
- **なぜ本番で重要か**: デプロイ・スケールイン時はSIGTERM→猶予→SIGKILL の順で止められる（Cloud Run等）。gracefulが無いと処理中のリクエストがぶった切られる

### ✅ベストプラクティス
- ロギングは最外層（401やプリフライトも全部記録）
- タイムアウトは「無限を許さない」が原則。値は用途に応じて調整（ファイルアップロード等があればReadTimeoutを伸ばす）

### ⚠️アンチパターン
- 素の `http.ListenAndServe`（全タイムアウト無限＝Slowloris無防備）を本番に置く
- SIGKILL前提の停止運用（graceful を実装していても待ち時間より長い処理は切れる。Shutdownのtimeoutは猶予期間より短く）

### 理解度チェック
- [ ] statusRecorder が必要な理由を ResponseWriter の性質から説明できる
- [ ] Slowloris の手口と ReadHeaderTimeout の関係を言える
- [ ] Shutdown と即時終了の違い（処理中リクエストの扱い）を言える
- [ ] ErrServerClosed をエラー扱いしない理由を言える

## Phase1 #49: 構造化ログ（log/slog）へ移行

### 何をした
`log.Printf` の平文ログを Go 標準の log/slog へ移行。`logger.go` で LOG_FORMAT（text/json）・LOG_LEVEL を切り替え、アクセスログとエラーログを属性つきで出力。ステータスに応じて 5xx=Error / 4xx=Warn / それ以外=Info に出し分け。

### 概念
- **構造化ログ**: メッセージに値を埋め込まず「key=value の属性」で渡す。ログ基盤がフィールド単位で検索・集計・アラートできる（`status=500` の件数監視など）。平文は grep しかできない
- **Logger と Handler の分離**: 「何を書くか」と「どう出すか」が別。コードは `slog.Info("msg", "key", v)` だけ書き、形式の切り替えは起動時の1箇所
- **出力先は常に標準出力**（12-Factor）: アプリはファイルに書かない。ローテーション・収集・保存は Docker / Cloud Run / ログ基盤の仕事。「どこに出すか」ではなく「どんな形式か」がアプリの責任
- **レベル設計**: 5xx=Error（要対応・アラート対象）/ 4xx=Warn（クライアント起因・調査の手がかり）/ 2xx=Info。混ぜると「エラーが多すぎて誰も見ない」状態になる
- **`slog.LogAttrs`**: 属性を型付きで渡す最速の書き方（`slog.String` / `slog.Int`）。可変長 any の `slog.Log` よりアロケーションが少ない
- **ログインジェクション対策が構造的に解決**: 属性方式ではフォーマット文字列に値を埋めないため、改行入りパスで偽のログ行を捏造できない。#29 で入れた `strconv.Quote` は不要になり削除（gosec も再発せず）
- **不正な LOG_LEVEL で起動を止めない**: 「間違っていても安全に動く設定」は既定値へフォールバック（DATABASE_URL の fail fast とは扱いを分ける・#28の基準）

### ✅ベストプラクティス
- `log.Fatal` は slog の形式に乗らないため、`slog.Error` + `os.Exit(1)` のヘルパーに置き換える
- エラー応答は err が nil でもログに残す（監視で 4xx/5xx の件数を追えるようにする）

### ⚠️アンチパターン
- メッセージ文字列に値を連結する（`fmt.Sprintf("user %d failed", id)`）→ 検索・集計ができない
- すべて Error レベルで出す／ログをファイルに書いて自前ローテーション

### 理解度チェック
- [ ] 構造化ログが平文より優れる点を「検索・集計」の観点で説明できる
- [ ] アプリがログをファイルに書かない理由を言える
- [ ] 4xx と 5xx でレベルを分ける理由を言える
- [ ] 属性方式がログインジェクションを防ぐ仕組みを説明できる

## Phase1 #50: リクエストID（相関ID）とエラーの突き合わせ

### 何をした
`requestIDMiddleware` でリクエストごとに一意のIDを発行し、context・レスポンスヘッダ（X-Request-ID）・アクセスログ・エラーログ・エラーレスポンスボディの5か所に伝播。`writeError` に ctx を渡す形へ変更（27箇所）し、認証済みなら user_id もログに残す。

### 概念
- **相関ID（Correlation ID）**: 1回のリクエストで発生する複数のログを1本の線で束ねるID。同時アクセス時に「どのエラーがどのリクエストか」を判別できる。分散システムでは複数サービス横断で追う仕組み（トレーシング）の入口
- **受信ヘッダの尊重**: `X-Request-ID` が来ていれば引き継ぐ（ロードバランサ/フロント/上流サービスが採番したIDでつながる）。無ければ自分で採番
- **crypto/rand による採番**: UUIDライブラリを足さず 16バイト→hex 32文字。相関IDに必要なのは一意性だけで、UUIDの版番号・書式は不要
- **外部入力の検証**: X-Request-ID は誰でも送れる値をログとヘッダに載せる経路。長さ64・英数字/-/_ に制限して汚染・インジェクションを防ぐ（信頼できない入力は境界で検証）
- **`slog.Logger.With` の子ロガー**: 属性を固定したロガーを作り、以降のログに自動で付与。呼び出し側が毎回IDを渡さなくてよい
- **ユーザーへの相関IDの提示**: エラーレスポンスに request_id を含めると、「この画面にこのIDが出た」という報告だけでログを特定できる（実務のサポート導線）
- **ミドルウェアの順序**: requestID を最外に置く（内側だとアクセスログがIDを取得できない）

### ✅ベストプラクティス
- ログ・レスポンス・ヘッダの3方向に同じIDを流す（内部調査と外部報告の両方が繋がる）
- 認証済みリクエストは user_id も添える（誰の操作で失敗したかの手がかり）
- 引数に `context.Context` を先頭で受ける関数シグネチャに揃える（Goの慣習）

### ⚠️アンチパターン
- 外部から来たIDを無検証でログ・ヘッダに載せる
- リクエストIDを毎回手で引き回す（context + 子ロガーで自動化する）
- 相関IDを付けずに「エラーログだけ」を眺める（同時アクセス時に無力）

### 理解度チェック
- [ ] 相関IDが無いと何が困るか、同時アクセスの例で説明できる
- [ ] X-Request-ID をサニタイズする理由を言える
- [ ] requestID ミドルウェアを最外に置く理由を言える

## Phase1 #51: panic recovery ミドルウェア

### 何をした
`recoverMiddleware` を追加し、ハンドラ内の panic を回復してスタックトレース・相関ID付きで Error ログに記録し、500 を返す。`httptest` によるテスト4ケースを追加。

### 概念
- **panic / recover**: Goの panic は例外ではなく「回復不能な異常」の通知。`recover()` は **defer した関数の中でしか効かない**（panicで巻き戻る途中に実行されるため）
- **なぜ自前で捕まえるか**: net/http も panic を捕捉するが、標準エラーへ素で出るだけで構造化ログにも相関IDにも乗らない。自前で捕まえて `slog.Error` にすることで、監視・アラート・調査の導線に統合される
- **`http.ErrAbortHandler` の特別扱い**: クライアント切断時に net/http 自身が投げる正常系の合図。捕まえるとログが汚れるため再パニックで素通しする（標準の作法）
- **`debug.Stack()`**: panic 発生時点のスタックトレースを取得。「どこで落ちたか」が分かる唯一の手がかり
- **panicの内容をクライアントに返さない**: 変数の中身やコード構造が漏れるため、レスポンスは定型文の500のみ（ログには全部残す）
- **ミドルウェアの配置**: requestID（外・IDは常に必要）→ recover → logging（内・500になった結果をアクセスログに残す）。recoverをloggingの外に置くとpanic時のアクセスログが消える
- **`httptest`**: 実サーバーを起動せずミドルウェア/ハンドラを検証できる標準パッケージ。`httptest.NewRequest` + `NewRecorder` で組み立て、`ServeHTTP` を直接呼ぶ

### ✅ベストプラクティス
- panic は握りつぶさず必ず記録する（バグの存在を隠さない）
- テストで「panicしても落ちない」ことを保証する（回帰テストとして永続化・一時的な検証ハンドラをコミットしない）
- 秘密が漏れないことをテストで固定する（TestRecoverMiddlewareHidesPanicDetail）

### ⚠️アンチパターン
- `recover()` を defer の外で呼ぶ（何も起きない）／panic を回復して何もログに残さない
- panic の値をそのままレスポンスに含める（情報漏えい）
- ErrAbortHandler まで捕まえて「エラー」として記録する（正常な切断がノイズになる）

- [ ] net/http 標準の回復では不十分な理由を言える
