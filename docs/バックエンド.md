## Issue #2: DB接続とヘルスチェック（main/db/response/health）

### 何をした
Go APIの土台4ファイルを作成。godotenvで`.env`読込 → pgxドライバでDB接続（プール上限を明示）→ `GET /health` がタイムアウト付きPingでDB疎通込みの死活確認を返す（:8081）。

### 概念（todo-appからの進化点）
- **pgx ドライバ**: todo-appの`lib/pq`はメンテナンスモード。現行標準は`jackc/pgx`（`stdlib`経由で`database/sql`から利用、ドライバ名`"pgx"`）
- **godotenv**: Goは`.env`を自動で読まない → `godotenv.Load()`で読込。無ければ実環境変数を使う（本番対応）。DSN未設定は**fallbackせずfatal**（12-factor: 設定は環境から明示的に）
- **接続プールの上限**: `SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime`。無制限だと高負荷時に接続枯渇でDBを巻き込む
- **`context.WithTimeout`＋`PingContext`**: DB無応答時に無限待ちしない。`r.Context()`から派生させるとクライアント切断でも中断される
- **writeErrorの改善**: 詳細は**ログのみ**、クライアントには安全なメッセージ（todo-appは`err.Error()`をそのまま返していた→情報漏えい対策）

### ✅ ベストプラクティス
- healthはDB疎通まで確認（プロセス生存だけでは「動いているのに使えない」を検知できない）
- 200/503の使い分け（LB・監視が判定に使う）

### ⚠️ アンチパターン
- `.env`をコードに直書き／DSN未設定のまま暗黙のデフォルトで起動（環境事故の温床）
- healthで常に200（DBが死んでいても「正常」に見える）

### 理解度チェック

- [ ] プール上限を設定しないと何が起きるか説明できる
- [ ] `PingContext`＋タイムアウトの意味を説明できる
