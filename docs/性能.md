# 性能計測（案件5万件）

> 計測日: 2026-08-05 ／ データ: 案件 50,003件（うち公開中 42,502件）・企業11社
> 環境: ローカル（Docker PostgreSQL 16 / ホストポート5434）・Go API はローカル直起動
> **このドキュメントは「現状の記録」。改善は #66 で行う**

## 計測方法（誰でも再現できる手順）

```bash
make db-up && make migrate-up && make seed-large   # 5万件を投入（決定的な生成なので毎回同じデータ）
make perf                                          # DB: EXPLAIN (ANALYZE, BUFFERS)
make dev-api                                       # 別ターミナル
make perf-load                                     # API: k6 で負荷試験
```

- 計測クエリは `migrations/perf_queries.sql`、負荷シナリオは `k6/list_projects.js`
- シードは `random()` を使わない決定的生成のため、**いつ誰が実行しても同じデータ**（before/after の比較が成立する）

## 実行計画の読み方

| 用語 | 意味 |
| --- | --- |
| **Seq Scan** | 全行を順に読む。小さい表なら最速だが、大きい表では赤信号 |
| **Index Scan** | 索引を辿って必要な行だけ読む。少数ヒット向き |
| **Bitmap Index Scan** | 索引で行の位置を集め、まとめて読む。中量ヒット向き（GINはこの形） |
| **Index Only Scan** | 索引だけで完結し表を読まない（最速。`Heap Fetches: 0` が理想） |
| **Nested Loop / Hash Join** | 結合方式。件数が少なければ Nested Loop、多ければ Hash Join が選ばれる |
| `cost=0.41..16860` | プランナの**見積もり**（相対値。左=初動コスト・右=全件コスト） |
| `actual time=0.096..0.665` | **実測ミリ秒**。cost と乖離が大きければ統計情報を疑う |
| `rows=42504` vs `rows=21` | 見積もり行数と実測行数。大きくズレたら `ANALYZE` 不足 |
| `Buffers: shared hit=37` | メモリから読んだブロック数（`read` ならディスク）。**I/O量の実測値** |
| `Rows Removed by Filter` | 索引で絞れず、行を読んでから捨てた数。**多いほど無駄** |

## 考察 — 将来のボトルネック候補

### 1. 深いページの OFFSET（最優先・#63で対応予定）

```
OFFSET 0     : 0.80ms  → Index Scan で先頭20件を読むだけ
OFFSET 40000 : 56.42ms → Seq Scan + 外部ソート（ディスク5MB書き出し）
```

**70倍の差**。OFFSET は「読み飛ばす行を実際に読む」ため、深いほど線形に遅くなる。さらにプランナが「どうせ大量に読むなら」と **Seq Scan + 全件ソート**に切り替えており、メモリに収まらず**ディスクへ退避**（`external merge`）している。

→ **seek（キーセット）ページネーション**で解消できる（#63）。

### 2. キーワード検索の Seq Scan

`ILIKE '%00042%'` は**前方一致でないため B-tree が使えない**（索引は「先頭から順に並んでいる」ので、途中に現れる文字列は探せない）。結果、5万行すべてを読んで捨てている。

→ 対策候補: **pg_trgm 拡張 + GINインデックス**（3文字単位の分割で部分一致を索引化）。ただし索引サイズが増えるため、**キーワード検索が主要導線になってから**判断する（#66）。

### 3. スキル検索が GIN を使っていない

`@> ARRAY['Go']` は 0.10ms と速いが、実行計画を見ると **`projects_status_created_at_idx`（B-tree）を使い、スキルは Filter で捨てている**。GIN（`projects_required_skills_idx`）は選ばれていない。

理由: `LIMIT 20` があるため、プランナが「新しい順の索引を辿って20件見つかった時点で止める方が速い」と判断したため。実際その通りで、**この形では GIN は不要**。一方 #61 で計測した `count(*)` を伴うクエリでは GIN が選ばれた（`Bitmap Index Scan`・4.08ms）。

→ **同じ索引でもクエリの形で使われ方が変わる**という好例。GIN が無駄というわけではなく、「件数集計」と「先頭N件」で最適な戦略が違う。

### 4. `count(*)` のコスト

`Index Only Scan` で 4.09ms。PostgreSQL は MVCC のため**「行数」を保持しておらず、条件に合う行を数え上げる**必要がある（MySQL の MyISAM のような即答はできない）。

→ 現状は許容範囲。件数が100万規模になったら「概算値（`reltuples`）を返す」「無限スクロールにして総件数を出さない」等の設計変更を検討する。
