## Phase0 #6: Next.js雛形＋Tailwind v4／shadcn/ui導入

### 何をした
create-next-app（Next.js 16 / React 19 / TS / App Router / src構成 / Tailwind v4）を `web/` に導入し、`(auth)`/`(main)` ルートグループを維持。shadcn/ui（radix基盤・Novaプリセット）を init し Button をトップに配置。ダークモードは方針として除去（`.dark` トークン・`@custom-variant dark` を削除）。

### 概念
- **layout.tsx と page.tsx**: layoutは共通骨格、pageが children に差し込まれる（コンポジションのルーティング版）。metadata は Server Component だから宣言できる
- **Tailwind v4**: `tailwind.config.js` が原則不要になり、`@import "tailwindcss"` と CSS内の `@theme` で設定する方式に変わった（v3の記事を読むときは注意）
- **utility-first**: CSSに命名して書く代わりに `className` にユーティリティを並べる。命名コスト・CSSとHTMLの往復が消える
- **shadcn/ui のコピーイン方式**: npm依存ではなく `src/components/ui/` に**コードとしてコピーされる**。node_modules のブラックボックスではなく自分のコードなので、自由に改造できる（Button のスタイルを直接編集できる）
- **デザイントークン（CSS変数）**: `--primary` 等のセマンティックな変数を `@theme inline` で Tailwind のクラス（`bg-primary`）に接続。#7 でブランドカラーに上書きすればアプリ全体に反映される
- **cn() ヘルパー**（`lib/utils.ts`）: clsx（条件付きクラス結合）+ tailwind-merge（後勝ち解決）。`cn("px-4", isActive && "bg-primary")` の形で使う
- **AGENTS.md**: 最新CNAが生成するAIエージェント向け注意書き（同梱docsを読め）。Next.jsの進化が学習データより速い時代の安全装置

### ✅ベストプラクティス
- 雛形のデモコンテンツは最初に全削除して最小状態から積む
- ダークモード非対応なら `dark:` プレフィックスを書かない・`.dark` トークンを残さない（中途半端が一番バグる）
- shadcn コンポーネントは `components/ui/`、自作部品は `components/` 直下で区別

### ⚠️アンチパターン
- page.tsx にロジックを盛る
- Tailwind v3 の設定ファイル方式を v4 に持ち込む
- shadcn を「UIライブラリ」と誤解して node_modules 感覚でバージョンアップを待つ（自分のコードなので自分で育てる）

### 理解度チェック
- [ ] layout と page の関係を children の言葉で説明できる
- [ ] shadcn/ui が npm ライブラリと本質的に違う点を説明できる

## Phase0 #7: web認証（BFF・httpOnly Cookie・login/signup画面）

### 何をした
デザイントークン適用（#1d4ed8・Noto Sans JP）→ (auth)レイアウト → BFF（Route Handler `/api/auth/*`）→ signup/login画面（useState＋HTML標準検証）。JWTはNext.jsサーバーでhttpOnly Cookieに変換し、ブラウザにトークンを渡さない。

### アーキテクチャ
```
ブラウザ(lib/authClient) → /api/auth/*(BFF) → lib/api(server-only) → Go API
                               └ token → httpOnly Cookie（sameSite=lax・maxAge=JWT expと同期）
```

### 概念
- **BFF (Backend for Frontend)**: フロント専用の裏方サーバー。認証情報の変換（token→Cookie）・API集約・バックエンド隠蔽を担う。今回はNext.jsのRoute Handlerで実装
- **httpOnly Cookie**: クライアントJSから読めないCookie。XSSを食らってもトークンが盗めない（localStorage保存がアンチパターンな理由）
- **server-only パッケージ**: importした瞬間にクライアント側ビルドをエラーにする番人。「サーバー専用コードの漏れ」をコンパイル時に防ぐ
- **判別可能ユニオン**: `{ok:true} | {ok:false; error}` 型。Goの `(結果, error)` ペアのTS版。分岐すると型が絞られる
- **`"use server"` の正体**: Server Actions（クライアントから呼べるサーバー関数=RPC）の宣言であり、`"use client"` の対称ではない。Server Componentは無印がデフォルト
- **`has-[:checked]:`**: CSS `:has()` の Tailwind 記法。中のradioの状態で親labelをスタイリング（選択タイルUI）

### 設計判断ログ（面接で語れる）
- **REST + fetch 継続**: axiosはNext.jsのfetch拡張（キャッシュ統合）に乗らない。GraphQLは「複数クライアント×複雑データ×専任チーム」が揃って初めて回収できる投資で、本作は条件を満たさない。型安全はOpenAPIスキーマ駆動（拡張フェーズ）で獲得予定
- **BFF実装はRoute Handler**（Server Actions不採用）: 仕組みを手で書いて理解する学習優先。API本数が増えて辛くなったら再設計（読み取りはRSC直fetchでBFF不要・汎用プロキシ・コード生成・Server Actions再検討）。参考実装it-support-serviceは同じBFF役をServer Actions＋OpenAPI生成クライアントで実現している
- **認証フォームはRHF不使用**: 2〜3フィールド・検証の正はサーバー側のため、useState＋HTML標準検証（required/minLength/type=email）で十分。RHF+ZodはPhase 2の案件掲載フォーム（複数ステップ・下書き保存）でデビュー
- **命名規則**: 自作コンポーネント=PascalCase／shadcn生成物(components/ui)=kebab-case（CLI準拠）／lib・hooks=camelCase

### ✅ベストプラクティス
- 送信中はボタン無効＋文言変更（二重送信防止）。成功時はsubmittingを戻さず遷移完了までロック
- エラーは `role="alert"` でスクリーンリーダーにも通知・Goの設計済みメッセージをそのまま中継
- CookieのmaxAgeとJWTのexpを揃える（片方だけ生き残るズレを防ぐ）
- autoComplete を用途で使い分け（new-password / current-password / email）

### ⚠️アンチパターン
- トークンをlocalStorageやレスポンスbodyでブラウザに渡す
- コンポーネントに直接fetchを書く（lib/集約ルール違反）
- `redirect()` をtry/catchで包む（NEXT_REDIRECT例外が握り潰される）※Server Actions採用時の注意

### 理解度チェック
- [ ] ブラウザに一度もトークンが渡らない流れを図で説明できる
- [ ] BFFが必要になる理由（直接Go呼び出しでは何が困るか）をCookieのオリジンの観点で言える
- [ ] server-onlyが防ぐ事故を説明できる
- [ ] RHFを使わなかった判断基準（どうなったら使うか）を言える

## Phase0 #8: 認証ガード（(main)レイアウト・共通ナビ）

### 何をした
`lib/auth.ts` の `getCurrentUser()`（Cookie→GET /me検証→ユーザー情報 or null）を土台に、`(main)/layout.tsx` で未ログインを `redirect('/login')`。共通ヘッダー（ロゴ・案件一覧ナビ・email/roleバッジ・ログアウト）を実装し、`/projects` プレースホルダとトップのログイン状態分岐を追加。

### 概念
- **レイアウトガード**: (main)/layout.tsx に認証チェックを1回書けば配下全ページが保護される（各ページに書かない）。ルートグループが「URLを変えずに保護境界を作る」道具になる
- **RSCの `redirect()`**: Server Component内で呼ぶとレンダリングを中断してリダイレクト応答を返す。内部は例外throw（try/catch で包まない）
- **RSC→GoのBearer転送**: 読み取りはBFFルート不要。RSCがサーバー上で cookies()→Bearer付きfetch できる（「読み取り=RSC・書き込み=サーバー経由」の読み取り側の実例）
- **ガードの判定は /me に委譲**: Cookie有無でなくGoの検証（署名・exp・alg）を単一の真実にする。フロントでJWTをデコードして検証した気にならない
- **cookies() と動的レンダリング**: cookies() を使うルートは自動的に動的（ƒ）になる。リクエストごとにユーザーが違うので当然静的化できない
- **middleware.ts との比較**: middlewareは全リクエストの入口で走る（エッジ実行・軽い処理向き）。「Cookieが無ければ/loginへ」の粗いガードには適するが、外部API検証のような重い処理には不向き。レイアウトガードは「そのUIツリーを描く直前」の確実な最終防衛線。実務では併用（middleware=早期リダイレクト・レイアウト=確実な検証）もある。Stage 1 は単純さ優先でレイアウト一本

### ✅ベストプラクティス
- 認証チェックの結果は null に潰して呼び出し側の分岐を単純に（理由の場合分けを持ち込まない）
- ナビの現在地・roleバッジなどの表示情報は、ガードで取得済みの user をそのまま使う（追加フェッチしない）

### ⚠️アンチパターン
- 各ページに認証チェックをコピペする（漏れが即事故）
- クライアント側ガード（useEffectでリダイレクト）だけに頼る：一瞬保護ページが見える・JSを切れば素通し
- Cookieの存在チェックだけで「ログイン済み」扱い

### 理解度チェック
- [ ] レイアウトガードが配下全ページに効く仕組みを説明できる
- [ ] middleware.ts 方式とのトレードオフを言える
- [ ] /projects が ƒ（動的）になる理由を言える
- [ ] クライアント側ガードだけではダメな理由を2つ言える

## Phase0 #8 追記: ルートグループ再編（(public)/(guest)/(authenticated)）と middleware の判断

### 何をした
ルートグループを「画面の種類」でなく**アクセス制御の境界**で3分割に再編。`(auth)`→`(guest)`（未ログイン専用・ログイン済みは/projectsへ送るガードを新設）、`(main)`→`(authenticated)`（要ログイン）、LPは`(public)`へ移動。CLAUDE.md・rules・READMEの記述も同期。

### 概念
- **グループ名＝アクセスポリシー**: フォルダ名を見ただけで「誰が入れるか」が分かる。新ページの置き場所に迷わない（認可の設計をディレクトリ構造で表現）
- **guestガード**: ログイン済みユーザーがlogin/signupを開いたら/projectsへ。UX改善＋「ログイン済みで再ログイン」の混乱防止
- **middleware.ts を今は入れない判断**: レイアウトガードで機能要件は満済。middlewareの利点（エッジでの早期リダイレクト）は本番規模で効く話で、学習初期は「ガードが2箇所」の追いにくさが上回る。保護グループが増えた/無駄リクエストを削りたくなったら matcher 込みで導入を再検討

### ⚠️アンチパターン
- URLの見た目でグループを分ける（/auth/xxx のようにURLに漏らすためにグループを使わない。グループはURLに現れないのが利点）
- ガードをグループlayout以外の場所に散らす

## Phase0 #24: Prettier 設定＋ESLint連携

### 何をした
`.prettierrc`（semi:false・singleQuote:true）と `.prettierignore` をコミットし、エディタ依存だった整形スタイルをリポジトリの設定として再現可能に。`eslint-config-prettier` をflat configの最後に追加してESLintの整形系ルールを無効化。`format`/`format:check` スクリプトを追加し全ファイルを一括正規化。

### 概念
- **linterとformatterの分業**: ESLint=コード品質（バグの芽・誤用）、Prettier=整形（見た目）。ESLintに整形をやらせると2つのツールが同じ行を取り合って喧嘩する
- **eslint-config-prettier**: ESLint側の「整形に関するルール」だけを全部offにする設定。**必ず設定配列の最後**に置く（後勝ちで上書きするため）
- **設定をコミットする意味**: エディタの個人設定に依存した整形は、クローン先・チームメンバー・CIで再現されない。`.prettierrc` がスタイルの単一の真実

### ✅ベストプラクティス
- lockファイル・生成物（.next等）は .prettierignore で除外
- 導入時に `format` で全ファイル一括正規化し「整形だけのdiff」を1コミットに隔離する

### ⚠️アンチパターン
- ESLintの整形系ルール（semi等）とPrettierの併用（無限に直し合う）
- 機能変更と整形を同じコミットに混ぜる（レビューで本質的な変更が埋もれる）

- [ ] ESLintとPrettierの役割分担を説明できる

## Phase0 #26: Vitest + Testing Library（テスト基盤と見本）

### 何をした
Vitest（jsdom・tsconfigPathsネイティブ解決）＋Testing Library＋user-eventを導入し、LoginFormの見本テスト2本（失敗時のエラー表示・成功時の遷移と二重送信防止）を作成。web-ciにTestステップを追加。依存競合（shadcn CLIパッケージ vs @vitejs/plugin-react@6のBabel8系）は plugin-react@5 へのダウングレードで解決。

### 概念
- **Testing Libraryの思想**: 実装詳細（state・関数名）でなく「ユーザーから見える振る舞い」をテストする。`getByRole('button', {name})` / `getByLabelText` で取得＝a11yが正しいほどテストが書きやすい（同じ方向を向く）
- **vi.mock + vi.hoisted**: vi.mockはファイル先頭に巻き上げられるため、参照するモック関数は vi.hoisted で先に生成。lib/に通信を集約した設計(#7)のおかげで login 1関数の差し替えだけでテスト可能
- **findByRole**: 非同期に現れる要素を待って取得（get=即時・query=無くてもnull・find=待つ）
- **userEvent**: fireEventより実挙動に近い（type はキー入力を1文字ずつ再現）
- **afterEach(cleanup)**: グローバル設定を使わない場合は明示的にDOM破棄（テスト間汚染防止）

### ✅ベストプラクティス
- コンポーネントと同じ場所に .test.tsx を置く（コロケーション）
- role="alert" の検証はUI仕様とa11y仕様を同時にテストしている
- 依存追加で競合したらログの依存チェーンを読み、最小の変更（1パッケージのメジャー選択）で解決する

### ⚠️アンチパターン
- 内部stateやclassNameでのアサーション（リファクタで壊れる脆いテスト）
- fetchを直接モック（lib集約を飛び越えるとテストが実装詳細に癒着）

## Phase0 #30: error.tsx / loading.tsx / not-found.tsx（境界の見本）

### 何をした
(authenticated) に error.tsx（再試行つきエラー境界）と loading.tsx（Skeletonフォールバック）、app直下に not-found.tsx を配置。shadcn skeleton を追加。

### 概念
- **error.tsx = エラー境界**: 同セグメント以下のページで throw されたエラーを捕まえ、アプリ全体のクラッシュを画面単位の失敗に限定する。React の Error Boundary（クラスコンポーネントの仕組み）を App Router がファイル規約に昇格させたもの。**クライアント側の仕組みなので 'use client' 必須**
- **error.tsx は同階層の layout を包まない**: 境界は「layoutの内側・pageの外側」に挟まる。layoutで起きたエラーは1つ上の error.tsx が受ける（ヘッダーは生きたままコンテンツ部だけエラー表示になる）
- **reset()**: 境界内を再レンダリングして復帰を試みる。一時的な失敗（ネットワーク断など）なら再試行で直る
- **loading.tsx = 自動Suspense**: page を `<Suspense fallback={<Loading/>}>` で包んだのと同等。サーバーがデータ取得している間、先にスケルトンが届く（streaming）
- **not-found.tsx**: 存在しないURL＋`notFound()` 呼び出しの両方で表示される
- **スケルトンは「次に来る画面の形」を予告する**: スピナーより体感が速い（レイアウトシフトも防ぐ）

### ✅ベストプラクティス
- エラー文言は具体的な内部情報を出さない（メッセージはユーザー向け・詳細はconsole/監視へ）
- スケルトンは実画面のレイアウトに近い形にする（#10で一覧が決まったら合わせて調整）

### ⚠️アンチパターン
- error.tsx を置かず1コのエラーで画面全体が白画面になる
- エラー境界に error.message をそのまま表示（内部情報の漏えい）

### 理解度チェック
- [ ] error.tsx に 'use client' が必須な理由を言える
- [ ] reset() が何をするか言える
- [ ] loading.tsx と Suspense の関係を言える

## Phase1 #46: プロフィール画面（React Hook Form + Zod デビュー）

### 何をした
`/profile`（(authenticated)）でRSC取得→role別フォーム（企業/人材）を表示。RHF + Zod（standardSchemaResolver）を初導入。書き込みはBFF（/api/profile）経由でPUT。ヘッダーに導線追加。

### 概念
- **React Hook Form の非制御方式**: `register('name')` が name/onChange/ref をまとめて渡す。入力のたびに state を更新しないため**キー入力ごとの再レンダリングが起きない**（フィールドが多いほど効く。#7のuseState方式との対比）
- **Zod と型の単一の真実**: `z.infer` でスキーマから型を導出。バリデーションルールと型定義がズレない
- **`z.input` と `z.output`**: `transform` があるスキーマは入力型と出力型が別物。skills はフォームで string（カンマ区切り）→ 送信時 string[] へ変換。`useForm<入力型, unknown, 出力型>` の3型引数で接続する
- **standardSchemaResolver**: Zod 4 は Standard Schema 準拠になったため、zodResolver でなく汎用リゾルバで繋ぐ（valibot等へ乗り換えても同じAPI）
- **二重バリデーション**: フロント（Zod）=即時フィードバック・UX／サーバー（Go）=最後の防衛線・セキュリティ。文言を揃えると体験が一貫する
- **`noValidate`**: ブラウザ標準検証を止めてZodに一本化（2種類のエラー表示が混ざるのを防ぐ）
- **`handleSubmit(onSubmit)`**: 検証通過時のみ onSubmit を呼ぶ。ハンドラ内では検証を気にしなくてよい
- **`formState.isSubmitting`**: 送信中フラグがRHF標準で手に入る（#7では自前useStateだった）
- **配列入力の設計判断**: タグUIは実装コストが高いため、カンマ区切り1入力＋`transform`で配列化。API↔フォームの相互変換（joinSkills / splitSkills）を lib に置く

### ✅ベストプラクティス
- RSCが取得した値をそのまま `defaultValues` に渡す（未作成なら空オブジェクト）
- 保存成功後は `router.refresh()` でRSCを再実行し表示を最新化
- クライアント検証エラーとサーバー由来エラーを別々のstateで持ち、どちらもフィールド近傍/フォーム下に `role="alert"` で表示

### ⚠️アンチパターン
- フロント検証だけで安心する（curlで直接叩かれる。サーバー検証が本体）
- スキーマに server-only を付ける（クライアントから import できなくなる）
- 依存追加後にDockerコンテナ側で npm install せず「モジュールが見つからない」で消耗する（node_modulesが遮蔽ボリュームのため。ローカル直起動運用が無難）

### 理解度チェック
- [ ] RHFの非制御方式が再レンダリングを減らす仕組みを説明できる
- [ ] z.input と z.output が分かれる理由を skills の例で説明できる
- [ ] フロントとサーバーで同じ検証を書く理由を役割の違いで説明できる

## Phase1 #10: 案件一覧・検索・詳細・掲載フォーム

### 何をした
人材側（`/talent/projects` 一覧＋検索＋ページネーション、`/talent/projects/[id]` 詳細）と企業側（`/company/projects` 管理、`/company/projects/new` 掲載フォーム）を実装。5万件のデータに対して動作。

### 概念
- **検索条件をURLに持たせる**: state ではなく URL クエリに持つと、(1)共有できる (2)ブラウザバックが効く (3)**RSCが `searchParams` で直接受け取れる**（クライアントでの再fetchが不要）。条件変更→URL変更→RSC再実行→新しいHTML、という流れでクライアントに検索結果の state を持たない
- **`searchParams` / `params` は Promise**（Next.js 15+ で非同期API化）。`await` が必要
- **動的ルート `[id]`**: フォルダ名の角括弧がURLの可変部分になる。Go側の `r.PathValue` と対
- **`notFound()`**: 例外throwで `app/not-found.tsx` を表示。この行より下では型が非nullに絞り込まれる
- **`generateMetadata`**: 動的なページタイトル。同一リクエスト内の同じfetchは**自動で重複排除**されるため、page と metadata で同じ関数を呼んでもHTTPは1回
- **ページャの責務分担**: 検索フォームは「条件を変えたら page を1に戻す」／ページャは「条件を保ったまま page だけ変える」。逆にすると3ページ目で絞り込んで空になる事故が起きる
- **非制御コンポーネント（`defaultValue` + FormData）**: URLが真実の情報源なので、入力中の値をReactが管理する必要がない
- **Zod の `refine` によるクロスフィールド検証**: `path: ['hourly_rate_max']` でエラーを特定フィールドに紐づけられる

### ✅ベストプラクティス
- 空欄はURLに載せない（`?skills=&q=` のようなノイズを防ぐ）
- DBの `0=未設定` を「応相談」など**意味のある言葉に翻訳**して表示する
- `whitespace-pre-wrap`（改行保持）と `break-words`（横スクロール防止）をユーザー入力の表示に付ける
- `tabular-nums` で数値の桁揃え（一覧の見た目が安定する）

### ⚠️アンチパターン
- 検索条件を useState に持つ（共有・戻る・RSC連携をすべて失う）
- 条件変更時にページ番号を引き継ぐ（結果が空のページに着地する）
- 未設定を `0円` とそのまま表示する

### 理解度チェック
- [ ] 検索条件をURLに持たせる利点を3つ言える
- [ ] 検索フォームとページャで page の扱いを変える理由を言える
- [ ] `notFound()` が型の絞り込みに効く理由を言える

## Phase1 #70: UI部品基盤の拡充

### 何をした
shadcn/ui に badge / select / sonner / separator を追加し、自前実装（`<span>` のタグ表示・生の `<select>`）を置き換え。`PageHeader` / `EmptyState` を作成して8画面の書式を統一。余白・タイポのスケールを `docs/デザインシステム.md` に明文化。

### 概念
- **モジュラースケール**: 余白や文字サイズは「任意の値」ではなく決まった段階（12/14/16/18/24・4/8pxグリッド）から選ぶ。ばらつきが「揃っていない感じ」の正体
- **入力欄は16px以上**: モバイルSafariは16px未満のinputにフォーカスすると**自動ズーム**する（意図しない拡大の原因）
- **Radix Select と RHF の接続**: shadcn の Select は `<select>` ではなく button+ポップオーバーのため `register`（DOMにrefを刺す）では繋がらない。**`Controller`** で制御コンポーネントとして扱う
  - `register` = 非制御（input / textarea）／`Controller` = カスタムUI部品
- **アイコンの扱いは「意味を持つか装飾か」で変わる**: 装飾なら `aria-hidden="true"`（意味はテキストが担う）、アイコンのみのボタンなら `aria-label` が必須
- **空状態は最初に見る画面**: 新規登録直後のユーザーが最初に出会うのは空の一覧。「何も無い」で終わらせず、理由と次の行動を置く。`EmptyState` は icon を必須プロパティにして型で強制した
- **見出しの集約**: h1 を `PageHeader` に集約すると、見出し階層の管理が1か所になり、書式のばらつきも消える

### ✅ベストプラクティス
- 共通部品は「使うと自然に規約が守られる」形にする（PageHeader を使えば見出し書式が揃う・EmptyState を使えば導線が置かれる）
- 同じ「空」でも文脈で言葉を変える（検索0件=「条件をゆるめては」／未作成=「最初の案件を掲載する」）
- 数値表示は `tabular-nums`（桁変動でレイアウトが揺れない）

### ⚠️アンチパターン
- 生の `<select>`（OS依存の見た目・キーボード操作やaria を自前実装することになる）
- 自前のタグ表示（`rounded-full bg-secondary` の直書き）を各所にコピペする
- 空状態を1行のテキストで済ませる

### 理解度チェック
- [ ] モジュラースケールを使う理由を説明できる
- [ ] `register` と `Controller` の使い分けを言える

### ✅ベストプラクティス
- 入口（認証）から出口（ダッシュボード）までロールの導線を一貫させる
- 相互リンク（「人材の方はこちら」）を置き、間違えた入口からでも移動できるようにする

- ロールをフォームのラジオで選ばせる（URLで決まるなら入力させない）
- 画面ごとにフォームコンポーネントを複製する（改善が分散する）

- **条件チップ**: URLのキー（`rate_min=8000`）を人が読める日本語に変換して表示し、個別に解除できるようにする。フォームを開いて該当欄を消す手間が省ける

## Phase1 #74: フォームUXの改善（トースト・エラー処理）

### 何をした
5つのフォーム（プロフィール2種・案件掲載・ログイン・新規登録）に、トースト通知・エラーサマリ・スピナー付き送信ボタン・必須マーク・離脱確認を適用。共通部品として `SubmitButton` / `FormErrorSummary` / `RequiredMark` / `useUnsavedChangesWarning` を作成。

### 概念
- **フィードバックの3層**: 一時的な結果=トースト／項目ごとの問題=フィールド直下／全体の問題=上部のサマリ。**同じ情報を2箇所に出さない**（本文中の「保存しました」を削除しトーストに一本化。視線が分散するため）
- **トースト vs インライン**: トーストは「消えてよい一時的な通知」、インラインは「直すまで残るべき情報」。保存成功はトースト、バリデーションエラーはインライン、が基本
- **エラーサマリの2つの工夫**: (1)`href="#id"` で該当フィールドへジャンプ（長いフォームで有効） (2)内部名（`hourly_rate_min`）ではなく画面上のラベル（「時給の下限」）を表示
- **`role="alert"`**: 出現した瞬間にスクリーンリーダーが読み上げる。送信直後の重要情報に付ける
- **送信中は3点セット**（無効化＋スピナー＋文言変更）。文言だけでは変化に気づきにくい
- **RHF の `shouldFocusError`**: 既定で有効。送信失敗時に最初のエラーフィールドへ自動フォーカスする
- **`beforeunload` の制約**: カスタムメッセージは指定できない（悪用防止のためブラウザ標準文言に固定）。Next.js のクライアント遷移（Link）は捕捉できないため、ブラウザ操作による離脱のみを対象にした
- **`RequiredMark`**: `*` だけでは意味が伝わらないため、`aria-hidden` の記号＋ `sr-only` の「必須」を組み合わせる

### ✅ベストプラクティス
- 状態を伝えるときは「視覚・動き・文言」を重ねる（単一手段に頼らない）
- できない制約はコードのコメントに残す（beforeunload のクライアント遷移非対応など）

### ⚠️アンチパターン
- 保存成功をトーストと本文中テキストの両方に出す（どちらを見ればよいか分からない）
- エラーサマリに内部フィールド名を出す
- 送信中の表現を文言だけにする

### 理解度チェック
- [ ] トーストとインライン表示の使い分けを言える
- [ ] エラーサマリを上部に置く理由を言える
- [ ] `beforeunload` の2つの制約を言える

## Phase1 #75: モバイル対応とアクセシビリティ点検

### 何をした
ヘッダーのナビをモバイルで Sheet に格納し、スキップリンクを追加。コントラスト比を計算で検証し、見出し階層・フォーカス・aria を点検して `docs/デザインシステム.md` に結果を記録した。

### 概念
- **`focus-visible` と `focus` の違い**: `focus` はマウスクリックでも発火するためリングが邪魔になる。`focus-visible` は**キーボード操作時のみ**発火する（ブラウザがヒューリスティックに判定）。shadcn は既定で `focus-visible` を使っている
- **スキップリンク**: `sr-only`（視覚的に隠す）→ `focus:not-sr-only`（Tabで現れる）のパターン。キーボード利用者が毎回ナビを通過しなくて済む
- **Sheet（ドロワー）が自前実装より安全な理由**: フォーカストラップ（開いている間、背後にフォーカスが移らない）・Esc で閉じる・背景スクロール抑止を Radix が実装済み
- **コントラスト比の計算**: 相対輝度（sRGB→リニア変換して重み付け）の比。本文は 4.5:1、大文字は 3:1 が AA 基準。**計算で検証できるので目視に頼らない**
- **`CardTitle` は div**: shadcn の CardTitle は見出しタグではないため、認証画面のようにカードがページの主題である場合、**そのままだとページに h1 が存在しない**。`asChild`（Radix Slot）を足して h1 に差し替えた
- **`aria-current="page"`**: ナビの現在地をスクリーンリーダーに伝える（視覚的なハイライトだけでは伝わらない）

### ✅ベストプラクティス
- a11y は「対応した」で終わらせず**点検結果を表で記録**する（新しい部品を足すときのチェックリストになる）
- 色を決めたらコントラストを計算する（`muted-foreground` は 4.53:1 と余裕が小さいことが分かり、これより薄い色を作らない指針になった）
- 既製部品（Radix）に任せられる部分は自前実装しない（フォーカストラップ・Escは自分で書くとバグる）

### ⚠️アンチパターン
- `focus` でリングを出す（マウス操作時に邪魔）／`outline: none` でリングを消す
- アイコンのみのボタンに代替テキストを付けない
- 見た目のためだけに見出しレベルを選ぶ（h1がない・階層を飛ばす）

### 理解度チェック
- [ ] `focus-visible` と `focus` の違いを言える
- [ ] スキップリンクの実装パターン（sr-only → focus:not-sr-only）を説明できる
- [ ] Sheet を自前ドロワーより優先する理由を3つ言える

## Phase1 #86: 応募・応募履歴画面（多層の責務分担）

### 何をした
案件詳細からの応募・応募履歴・選考操作（承諾／辞退／取り下げ）を実装した。あわせて #85 で必須化した表示名の入力欄を追加し、壊れていたプロフィール保存を直した。

### 概念

#### 同じ知識が2箇所にあるとき、どちらが「正」かを決める
状態遷移のルールは **Go の遷移表**と**フロントの `actionsByStatus`** の両方にある。重複に見えるが役割が違う。

| | Go の遷移表 | フロントの `actionsByStatus` |
| --- | --- | --- |
| 役割 | **正しさの担保** | **ボタンの出し分け（UX）** |
| 破られたら | データが壊れる | 押しても409で弾かれる（無害） |

- フロントが古くてもデータは壊れない／書き忘れてもボタンが出ないだけ
- 逆に**フロントを信じてAPIが検証を省くと、curl 1発でどんな状態にも飛べる**。この非対称性を意識する
- BFF にも遷移の判定は書かない（画面・BFF・APIで三重に持つと、遷移表を更新したのに BFF が古いという不整合が起きる）

#### BFF は URL を翻訳してよい
クライアントに自然な形（`POST /api/applications`）と、API の REST な形（`POST /projects/{id}/applications`）は**一致していなくてよい**。BFF がその翻訳を担う。
- **URLに埋め込む値は型を確定させてから使う**（`Number.isInteger` チェック）。文字列のまま埋めるとパスが壊れる

#### `useTransition` — サーバー再取得の完了を追う
`router.refresh()` は非同期でサーバーコンポーネントを取り直すが、**その完了は `useState` では追えない**。`startTransition` で包むと React が `pending` で教えてくれる。
```tsx
const [pending, startTransition] = useTransition()
const [sending, setSending] = useState(false)
const disabled = sending || pending   // 送信中 かつ 再取得中 は押せない
```
- **失敗時も `router.refresh()` する**: 409 が返るのは「表示していた状態が古かった」ケースが大半。エラーを出して終わりにせず、正しい状態を見せる

#### リンクによる絞り込み（RSCのまま完結）
`<Link href="?status=applied">` を踏むと `searchParams` が変わり、サーバーが新しい一覧を返すだけ。**`"use client"` も状態管理も不要**。リロード・共有・戻るで再現できる
- 選択中は `aria-current="page"`（色だけに頼らない）
- ラベルは `applicationStatusLabel()` から取り、バッジと絞り込みで表記がズレないようにする

#### 型で網羅を強制する
```ts
export const APPLICATION_STATUSES = ['applied', 'offered', ...] as const
export type ApplicationStatus = (typeof APPLICATION_STATUSES)[number]   // ユニオン型を生成
const statusMeta: Record<ApplicationStatus, {...}>       // 状態を足すとコンパイルエラー
const actionsByStatus: Partial<Record<ApplicationStatus, Action[]>>  // 終端状態はキーを持たない
```
- `as const` + インデックスアクセスで**値の一覧と型を二重管理しない**
- `Partial<Record<...>>` が「終端状態からは操作できない」を型で表現している（Go 側で終端が `from` に現れないのと同じ形）

#### UIで設計判断を伝える
- 表示名の欄に「**メールアドレスは公開されません**」と添える ＝ #85 でAPIがemailを返さないと決めた設計をユーザーに翻訳したもの
- 確認ダイアログの説明文には**結果を具体的に書く**（「承諾すると契約が成立します」）。「よろしいですか？」だけでは判断材料にならない
- 「辞退」（人材が断る）と「見送り」（企業が断る）は文字が似ているため、バッジに `description` を添えて誰の行為かを補う

### ✅ベストプラクティス
- 確認ダイアログは Radix（`AlertDialog`）を使う。`window.confirm` はフォーカス管理・スタイルが制御できない
- 破壊的操作は**結果を書いて確認**、処理中は**サーバー再取得の完了まで**無効化
- 割り切り（応募済み判定の上限100件）は**理由と影響をコメントに残す**

### ⚠️アンチパターン
- フロントの出し分けを正しさの担保だと考える
- BFF に業務ルールの判定を書く（真実が二重化する）
- エラーを出して画面を古いまま放置する
- 状態の一覧を型と配列で別々に管理する

## Phase1 #87: 企業の応募者管理（共通化の判断と意図的な割り切り）

### 何をした
企業が応募者を確認してオファー／見送りできる画面を作り、案件管理に応募件数と導線を追加した。これで**状態機械①が画面から一周する**（応募→オファー→承諾→成立）。

### 概念

#### 遷移表を2つの画面が別々の角度から写す

| 状態 | 人材の操作（#86） | 企業の操作（#87） |
| --- | --- | --- |
| applied | 取り下げ | **オファー** / 見送り |
| offered | **承諾** / 辞退 / 取り下げ | **なし** |

- 足すと Go の遷移表（6行）に戻る
- **`offered` に企業のエントリが無い**＝オファー後に企業が押せるボタンは1つも無い。「あとは相手の返事を待つだけ」が**ボタンの不在**として表現されている
- どちらかに相手ロールの操作が紛れてもデータは壊れない（API が 403/409 で止める）

#### 共通化するか、分けるか

| | `ApplicationStatusFilter` | `CompanyProjectCard` |
| --- | --- | --- |
| 人材版との違い | `basePath` **だけ** | 遷移先・表示情報・状態バッジ・件数 |
| 判断 | **共通化**（引数1つ） | **分ける** |

- 基準は「**違いがパラメータで表せるか**」。無理に共通化すると `<ProjectCard variant="company" showCount linkTo="applications" />` のような**フラグだらけの部品**になり、内部が分岐だらけになって片方の変更がもう片方を壊す
- **2箇所目を書く瞬間が切り出しどき**（コピーする前に共通化する）
- 分けたことで既存のバグも解消した: `ProjectCard` のリンク先が `/talent/projects/{id}` 固定で、**企業が自社案件をクリックすると人材側の画面に飛んでいた**

#### 同じ部品でも「誰が何のために見るか」で初期状態を変える
- 志望動機の `<details>`: 人材側は**閉じる**（自分が書いた文章）／企業側は **`open`**（選考で必ず読む）

#### 意図的な割り切りは3点セットで残す
案件一覧APIが応募件数を返さないため、案件ごとに応募一覧APIを叩いている（**fan-out ＝ N+1**）。許容した理由と直し方を残した。

1. **動くものを作る**（`Promise.all` で並列化＝待ち時間は合計でなく最大値／`limit=1` で total だけ受け取り転送量をほぼゼロに）
2. **なぜ許容できるかをコメントに書く**（自社の掲載案件数は通常数件〜数十件）
3. **いつ・どう直すかを Issue にして番号を残す**（#93）

→ 3つ揃って初めて「意図的な割り切り」になる。1だけなら**ただの N+1 バグ**

#### 表示の優先順位と情報の削り方
- 未対応（`applied`）の件数だけ `text-primary` で強調 ＝「**あなたが次にやること**」
- **未対応が0のときは括弧ごと出さない**（「0件が未対応」は情報として無意味でノイズ）
- 数字の一覧は `tabular-nums`（桁が揃って読みやすい）
- 一覧は**定量的な足切り情報を先、読む文章を後**（表示名 → 経験年数・スキル → 志望動機）

#### 相手に影響する操作の確認文
企業の操作は相手の心情に影響するため、**「相手に伝わる」ことを明示**する。
- 「相手に通知され、承諾されると契約が成立します。オファーは取り消せません。」
- 「相手に見送りとして伝わります。取り消して選考を再開することはできません。」

#### API の 404 をそのまま画面の 404 に翻訳する
他社の案件IDは API が 404（#85 で「403だと存在が漏れる」と決めた）。フロントは `notFound()` を呼ぶだけでよく、**「権限エラーか、存在しないのか」を分岐する必要がない**。API設計がフロントの複雑さを減らしている例。

### ✅ベストプラクティス
- 割り切りは**理由 + Issue番号**をコメントに残す
- **フラグだらけの共通部品を作らない**（分けるほうが安いことが多い）
- 状態の対応表は**ドメインごとに分ける**（案件の掲載状態と応募の選考状態は別物）

### ⚠️アンチパターン
- N+1 を「あとで直す」と思いながら何も残さない
- `variant` プロパティで役割の違う部品を1つにまとめる
- すべての `<details>` を一律で開く／閉じる

### 理解度チェック
- [ ] 人材側と企業側の操作表を足すと何になるか言える
- [ ] `offered` に企業の操作が無いことの意味を言える
- [ ] 共通化するか分けるかの判断基準を言える
- [ ] fan-out を許容した3つの根拠と、それでもIssueを立てた理由を言える

## Phase1 #98: 案件の編集・状態切り替え（層をまたいだ一貫性）

### 何をした
企業側の案件詳細・編集画面・掲載状態の切り替えを実装した。これで**案件のライフサイクルが画面から完結する**（下書き作成 → 編集 → 公開 → 募集終了 → 再募集）。

### 概念

#### API の設計判断を画面・文言まで貫く
#97 で「内容の編集」と「掲載状態の変更」をエンドポイントごと分けた判断が、4層すべてに現れている。

```
API   : PUT は status を SET 句に書かない
 ↓
BFF   : PUT に status が来ても、そのまま Go に流すだけ（判定しない）
 ↓
画面  : 編集フォームに公開設定を出さない
 ↓
文言  : 「掲載状態は変わりません（公開・終了は詳細画面から操作します）」
```

- **どこか1層が違う判断をするとユーザーが混乱する**（例: 画面に公開設定があるのに保存しても変わらない）
- **最下層のAPIが最も強い**: 画面やBFFが間違っても、SET句に無ければ status は変わらない

#### モードはフラグではなくデータの有無で表す
```tsx
export function ProjectForm({ project }: { project?: MyProject }) {
  const isEdit = project != null
```
- `mode="edit"` のようなフラグを別に受け取ると、**「mode=edit なのに project が無い」というありえない組み合わせが型として作れてしまう**
- データの有無だけで判定すれば、その矛盾が存在しない

#### 遷移表の写しは、型にドメインの事実が出る

| | 応募の操作（#86/#87） | 案件の掲載状態（#98） |
| --- | --- | --- |
| 型 | `**Partial**<Record<Status, Action[]>>` | `Record<ProjectStatus, Action[]>` |
| 理由 | **終端状態はキーを持たない** | **どの状態にも操作がある**（終端が無い） |
| ガード | `if (!actions) return null` が必要 | 不要 |

Go 側で `map[...]string` → `map[...]bool` にした事実が、TypeScript の型でも同じように表れている。

#### 確認ダイアログの基準はドメインで変わる
| | 応募の操作 | 掲載状態の操作 |
| --- | --- | --- |
| 取り消し | **すべて不可** | **すべて可能** |
| 確認の基準 | 取り消せないから全部に付ける | **相手（人材）に影響するか** |

| 操作 | 確認 | 理由 |
| --- | --- | --- |
| 公開する / 再募集する | なし | すぐ元に戻せる・相手に不利益がない |
| 募集を終了する / 非公開に戻す | あり | 人材から見えなくなる |

- **「破壊的操作には確認」を機械的に適用しない**。確認だらけにするとユーザーは読まずに押すようになる
- ルールの背後にある目的（**ユーザーが後悔する操作を防ぐ**）に立ち返ると、基準は状況で変わる

#### 確認文には「相手にどうなるか」と「取り返しがつくか」を書く
> 「人材の一覧から外れ、新しい応募を受け付けなくなります。**選考中の応募はそのまま残ります。あとで再募集できます。**」

企業が最も不安なのは「選考中の応募が消えるのでは」なので、そこに先回りして答える。取り返しがつくことを明示すると迷わず操作できる。

#### 導線の集約でリンクの入れ子を避ける
一覧のカードは全体が `<Link>` なので、**中にボタンを置くとリンクの入れ子**になる（HTMLとして不正・キーボード操作も壊れる）。
- 一覧 → **詳細**（1クリック）→ 各操作、という導線にした
- 結果として「案件に対してできること」が詳細ページに集約され、構造も分かりやすくなった

#### 機能を隠したら、代わりの場所を案内する
編集フォームから公開設定を消したので、ヘッダーに「掲載状態は変わりません（公開・終了は詳細画面から操作します）」と書いた。**無いことをバグと思わせない**。

#### 共通化は3つ目が出てから
`joinSkills`（配列 → カンマ区切り）は `profileSchema.ts` にも同じものがある。2つとも2行なので、それぞれのスキーマファイルに置いたまま（共通化すると import が増えるだけ）。3つ目が出たら検討する。

### ✅ベストプラクティス
- モードは**データの有無**で表す（ありえない組み合わせを作れなくする）
- UIから項目を消したら、**どこで操作するかを書く**
- 確認は**必要な操作にだけ**付ける
- 画面の並び順は**その画面に来る目的**の順にする（詳細ページは「掲載状態」を上に）

### ⚠️アンチパターン
- `mode` フラグと `data` を別々に受け取る（矛盾した状態が作れる）
- `<Link>` の中にボタンを置く
- 「破壊的操作には確認」を機械的に適用する（目的を見失う）
- 項目を消しただけで説明しない

### 理解度チェック
- [ ] API → BFF → 画面 → 文言 の4層で方針を揃える理由を言える
- [ ] `mode` フラグではなくデータの有無でモードを決める利点を言える
- [ ] `Record` と `Partial<Record>` の使い分けがドメインの何を表しているか言える
- [ ] 「公開する」に確認を付けなかった理由を言える

## Phase2 #107: 人材の契約・稼働報告画面

### 何をした
契約の一覧・詳細と、稼働報告の提出・再提出を実装した。**新しい概念はほぼ無く、#86〜#98 で確立したパターンの組み合わせ**で作れている。

| 部品 | 元にしたもの |
| --- | --- |
| 契約一覧・状態フィルタ | 応募履歴（#86）・`ApplicationStatusFilter`（#87で共通化） |
| `ContractActions` | `ApplicationActions`（#86）・`ProjectStatusActions`（#98） |
| 確認ダイアログの基準 | デザインシステムの規約（#98で書き直したもの） |
| BFF | `/api/applications/[id]/status`（#86） |

### 概念

#### 状態バッジが4つになった
| 部品 | 対象 | 値 |
| --- | --- | --- |
| `ApplicationStatusBadge` | 応募の選考 | 6 |
| `ProjectStatusBadge` | 案件の掲載 | 3 |
| `ContractStatusBadge` | 契約の進行 | 5 |
| `WorkReportStatusBadge` | 報告の確認 | 3 |

すべて `Record<Status, ...>` で定義（状態を足すとコンパイルエラー）。**別ドメインの状態は混ぜない**という判断を4回維持している。

**似た状態名はあえてラベルを変える**: 契約の `reviewing` は「検収待ち」、報告の `submitted` は「確認待ち」。両方「確認待ち」だと同じ画面に並んだとき区別できない。

#### 表示は共通化し、操作は差し込む
```tsx
<WorkReportList reports={...} renderActions={(report) => ...} />
```
稼働報告の一覧は企業・人材で同じものを表示する（**共有された記録なので視点で見え方を変えない**）。違うのは操作だけなので、`renderActions` で差し込む。
- **関数**にしているのは、**報告ごとに違うボタンを出す**必要があるため（差し戻された報告だけ「修正する」を出す）

#### RHF の型は1つ。モードでスキーマを切り替えられない
```tsx
// ❌ 型が合わない
resolver: standardSchemaResolver(isResubmit ? contentSchema : fullSchema)
```
`useForm<FormValues, ...>` は1つの型で固定されるため、フィールドが異なるスキーマは代入できない。

**解法は #98 の `ProjectForm` と同じ**——**値は持つが、入力欄は出さず、送信にも使わない**:
```tsx
resolver: standardSchemaResolver(workReportSchema)   // 常に週を含む
defaultValues: { week_start: report.week_start, ... } // 検証を通すため値は入れる
// 送信は hours と summary だけ（api も PUT では週を受け取らない）
```
**過去の解法を思い出せたのは、#98 のコメントに「なぜ status を残すのか」が書いてあったから**。

#### 確認ダイアログ：同じ操作でも状態によって文言を変える
「契約を中止する」は3つの状態から実行できるが、**失うものが違う**ため確認文を変えた。
- `active`: 「取り消して再開することはできません」
- `working`: 「**提出済みの稼働報告は記録として残りますが**、取り消して再開することはできません」
- `reviewing`: 「**企業が検収中です**。中止すると取引は完了せず…」

**確認文には副作用も書く**: 検収依頼には「**確認中は稼働報告を追加できません**」を明記。押す前に知らないと気づけない制約は、確認文で伝える。

#### 選べないものは選択肢に出さない
提出済みの週はセレクトから外す（すり抜けても API が409）。
**選べてしまうと「なぜエラーか」が分からない**。
```tsx
{weekOptions.length === 0 && <p>直近8週分はすべて提出済みです</p>}
```
**空のセレクトを黙って出さない**——選択肢が無いことにも理由を添える。

同じ理由で、**フォーム自体も稼働中のときだけ出す**（検収待ち・完了後に出すと「押せるのに失敗するボタン」になる）。

#### `"use client"` は状態を持つ葉だけ
`WorkReportList` はサーバーコンポーネントのまま保ち、開閉の状態を持つ「修正する」ボタンだけ `WorkReportEditor` として切り出した。

#### サーバー側の設計判断をユーザーに翻訳する
> この契約の条件は、承諾した時点の内容で固定されています（案件の掲載内容が変更されても影響しません）。

#103 のスナップショット設計を一文にしたもの。企業が案件を編集すると案件ページと契約ページで単価が違って見えるため、**説明が無いと「バグでは？」と思われる**。「仕様です」ではなく「**あなたが合意した条件は守られています**」というメッセージとして書く。

#### サーバー側で意味を1つに保った効果
差し戻し理由の表示は `{report.review_note && ...}` の判定だけで済む。
**#105 で「承認時は review_note を空にする」と決めた**ため、フロントで「status が rejected のときだけ」という条件が要らない。

### ✅ベストプラクティス
- 確認文には**副作用**も書く／**同じ操作でも状態で文言を変える**
- 選択肢は**選べないものを外し**、無いときは理由を添える
- **表示は共通化し、操作は差し込む**
- `"use client"` は**状態を持つ葉だけ**に切り出す

### ⚠️アンチパターン
- モードでスキーマを切り替える（RHFの型が破綻する）
- 空のセレクトを黙って表示する／押せるのに必ず失敗するボタンを出す
- 別ドメインの状態を1つの対応表にまとめる
- 同じラベルを違う概念に使う

### 理解度チェック
- [ ] 契約の「検収待ち」と報告の「確認待ち」でラベルを変えた理由を言える
- [ ] `renderActions` を関数にした理由を言える
- [ ] スキーマをモードで切り替えられない理由と解法を言える
- [ ] 「稼働を開始する」に確認を付けなかった理由を言える
