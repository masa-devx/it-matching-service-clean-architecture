## Phase0 #6: Next.js雛形＋Tailwind v4／shadcn/ui導入

### 何をした
create-next-app（Next.js 16 / React 19 / TS / App Router / src構成 / Tailwind v4）を `web/` に導入し、`(auth)`/`(main)` ルートグループを維持。shadcn/ui（radix基盤・Novaプリセット）を init し Button をトップに配置。ダークモードは方針として除去（`.dark` トークン・`@custom-variant dark` を削除）。

### 概念
- **layout.tsx と page.tsx**: layoutは共通骨格、pageが children に差し込まれる（コンポジションのルーティング版）。metadata は Server Component だから宣言できる
- **Tailwind v4**: `tailwind.config.js` が原則不要になり、`@import "tailwindcss"` と CSS内の `@theme` で設定する方式に変わった（v3の記事を読むときは注意）
- **utility-first**: CSSに命名して書く代わりに `className` にユーティリティを並べる。命名コスト・CSSとHTMLの往復が消える
- **shadcn/ui のコピーイン方式**: npm依存ではなく `src/components/ui/` に**コードとしてコピーされる**。node_modules のブラックボックスではなく自分のコードなので、自由に改造できる（Button のスタイルを直接編集できる）
- **デザイントークン（CSS変数）**: `--primary` 等のセマンティックな変数を `@theme inline` で Tailwind のクラス（`bg-primary`）に接続。#7 でブランドカラーに上書きすればアプリ全体に反映される
- **cn() ヘルパー**（`lib/utils.ts`）: clsx（条件付きクラス結合）+ tailwind-merge（後勝ち解決）。`cn("px-4", isActive && "bg-primary")` の形で使う
- **AGENTS.md**: 最新CNAが生成するAIエージェント向け注意書き（同梱docsを読め）。Next.jsの進化が学習データより速い時代の安全装置

### ✅ベストプラクティス
- 雛形のデモコンテンツは最初に全削除して最小状態から積む
- ダークモード非対応なら `dark:` プレフィックスを書かない・`.dark` トークンを残さない（中途半端が一番バグる）
- shadcn コンポーネントは `components/ui/`、自作部品は `components/` 直下で区別

### ⚠️アンチパターン
- page.tsx にロジックを盛る
- Tailwind v3 の設定ファイル方式を v4 に持ち込む
- shadcn を「UIライブラリ」と誤解して node_modules 感覚でバージョンアップを待つ（自分のコードなので自分で育てる）

### 理解度チェック
- [ ] layout と page の関係を children の言葉で説明できる
- [ ] shadcn/ui が npm ライブラリと本質的に違う点を説明できる

## Phase0 #7: web認証（BFF・httpOnly Cookie・login/signup画面）

### 何をした
デザイントークン適用（#1d4ed8・Noto Sans JP）→ (auth)レイアウト → BFF（Route Handler `/api/auth/*`）→ signup/login画面（useState＋HTML標準検証）。JWTはNext.jsサーバーでhttpOnly Cookieに変換し、ブラウザにトークンを渡さない。

### アーキテクチャ
```
ブラウザ(lib/authClient) → /api/auth/*(BFF) → lib/api(server-only) → Go API
                               └ token → httpOnly Cookie（sameSite=lax・maxAge=JWT expと同期）
```

### 概念
- **BFF (Backend for Frontend)**: フロント専用の裏方サーバー。認証情報の変換（token→Cookie）・API集約・バックエンド隠蔽を担う。今回はNext.jsのRoute Handlerで実装
- **httpOnly Cookie**: クライアントJSから読めないCookie。XSSを食らってもトークンが盗めない（localStorage保存がアンチパターンな理由）
- **server-only パッケージ**: importした瞬間にクライアント側ビルドをエラーにする番人。「サーバー専用コードの漏れ」をコンパイル時に防ぐ
- **判別可能ユニオン**: `{ok:true} | {ok:false; error}` 型。Goの `(結果, error)` ペアのTS版。分岐すると型が絞られる
- **`"use server"` の正体**: Server Actions（クライアントから呼べるサーバー関数=RPC）の宣言であり、`"use client"` の対称ではない。Server Componentは無印がデフォルト
- **`has-[:checked]:`**: CSS `:has()` の Tailwind 記法。中のradioの状態で親labelをスタイリング（選択タイルUI）

### 設計判断ログ（面接で語れる）
- **REST + fetch 継続**: axiosはNext.jsのfetch拡張（キャッシュ統合）に乗らない。GraphQLは「複数クライアント×複雑データ×専任チーム」が揃って初めて回収できる投資で、本作は条件を満たさない。型安全はOpenAPIスキーマ駆動（拡張フェーズ）で獲得予定
- **BFF実装はRoute Handler**（Server Actions不採用）: 仕組みを手で書いて理解する学習優先。API本数が増えて辛くなったら再設計（読み取りはRSC直fetchでBFF不要・汎用プロキシ・コード生成・Server Actions再検討）。参考実装it-support-serviceは同じBFF役をServer Actions＋OpenAPI生成クライアントで実現している
- **認証フォームはRHF不使用**: 2〜3フィールド・検証の正はサーバー側のため、useState＋HTML標準検証（required/minLength/type=email）で十分。RHF+ZodはPhase 2の案件掲載フォーム（複数ステップ・下書き保存）でデビュー
- **命名規則**: 自作コンポーネント=PascalCase／shadcn生成物(components/ui)=kebab-case（CLI準拠）／lib・hooks=camelCase

### ✅ベストプラクティス
- 送信中はボタン無効＋文言変更（二重送信防止）。成功時はsubmittingを戻さず遷移完了までロック
- エラーは `role="alert"` でスクリーンリーダーにも通知・Goの設計済みメッセージをそのまま中継
- CookieのmaxAgeとJWTのexpを揃える（片方だけ生き残るズレを防ぐ）
- autoComplete を用途で使い分け（new-password / current-password / email）

### ⚠️アンチパターン
- トークンをlocalStorageやレスポンスbodyでブラウザに渡す
- コンポーネントに直接fetchを書く（lib/集約ルール違反）
- `redirect()` をtry/catchで包む（NEXT_REDIRECT例外が握り潰される）※Server Actions採用時の注意

### 理解度チェック
- [ ] ブラウザに一度もトークンが渡らない流れを図で説明できる
- [ ] BFFが必要になる理由（直接Go呼び出しでは何が困るか）をCookieのオリジンの観点で言える
- [ ] server-onlyが防ぐ事故を説明できる
- [ ] RHFを使わなかった判断基準（どうなったら使うか）を言える

## Phase0 #8: 認証ガード（(main)レイアウト・共通ナビ）

### 何をした
`lib/auth.ts` の `getCurrentUser()`（Cookie→GET /me検証→ユーザー情報 or null）を土台に、`(main)/layout.tsx` で未ログインを `redirect('/login')`。共通ヘッダー（ロゴ・案件一覧ナビ・email/roleバッジ・ログアウト）を実装し、`/projects` プレースホルダとトップのログイン状態分岐を追加。

### 概念
- **レイアウトガード**: (main)/layout.tsx に認証チェックを1回書けば配下全ページが保護される（各ページに書かない）。ルートグループが「URLを変えずに保護境界を作る」道具になる
- **RSCの `redirect()`**: Server Component内で呼ぶとレンダリングを中断してリダイレクト応答を返す。内部は例外throw（try/catch で包まない）
- **RSC→GoのBearer転送**: 読み取りはBFFルート不要。RSCがサーバー上で cookies()→Bearer付きfetch できる（「読み取り=RSC・書き込み=サーバー経由」の読み取り側の実例）
- **ガードの判定は /me に委譲**: Cookie有無でなくGoの検証（署名・exp・alg）を単一の真実にする。フロントでJWTをデコードして検証した気にならない
- **cookies() と動的レンダリング**: cookies() を使うルートは自動的に動的（ƒ）になる。リクエストごとにユーザーが違うので当然静的化できない
- **middleware.ts との比較**: middlewareは全リクエストの入口で走る（エッジ実行・軽い処理向き）。「Cookieが無ければ/loginへ」の粗いガードには適するが、外部API検証のような重い処理には不向き。レイアウトガードは「そのUIツリーを描く直前」の確実な最終防衛線。実務では併用（middleware=早期リダイレクト・レイアウト=確実な検証）もある。Stage 1 は単純さ優先でレイアウト一本

### ✅ベストプラクティス
- 認証チェックの結果は null に潰して呼び出し側の分岐を単純に（理由の場合分けを持ち込まない）
- ナビの現在地・roleバッジなどの表示情報は、ガードで取得済みの user をそのまま使う（追加フェッチしない）

### ⚠️アンチパターン
- 各ページに認証チェックをコピペする（漏れが即事故）
- クライアント側ガード（useEffectでリダイレクト）だけに頼る：一瞬保護ページが見える・JSを切れば素通し
- Cookieの存在チェックだけで「ログイン済み」扱い

### 理解度チェック
- [ ] レイアウトガードが配下全ページに効く仕組みを説明できる
- [ ] middleware.ts 方式とのトレードオフを言える
- [ ] /projects が ƒ（動的）になる理由を言える
- [ ] クライアント側ガードだけではダメな理由を2つ言える

## Phase0 #8 追記: ルートグループ再編（(public)/(guest)/(authenticated)）と middleware の判断

### 何をした
ルートグループを「画面の種類」でなく**アクセス制御の境界**で3分割に再編。`(auth)`→`(guest)`（未ログイン専用・ログイン済みは/projectsへ送るガードを新設）、`(main)`→`(authenticated)`（要ログイン）、LPは`(public)`へ移動。CLAUDE.md・rules・READMEの記述も同期。

### 概念
- **グループ名＝アクセスポリシー**: フォルダ名を見ただけで「誰が入れるか」が分かる。新ページの置き場所に迷わない（認可の設計をディレクトリ構造で表現）
- **guestガード**: ログイン済みユーザーがlogin/signupを開いたら/projectsへ。UX改善＋「ログイン済みで再ログイン」の混乱防止
- **middleware.ts を今は入れない判断**: レイアウトガードで機能要件は満済。middlewareの利点（エッジでの早期リダイレクト）は本番規模で効く話で、学習初期は「ガードが2箇所」の追いにくさが上回る。保護グループが増えた/無駄リクエストを削りたくなったら matcher 込みで導入を再検討

### ⚠️アンチパターン
- URLの見た目でグループを分ける（/auth/xxx のようにURLに漏らすためにグループを使わない。グループはURLに現れないのが利点）
- ガードをグループlayout以外の場所に散らす

## Phase0 #24: Prettier 設定＋ESLint連携

### 何をした
`.prettierrc`（semi:false・singleQuote:true）と `.prettierignore` をコミットし、エディタ依存だった整形スタイルをリポジトリの設定として再現可能に。`eslint-config-prettier` をflat configの最後に追加してESLintの整形系ルールを無効化。`format`/`format:check` スクリプトを追加し全ファイルを一括正規化。

### 概念
- **linterとformatterの分業**: ESLint=コード品質（バグの芽・誤用）、Prettier=整形（見た目）。ESLintに整形をやらせると2つのツールが同じ行を取り合って喧嘩する
- **eslint-config-prettier**: ESLint側の「整形に関するルール」だけを全部offにする設定。**必ず設定配列の最後**に置く（後勝ちで上書きするため）
- **設定をコミットする意味**: エディタの個人設定に依存した整形は、クローン先・チームメンバー・CIで再現されない。`.prettierrc` がスタイルの単一の真実

### ✅ベストプラクティス
- lockファイル・生成物（.next等）は .prettierignore で除外
- 導入時に `format` で全ファイル一括正規化し「整形だけのdiff」を1コミットに隔離する

### ⚠️アンチパターン
- ESLintの整形系ルール（semi等）とPrettierの併用（無限に直し合う）
- 機能変更と整形を同じコミットに混ぜる（レビューで本質的な変更が埋もれる）

- [ ] ESLintとPrettierの役割分担を説明できる

## Phase0 #26: Vitest + Testing Library（テスト基盤と見本）

### 何をした
Vitest（jsdom・tsconfigPathsネイティブ解決）＋Testing Library＋user-eventを導入し、LoginFormの見本テスト2本（失敗時のエラー表示・成功時の遷移と二重送信防止）を作成。web-ciにTestステップを追加。依存競合（shadcn CLIパッケージ vs @vitejs/plugin-react@6のBabel8系）は plugin-react@5 へのダウングレードで解決。

### 概念
- **Testing Libraryの思想**: 実装詳細（state・関数名）でなく「ユーザーから見える振る舞い」をテストする。`getByRole('button', {name})` / `getByLabelText` で取得＝a11yが正しいほどテストが書きやすい（同じ方向を向く）
- **vi.mock + vi.hoisted**: vi.mockはファイル先頭に巻き上げられるため、参照するモック関数は vi.hoisted で先に生成。lib/に通信を集約した設計(#7)のおかげで login 1関数の差し替えだけでテスト可能
- **findByRole**: 非同期に現れる要素を待って取得（get=即時・query=無くてもnull・find=待つ）
- **userEvent**: fireEventより実挙動に近い（type はキー入力を1文字ずつ再現）
- **afterEach(cleanup)**: グローバル設定を使わない場合は明示的にDOM破棄（テスト間汚染防止）

### ✅ベストプラクティス
- コンポーネントと同じ場所に .test.tsx を置く（コロケーション）
- role="alert" の検証はUI仕様とa11y仕様を同時にテストしている
- 依存追加で競合したらログの依存チェーンを読み、最小の変更（1パッケージのメジャー選択）で解決する

### ⚠️アンチパターン
- 内部stateやclassNameでのアサーション（リファクタで壊れる脆いテスト）
- fetchを直接モック（lib集約を飛び越えるとテストが実装詳細に癒着）

- [ ] vi.hoisted が必要な理由（巻き上げ）を説明できる

## Phase0 #30: error.tsx / loading.tsx / not-found.tsx（境界の見本）

### 何をした
(authenticated) に error.tsx（再試行つきエラー境界）と loading.tsx（Skeletonフォールバック）、app直下に not-found.tsx を配置。shadcn skeleton を追加。

### 概念
- **error.tsx = エラー境界**: 同セグメント以下のページで throw されたエラーを捕まえ、アプリ全体のクラッシュを画面単位の失敗に限定する。React の Error Boundary（クラスコンポーネントの仕組み）を App Router がファイル規約に昇格させたもの。**クライアント側の仕組みなので 'use client' 必須**
- **error.tsx は同階層の layout を包まない**: 境界は「layoutの内側・pageの外側」に挟まる。layoutで起きたエラーは1つ上の error.tsx が受ける（ヘッダーは生きたままコンテンツ部だけエラー表示になる）
- **reset()**: 境界内を再レンダリングして復帰を試みる。一時的な失敗（ネットワーク断など）なら再試行で直る
- **loading.tsx = 自動Suspense**: page を `<Suspense fallback={<Loading/>}>` で包んだのと同等。サーバーがデータ取得している間、先にスケルトンが届く（streaming）
- **not-found.tsx**: 存在しないURL＋`notFound()` 呼び出しの両方で表示される
- **スケルトンは「次に来る画面の形」を予告する**: スピナーより体感が速い（レイアウトシフトも防ぐ）

### ✅ベストプラクティス
- エラー文言は具体的な内部情報を出さない（メッセージはユーザー向け・詳細はconsole/監視へ）
- スケルトンは実画面のレイアウトに近い形にする（#10で一覧が決まったら合わせて調整）

### ⚠️アンチパターン
- error.tsx を置かず1コのエラーで画面全体が白画面になる
- エラー境界に error.message をそのまま表示（内部情報の漏えい）

### 理解度チェック
- [ ] error.tsx に 'use client' が必須な理由を言える
- [ ] reset() が何をするか言える
- [ ] loading.tsx と Suspense の関係を言える

## Phase1 #46: プロフィール画面（React Hook Form + Zod デビュー）

### 何をした
`/profile`（(authenticated)）でRSC取得→role別フォーム（企業/人材）を表示。RHF + Zod（standardSchemaResolver）を初導入。書き込みはBFF（/api/profile）経由でPUT。ヘッダーに導線追加。

### 概念
- **React Hook Form の非制御方式**: `register('name')` が name/onChange/ref をまとめて渡す。入力のたびに state を更新しないため**キー入力ごとの再レンダリングが起きない**（フィールドが多いほど効く。#7のuseState方式との対比）
- **Zod と型の単一の真実**: `z.infer` でスキーマから型を導出。バリデーションルールと型定義がズレない
- **`z.input` と `z.output`**: `transform` があるスキーマは入力型と出力型が別物。skills はフォームで string（カンマ区切り）→ 送信時 string[] へ変換。`useForm<入力型, unknown, 出力型>` の3型引数で接続する
- **standardSchemaResolver**: Zod 4 は Standard Schema 準拠になったため、zodResolver でなく汎用リゾルバで繋ぐ（valibot等へ乗り換えても同じAPI）
- **二重バリデーション**: フロント（Zod）=即時フィードバック・UX／サーバー（Go）=最後の防衛線・セキュリティ。文言を揃えると体験が一貫する
- **`noValidate`**: ブラウザ標準検証を止めてZodに一本化（2種類のエラー表示が混ざるのを防ぐ）
- **`handleSubmit(onSubmit)`**: 検証通過時のみ onSubmit を呼ぶ。ハンドラ内では検証を気にしなくてよい
- **`formState.isSubmitting`**: 送信中フラグがRHF標準で手に入る（#7では自前useStateだった）
- **配列入力の設計判断**: タグUIは実装コストが高いため、カンマ区切り1入力＋`transform`で配列化。API↔フォームの相互変換（joinSkills / splitSkills）を lib に置く

### ✅ベストプラクティス
- RSCが取得した値をそのまま `defaultValues` に渡す（未作成なら空オブジェクト）
- 保存成功後は `router.refresh()` でRSCを再実行し表示を最新化
- クライアント検証エラーとサーバー由来エラーを別々のstateで持ち、どちらもフィールド近傍/フォーム下に `role="alert"` で表示

### ⚠️アンチパターン
- フロント検証だけで安心する（curlで直接叩かれる。サーバー検証が本体）
- スキーマに server-only を付ける（クライアントから import できなくなる）
- 依存追加後にDockerコンテナ側で npm install せず「モジュールが見つからない」で消耗する（node_modulesが遮蔽ボリュームのため。ローカル直起動運用が無難）

### 理解度チェック
- [ ] RHFの非制御方式が再レンダリングを減らす仕組みを説明できる
- [ ] z.input と z.output が分かれる理由を skills の例で説明できる
- [ ] フロントとサーバーで同じ検証を書く理由を役割の違いで説明できる

## Phase1 #10: 案件一覧・検索・詳細・掲載フォーム

### 何をした
人材側（`/talent/projects` 一覧＋検索＋ページネーション、`/talent/projects/[id]` 詳細）と企業側（`/company/projects` 管理、`/company/projects/new` 掲載フォーム）を実装。5万件のデータに対して動作。

### 概念
- **検索条件をURLに持たせる**: state ではなく URL クエリに持つと、(1)共有できる (2)ブラウザバックが効く (3)**RSCが `searchParams` で直接受け取れる**（クライアントでの再fetchが不要）。条件変更→URL変更→RSC再実行→新しいHTML、という流れでクライアントに検索結果の state を持たない
- **`searchParams` / `params` は Promise**（Next.js 15+ で非同期API化）。`await` が必要
- **動的ルート `[id]`**: フォルダ名の角括弧がURLの可変部分になる。Go側の `r.PathValue` と対
- **`notFound()`**: 例外throwで `app/not-found.tsx` を表示。この行より下では型が非nullに絞り込まれる
- **`generateMetadata`**: 動的なページタイトル。同一リクエスト内の同じfetchは**自動で重複排除**されるため、page と metadata で同じ関数を呼んでもHTTPは1回
- **ページャの責務分担**: 検索フォームは「条件を変えたら page を1に戻す」／ページャは「条件を保ったまま page だけ変える」。逆にすると3ページ目で絞り込んで空になる事故が起きる
- **非制御コンポーネント（`defaultValue` + FormData）**: URLが真実の情報源なので、入力中の値をReactが管理する必要がない
- **Zod の `refine` によるクロスフィールド検証**: `path: ['hourly_rate_max']` でエラーを特定フィールドに紐づけられる

### ✅ベストプラクティス
- 空欄はURLに載せない（`?skills=&q=` のようなノイズを防ぐ）
- DBの `0=未設定` を「応相談」など**意味のある言葉に翻訳**して表示する
- `whitespace-pre-wrap`（改行保持）と `break-words`（横スクロール防止）をユーザー入力の表示に付ける
- `tabular-nums` で数値の桁揃え（一覧の見た目が安定する）

### ⚠️アンチパターン
- 検索条件を useState に持つ（共有・戻る・RSC連携をすべて失う）
- 条件変更時にページ番号を引き継ぐ（結果が空のページに着地する）
- 未設定を `0円` とそのまま表示する

### 理解度チェック
- [ ] 検索条件をURLに持たせる利点を3つ言える
- [ ] 検索フォームとページャで page の扱いを変える理由を言える
- [ ] `notFound()` が型の絞り込みに効く理由を言える

## Phase1 #70: UI部品基盤の拡充

### 何をした
shadcn/ui に badge / select / sonner / separator を追加し、自前実装（`<span>` のタグ表示・生の `<select>`）を置き換え。`PageHeader` / `EmptyState` を作成して8画面の書式を統一。余白・タイポのスケールを `docs/デザインシステム.md` に明文化。

### 概念
- **モジュラースケール**: 余白や文字サイズは「任意の値」ではなく決まった段階（12/14/16/18/24・4/8pxグリッド）から選ぶ。ばらつきが「揃っていない感じ」の正体
- **入力欄は16px以上**: モバイルSafariは16px未満のinputにフォーカスすると**自動ズーム**する（意図しない拡大の原因）
- **Radix Select と RHF の接続**: shadcn の Select は `<select>` ではなく button+ポップオーバーのため `register`（DOMにrefを刺す）では繋がらない。**`Controller`** で制御コンポーネントとして扱う
  - `register` = 非制御（input / textarea）／`Controller` = カスタムUI部品
- **アイコンの扱いは「意味を持つか装飾か」で変わる**: 装飾なら `aria-hidden="true"`（意味はテキストが担う）、アイコンのみのボタンなら `aria-label` が必須
- **空状態は最初に見る画面**: 新規登録直後のユーザーが最初に出会うのは空の一覧。「何も無い」で終わらせず、理由と次の行動を置く。`EmptyState` は icon を必須プロパティにして型で強制した
- **見出しの集約**: h1 を `PageHeader` に集約すると、見出し階層の管理が1か所になり、書式のばらつきも消える

### ✅ベストプラクティス
- 共通部品は「使うと自然に規約が守られる」形にする（PageHeader を使えば見出し書式が揃う・EmptyState を使えば導線が置かれる）
- 同じ「空」でも文脈で言葉を変える（検索0件=「条件をゆるめては」／未作成=「最初の案件を掲載する」）
- 数値表示は `tabular-nums`（桁変動でレイアウトが揺れない）

### ⚠️アンチパターン
- 生の `<select>`（OS依存の見た目・キーボード操作やaria を自前実装することになる）
- 自前のタグ表示（`rounded-full bg-secondary` の直書き）を各所にコピペする
- 空状態を1行のテキストで済ませる

- [ ] `register` と `Controller` の使い分けを言える
- [ ] アイコンに aria-hidden / aria-label のどちらを付けるか判断できる
