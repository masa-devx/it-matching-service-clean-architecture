2. 解決する課題（なぜ作るか）

市場背景

  • 副業解禁・リモートワークの定着で、エンジニアの副業・業務委託は一般化した
  • 一方で中小企業・スタートアップは正社員エンジニアの採用が困難（採用競争・年収高騰）→ 副業/業務委託の活用が現実解
  • しかし両者をつなぐ場には、信頼とお金のトラブルという構造的な課題が残っている

三者の課題（一人称）

立場課題
企業（発注側）「正社員を雇う余裕はないが技術力が必要」「誰が本当にできる人か見極められない」「業務委託の契約・支払い事務が面倒」「途中で音信不通になったら…」
IT人材（受注側）「副業を始めたいが最初の案件の入口がない」「相場が分からない」「納品したのに支払われないリスク」「作業スコープが際限なく膨らむ」「実績が形に残らない」
プラットフォーム（運営）「直接取引（中抜け）で手数料を回避される」「報復レビューで評価が信頼できなくなる」「ミスマッチによる炎上・トラブル」
本質：マッチングサービスの価値は「出会わせること」ではなく「知らない者同士が安心して取引できる仕組み」。だから本作の独自機能はすべて信頼の設計（お金・連絡・評価・本人性）に集中させる。

3. 機能一覧（＝「なぜ作るか」との対応表）

各機能に「解決する課題」を併記。MVP / 拡張 / やらない

A. アカウント・プロフィール

機能なぜ作るか（解決する課題）区分
会員登録・認証（JWT＋httpOnly Cookie）基盤（todo-appの型を再利用）MVP
企業プロフィール／人材プロフィール（スキル・稼働可能時間・希望単価・経歴）「誰なのか」を構造化して見極めコストを下げるMVP
KYC（本人確認）：書類アップロード→審査→承認バッジ「音信不通・なりすまし」への安心。it-supportのKYC構造を模倣MVP（簡易版）
実績バッジ・累計稼働時間の可視化「実績が形に残らない」→ 続けるほど信頼が積み上がる拡張

B. 案件・応募（マッチング）

機能なぜ作るか区分
案件の掲載（テンプレで迷わず書ける：業務内容・スキル・単価・稼働・リモート可否）発注に不慣れな企業の募集の質を底上げ（ミスマッチの根本原因対策）MVP
検索一覧（スキル×単価×稼働×リモートのフィルタ・seekページング）「入口がない」→ 発見性。1万件シードで性能計測の主戦場にするMVP
応募 → 選考（書類→面談）→ 承諾（状態機械①）選考の現在地を双方に可視化（「音沙汰なし」の不安を消す）MVP
ダブルオプトイン成立（両者承諾で初めて契約へ）片思い状態での進行を防ぎミスマッチを減らすMVP
スカウト（企業→人材への逆オファー）企業側の能動的な発見拡張

C. 契約・稼働

機能なぜ作るか区分
契約管理（状態機械②：契約中→検収待ち→完了/中止）＋ステータストラッカー「今どういう状態？」を宅配便追跡のように可視化＝透明性が信頼を作るMVP
稼働報告（週次レポート・作業ログ）リモート業務委託の「ちゃんと働いてる？が見えない」不安（企業側）と「働いた証拠を残したい」（人材側）を同時に解決MVP
スコープ変更の記録（追加作業の合意ログ）「作業が際限なく膨らむ」→ 合意を形に残す拡張

D. 決済（エスクロー）独自機能の柱

機能なぜ作るか区分
エスクロー決済（状態機械③）：契約時に企業が仮払い → 検収 → 人材へ支払い人材の「未払いリスク」と企業の「前払いリスク」を同時に解決する、マッチングの信頼の核。お金の状態機械として設計の見せ場拡張（最優先）
請求書・支払記録のPDF出力両者の事務コスト削減拡張

E. 信頼・安全（プラットフォームの生命線）

機能なぜ作るか区分
メッセージ機能＋連絡先の自動マスキング（メール/電話番号を検出して伏せる）直接取引（中抜け）の防止＝マッチング事業の生命線。実務で必ず問われる仕組みMVP（マスキングはMVP後半）
レビュー同時公開（両者が書き終わるまで互いに非公開→同時公開）報復レビューを防ぎ、評価の信頼性を守る（Airbnb方式の公平性設計）MVP
通報・運営対応トラブルの逃げ道拡張

F. 管理・可視化

機能なぜ作るか区分
企業ダッシュボード（募集中案件・応募状況・契約中の稼働）管理画面の見せ場（大量テーブル・集計）MVP後半
人材ダッシュボード（応募状況・稼働時間・収入見込み）副業の「自分の現在地」可視化拡張
通知（応募・承諾・検収依頼・レビュー依頼）状態遷移の見逃し防止MVP（アプリ内）

G. やらないこと

AI機能（レコメンド・自動マッチング）／リアルタイムチャット（WebSocket）／モバイルアプリ／複数通貨・国際対応やらない（スコープ防衛。メッセージはポーリング/更新ベースで十分）

4. it-support-service との構造対応（模倣マップ）

it-support-service→ 本サービス模倣で学ぶこと
企業（支援を求める側）企業（発注側）Go クリーンアーキ（handler→usecase→repository）／スキーマ駆動（TypeSpec/OpenAPI→型生成）／状態遷移設計／KYCワークフロー／Next.js App Router・RSC の境界設計
サポーター（提供側）IT人材（副業・フリーランス）
プロジェクト掲載案件掲載
支援プラン・契約（状態遷移）応募→選考→契約→検収→完了（状態機械①②）
KYC（本人確認）KYC（書類→審査→バッジ）
決済エスクロー決済（状態機械③）← 本作で深化させる部分
模倣の進め方：各Phaseで「①参考実装の該当層を読む → ②自分のドメイン語彙で再実装 → ③差分を説明できるか確認」。丸写しではなく「読んで・書いて・比べる」のサイクルで、面接で『なぜこの設計か』を自分の言葉にする。

5. 状態遷移（状態機械3本）

① 選考 applications:
   応募 → 書類選考 → 面談 → 承諾（ダブルオプトイン成立）／ 見送り ／ 取り下げ

② 契約 contracts:
   成立 → 稼働中 →（稼働報告を積む）→ 検収待ち → 完了 ／ 中止
                                        └ 差し戻し → 稼働中（修正対応）

③ 決済 payments（エスクロー・お金の状態機械）★独自の柱:
   仮払い待ち → 仮払い済み(エスクロー) → 検収OK → 支払い実行 → 支払い完了
                └ 中止時 → 返金

⑤ レビュー:
   契約完了 → 両者が提出 → 同時公開（片方だけでは公開されない・期限で自動公開）

★ ②契約 と ③決済 が連動する（検収=契約の遷移がお金の遷移を引き起こす）。「業務の状態」と「お金の状態」を別の機械として分離しつつ同期させるのが設計の見せ場。

6. データ設計

-- ユーザー（1ユーザーが企業/人材どちらのロールも持てる設計も可。まずは択一で簡素に）
users           id, email, password_hash, name, role(company/talent), created_at

companies       id, user_id, name, description, industry, size
talents         id, user_id, bio, skills[](Go/React/AWS…), years_of_exp,
                available_hours_per_week, desired_hourly_rate, remote_ok

identifications id, user_id, doc_type(本人確認書類), file_url,
                status(審査中/承認/却下), verified_at            -- KYC

-- 案件と応募
projects        id, company_id, title, description, required_skills[],
                hourly_rate_min/max, hours_per_week, remote_ok,
                status(下書き/公開/締切), created_at
applications    id, project_id, talent_id, message,
                status(応募/書類/面談/承諾/見送り/取り下げ)       -- 状態機械①

-- 契約・稼働・決済
contracts       id, application_id, hourly_rate, start_date, end_date,
                status(成立/稼働中/検収待ち/完了/中止)            -- 状態機械②
work_reports    id, contract_id, week_start, hours, summary,
                status(提出済/承認/差し戻し)                      -- 稼働報告
payments        id, contract_id, amount, stripe_payment_intent_id,
                status(仮払い待ち/仮払い済み/支払い実行/完了/返金),  -- 状態機械③
                idempotency_key                                   -- 冪等性★

-- 信頼・安全
messages        id, contract_id(or application_id), sender_id, body,
                masked_body, masked(bool)                         -- マスキング
reviews         id, contract_id, reviewer_role(company/talent),
                rating, comment, submitted_at, published_at       -- 同時公開
notifications   id, user_id, type, payload, read_at

データ設計の「見せ場」

見せ場内容
1. 業務とお金の状態分離contracts（業務）と payments（お金）を別の状態機械にし、「検収OK→支払い実行」で同期。混ぜると破綻する典型例を、分けて設計したと語れる
2. 決済の冪等性Stripe Webhookは重複配送があり得る → idempotency_key＋処理済み判定で二重支払いを構造的に防ぐ
3. レビュー同時公開submitted_at（提出）と published_at（公開）を分離。両者揃うか期限到来で公開するロジック
4. マスキングの監査性body（原文）と masked_body（表示用）を分けて保存 → 運営がトラブル調査できる（＋個人情報の扱いを語れる）
5. 検索設計skills[] にGINインデックス・単価/稼働のレンジ検索・seekページング。1万件シードで計測

8. 技術的な課題と解法

課題何が難しいか解法・学び
エスクロー決済仮払い（与信）→検収→キャプチャの流れ。Webhookの重複配送・順序保証なしStripe PaymentIntent（manual capture）＋idempotency_key＋イベント処理済みテーブル。お金は「最低1回」でなく「ちょうど1回」を作り込む
状態機械の整合選考①・契約②・決済③が連動。不正な遷移（検収前に支払い等）を許すと事故遷移表を定義→usecase層でガード→テーブル駆動テストで全遷移を網羅（go-basicsのテスト手法が活きる）
連絡先マスキングメール・電話・SNS IDの検出。正規表現の限界（全角・分かち書き回避）まず基本パターン（メール/電話/URL）＋原文保存で監査可能に。完璧でなく「抑止＋検知」を狙うと設計思想を語る
レビュー同時公開「両者揃うまで非公開」＋「片方が書かない場合」の扱いsubmitted/published分離＋期限（14日）で自動公開のバッチ
検索パフォーマンススキル配列×レンジ×ソートの複合条件で1万件GINインデックス・seekページング・EXPLAIN ANALYZEで計測 → before/after数値化
楽観的更新の整合応募・承諾の連打・失敗時のUI巻き戻しTanStack QueryのonMutate/onError/onSettledでロールバック＋invalidate
認可企業/人材/運営のロール×所有者チェック（自分の案件だけ編集等）todo-appのIDOR対策を発展：ロール×リソース所有の二重チェックをミドルウェア＋usecaseで
スキーマ駆動の運用API変更のたびに型がズレる問題OpenAPI定義を単一の真実に→生成型をフロント/バック両方が参照（it-supportの手法を模倣）

10. MVPスライスとビルド順

MVPスライス（最初に1周する線）：
登録（企業/人材）→ 案件掲載 → 検索 → 応募 → 選考 → 承諾（ダブルオプトイン）→ 契約 → 稼働報告 → 検収 → 完了 → レビュー同時公開
※エスクロー決済（Stripe）は拡張最優先（MVP完成後すぐ着手）。KYCはMVPでは簡易版（書類アップ＋手動承認）
Phase作るもの学びの核
0環境（monorepo api/web・docker・OpenAPIセットアップ）＋ it-support読解（設計研究ノートと突き合わせ）参考実装の全体像
1認証＋企業/人材プロフィール（Goクリーンアーキの土台・簡易KYC）handler→usecase→repository・DI
2案件CRUD＋検索一覧（RSC・フォーム・シードデータ）RSC境界・検索設計・フォームUX
3応募→選考→承諾（状態機械①・楽観的更新・トラッカー）TanStack Query・状態遷移テスト
4契約＋稼働報告＋検収（状態機械②）業務の状態設計・タイムライン
5メッセージ（マスキング）＋レビュー同時公開 ＝ MVP完成信頼の設計・バッチ処理
拡張エスクロー決済(Stripe) → 企業ダッシュボード → 1万件計測 → Storybook → スカウト → 実績バッジ各段が面接ネタ
