# 開発ワークフロー

## ステップの型（理解して作る）

1. **Issueが指定されたら、まず Claude がブランチを作成・切り替え**（`phase{N}/{Issue番号}-{内容}`）。現在ブランチを確認してから作業する
2. **実装前に方針を宣言**（何を・なぜ・どう作るか）→ ユーザーのOKを得てから書く
3. 1ステップ＝1つの小さな増分（例:「signup だけ」「一覧APIだけ」。大きいIssueは2〜3分割）
4. 実装 → **詳細解説（何を/生成物のウォークスルー/なぜ/新出概念/✅ベストプラクティス/⚠️アンチパターン/理解度チェック□）→ ユーザー確認 → コミット（ユーザーが実施）** の順を崩さない
   - ウォークスルーでは生成・変更したファイルの中身をブロックごとに引用し、ユーザーがコードを読みながら理解を確認できるようにする
5. **理解度ゲート**: チェックに自分の言葉で答えられない項目は質問→解消してから次へ。**分からないままマージしない**
6. 解説では、ユーザーが学習済みの内容（todo-app・react-basics・go-basics）と接続して説明する
7. 新出の概念・実務のコツ・ハマりは `docs/`（バックエンド.md / DB.md / フロントエンド.md）へ追記する
8. **PR本文の「対応内容」はユーザーが自分の言葉で書く**（Claudeは求められたときだけ下書き補助）
9. コード内コメントは実務品質（whyのみ）。学習用の逐行解説はコードに書かず、チャットと docs/ に置く

## やらないこと

- 一度に複数機能をまとめて実装しない
- **`git add` / `git commit` / `git push` は Claude が行わない**（コミットはユーザーが機能ごとに小さく実施。`git status` / `diff` / `log` の確認は可）
- サーバーの起動・停止（`go run` / `npm run dev`）は Claude が行わない（build/vet/test まで）

## リファクタ（R1〜R3）のとき

- 必ず `refactor/xxx` ブランチで行う
- 「なぜこのタイミングで層を分けるのか（どんな痛みが出たか）」を解説し、docs に記録する
